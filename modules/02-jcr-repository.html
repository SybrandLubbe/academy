JCR & the Content Repository

Every piece of content in AEM — a page, an image, a component's settings, a user's profile — is a node in one big tree. Learn to read that tree and you can debug almost anything without guessing.

What you'll learn

  • Nodes, properties, and how paths map to the tree structure
  • The node types you'll see constantly: cq:Page, nt:unstructured, nt:folder
  • What the jcr:, cq:, and sling: namespace prefixes mean
  • The standard top-level paths and what belongs in each
  • How to browse and query the repository yourself

Nodes and properties

A JCR repository is a tree of nodes. Each node has a name, a path, a primary type that determines what properties and child nodes it's allowed to have, and zero or more properties — typed key/value pairs (string, boolean, date, binary, long, and reference types are the common ones). A node can hold child nodes, so the tree can go arbitrarily deep.

A page in AEM is actually two nodes stacked on top of each other:

a page, as nodes/content/my-site/en/about            [cq:Page]
/content/my-site/en/about/jcr:content [cq:PageContent]
    jcr:title = "About Us"
    sling:resourceType = "my-site/components/page"
    jcr:createdBy = "jdoe"

The outer node (cq:Page) is mostly a container — it exists so AEM has something stable to version and reference. The actual content — title, components, properties an author sets in a dialog — lives under jcr:content. This split trips up almost every new developer at least once: if you're looking for a page's title in code and querying the wrong node, you'll get nothing back.

Common pitfall /content/my-site/en/about and /content/my-site/en/about/jcr:content are different nodes with different properties. Page-level metadata (title, template, properties set in the page properties dialog) lives under jcr:content, not on the page node itself.

Namespaces, in plain terms

Node and property names are often prefixed, and each prefix tells you where the concept comes from:

  • jcr: — core JCR spec (jcr:content, jcr:title, jcr:primaryType)
  • nt: — built-in JCR node types (nt:unstructured, nt:folder, nt:file)
  • cq: — AEM-specific concepts inherited from the old "Communiqué" product name (cq:Page, cq:dialog, cq:template)
  • sling: — Sling-specific properties, most importantly sling:resourceType, which you'll meet properly in the next module

The top-level paths

A handful of root paths show up in every AEM project, and knowing what belongs where will save you a lot of confusion early on:

repository root/content    → authored content: pages, assets metadata, experience fragments
/apps       → your project's code: components, templates, clientlibs, OSGi configs
/libs       → out-of-the-box AEM code — read-only, never modify
/conf       → configuration: templates' policies, cloud configs (modern AEM)
/etc        → legacy location for some configs/design content (older projects)
/var        → runtime/internal data: audit logs, workflow instances
/home       → user and group nodes (authentication/authorization)
Mental model If you're not sure where something lives, ask: "is this content an author typed in, or code a developer wrote?" Content goes under /content. Code goes under /apps. Almost everything else is a variation on that split.

Mixins and versioning

Beyond a primary type, a node can have one or more mixin types that add optional capabilities — for example mix:versionable lets a node participate in JCR versioning (used for page version history), and mix:lockable lets it be locked for exclusive editing. You won't author these by hand often, but you'll see them in node properties and they explain features like "Page History" in the author UI.

Exploring the repository yourself

Two tools you'll use constantly as a backend developer:

  • CRXDE Lite (/crx/de) — a browser-based tree explorer and editor. Good for poking around and quick debugging; not where you do real development.
  • Query Builder / JCR-SQL2 — for finding nodes by criteria rather than walking the tree by hand, e.g. "all pages with a given template" or "all assets tagged X."
Try it In CRXDE Lite, navigate to any existing page's jcr:content node and look at its properties panel. Find sling:resourceType and note its value — you'll use exactly this property to understand rendering in the next module.
