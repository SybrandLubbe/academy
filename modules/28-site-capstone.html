Capstone 90 min task

Capstone — Mini Site, Live Copy & Dynamic Navigation

Everything in this training leads here. You will build a real multi-language mini site from scratch in AEM, create a live copy from the English master, add five or more pages with real content, and implement a Sling Model–driven navigation bar that automatically discovers and links every page you add — with no authoring required and no code changes when the site grows.

What you're building

  • A mini site under /content/academy-mini/en/ — the English language master
  • At least 5 pages with content authored using existing Core Components
  • A German live copy at /content/academy-mini/de/ using AEM Multi-Site Manager
  • A custom navigation component: full Java model, HTL template, CSS, and JavaScript
  • The navigation reads child pages from the JCR at runtime — add a page, it appears in the nav automatically
  • Dropdown support for sub-pages, active-state highlighting, and mobile responsiveness
Modules this capstone draws from Site structure (02), Sling framework (03), Sling Models (06+07), HTL (09), Components (11+12), OSGi Config (05). Every annotation and pattern in the code below has been covered. If something looks unfamiliar, the module number is noted in the comment above it.

📖 Why this code?

This structure follows the exact same conventions as a production Netcentric AEM project. Each choice has a reason.

  • /content/academy-mini/en/ — the en folder is the language root, at JCR depth 3 (/content/[site]/[language]). The navigation model will auto-detect this depth to find the site root, so the nav works on every page without any configuration.
  • courses/ has sub-pages — this tests the dropdown behaviour. The navigation model recurses one level deep; sub-pages of sub-pages are deliberately not shown (three-level navs confuse users).
  • de/ as a live copy — MSM keeps German pages synchronised with English. Authors editing the English master can roll out changes to German automatically. German editors can localise copy without disconnecting from the master.
  • /apps/academy/components/navigation/ — under your project's component tree, not under /libs. This is the only safe place for custom code (module 01).

📖 Why this code?

The page naming choices here are deliberate, not arbitrary.

  • Name vs Title — the Name becomes the URL path segment and the JCR node name (e.g. about → /content/academy-mini/en/about → URL /content/academy-mini/en/about.html). The Title is what the navigation component displays. Keeping names short and URL-safe, and titles human-readable, is the correct separation.
  • List component in "child pages" mode — this is a Core Component feature that automatically discovers and links child pages. It demonstrates the same pattern your navigation component will use at the site level.
  • Manage Publication with "Include Children" — AEM's replication system. Publishing the root alone doesn't publish children. The "Include Children" checkbox traverses the subtree and queues every child page for replication to the publish instance.

Part 3 — Create a Live Copy (DE from EN master)

AEM's Multi-Site Manager (MSM) creates a live relationship between a source tree and one or more target trees. Changes to the source can be rolled out to targets automatically or manually. The live copy pages share content with the source until a page is detached or a property is cancelled.

creating the DE live copy — AEM author UI stepsMETHOD 1 — Sites console (recommended)
  1. Navigate to /content/academy-mini/en in the Sites console.
  2. Select the "en" page (checkbox, not the page title).
  3. Top toolbar → Create → Live Copy.
  4. In the wizard:
       Source:           /content/academy-mini/en   (pre-filled)
       Destination:      /content/academy-mini/
       Title:            Deutsch
       Name:             de
       Rollout Config:   Standard rollout config
                         (synchronises on source activation by default)
  5. Click Create.

MSM creates /content/academy-mini/de/ with:
  - All the same child pages as en/
  - Each page marked with jcr:mixinTypes = [msm:LiveRelationship]
  - A cq:LiveSyncConfig node storing the source path and rollout config

METHOD 2 — CRXDE (shows what MSM creates under the hood)
  After creating via UI, inspect the result in CRXDE:

  /content/academy-mini/de/jcr:content
    cq:isDelivered     = true
    jcr:mixinTypes     = [msm:LiveRelationship]

  /content/academy-mini/de/jcr:content/cq:LiveSyncConfig
    jcr:primaryType    = "cq:LiveSyncConfig"
    cq:master          = "/content/academy-mini/en"
    cq:rolloutConfigs  = ["/libs/msm/wcm/rolloutconfigs/default"]
    cq:isDeep          = true   ← live copy applies to all descendants
📖 Why this code?

MSM is one of AEM's most powerful — and most misunderstood — features. These details help you debug it when it doesn't behave as expected.

  • jcr:mixinTypes = [msm:LiveRelationship] — mixin types are additional node type declarations that add capability without changing the primary type. MSM adds this mixin to mark a page as part of a live copy. You can check this in CRXDE to instantly confirm which pages are live copies and which are not.
  • cq:isDeep = true — the live copy relationship applies to the entire subtree, not just the root page. When you roll out a change to en/courses/aem-basics, it propagates to de/courses/aem-basics too.
  • Rollout configs determine what triggers synchronisation: the Standard config rolls out when the source page is activated (published). Other configs roll out on page creation, deletion, or on a schedule. For localisation projects, you often want manual rollout so German editors aren't surprised by overnight content changes.
  • Cancelled properties — when a German editor changes the page title in de/about, MSM "cancels" that property on the live copy. The EN master still controls all other properties, but the title is now locally owned. This is the intended localisation mechanism.
rolling out changes from EN to DE — the day-to-day workflowROLL OUT A SINGLE PAGE
  Sites console → select en/about → More options (⋯) → Rollout
  Or: open en/about → Page Properties → Live Copy tab → Rollout

ROLL OUT THE ENTIRE SITE AT ONCE
  Sites console → select en/ → Rollout → tick "Include Subpages"
  All changed pages flow to de/ in one operation.

VERIFY LIVE COPY STATUS
  Sites console → en/ → Live Copy Overview (globe icon)
  Green = in sync. Orange = inherited but locally modified. Red = detached.

DETACH A PAGE FROM THE LIVE COPY
  de/about → Page Properties → Live Copy tab → Detach
  After detach: de/about is a fully independent page.
  Use for pages that need completely different content in DE —
  not just translated copy, but different structure entirely.
📖 Why this code?

Rollout is the publish action for multi-site managers — understanding it prevents the most common MSM support issue on real projects.

  • Roll out vs Publish — rolling out copies content from the EN master to DE pages; publishing makes DE pages visible on the publish instance. Both steps are required for changes to reach end users on the German site. Forgetting to publish after rollout is the most common mistake.
  • Live Copy Overview — the most useful MSM tool. Open it before every rollout on a production project to see exactly which pages are out of sync and why. Orange pages have local overrides that will be preserved; red pages won't receive rollout updates at all.

Part 4 — The Navigation Component

This is the core backend development task. You are building a component that requires no authoring — it automatically discovers and links every page in the current site's language root. Add a page, refresh, it appears in the nav. This is what "content-driven navigation" means in AEM.

4a — Component definition

/aem-academy/ui.apps/src/main/content/jcr_root/apps/academy/components/navigation/.content.xml (academy.ui.apps)<?xml version="1.0" encoding="UTF-8"?>
<jcr:root
    xmlns:jcr  ="http://www.jcp.org/jcr/1.0"
    xmlns:sling="http://sling.apache.org/jcr/sling/1.0"
    xmlns:cq   ="http://www.day.com/jcr/cq/1.0"
    jcr:primaryType   ="cq:Component"
    jcr:title         ="Academy Site Navigation"
    jcr:description   ="Horizontal nav bar — auto-built from the current site's child pages."
    componentGroup    ="Academy Training"
    sling:resourceSuperType="core/wcm/components/commons/v1/template"/>
📖 Why this code?

This is the minimal component definition — every field matters.

  • jcr:primaryType="cq:Component" — the node type that registers this folder as a component in AEM's component registry. Without it, AEM treats the folder as just a directory and it never appears in the component browser.
  • componentGroup="Academy Training" — the group name that template policies use to allow or block this component. Must match the group name in your template's content policy for authors to be able to add it.
  • sling:resourceSuperType="core/wcm/components/commons/v1/template" — inherits edit-mode placeholder rendering from Core Components. Without it, the component shows a blank space in the page editor, confusing authors.
  • There is no sling:resourceType here because the component folder is the resource type. The path academy/components/navigation relative to the search path is the resource type string.

By default the model auto-detects the language root. This dialog lets an author override it — useful when embedding the same nav on a microsite at a different path.

📖 Why this code?

This dialog follows the same Granite UI pattern from module 11 — resource type per field, name="./navRootPath" writes to the component's content node, which the Sling Model reads with @ValueMapValue.

  • sling:resourceType="granite/ui/components/coral/foundation/form/pathfield" — renders a path browser field in the author dialog. The author can type or browse to any JCR path, which becomes the navigation root.
  • name="./navRootPath" — the ./ prefix writes the value as a property on the navigation component's own content node. This is the property @ValueMapValue(name = "navRootPath") reads in the Java model.
  • The fieldDescription explains what to leave empty — critical for optional fields. Without it, authors will always fill it in "just to be safe," breaking the auto-detection.

4c — The Sling Model

This is the heart of the component. It reads the JCR page tree at request time and returns a list of typed NavItem objects that the HTL template renders. No caching — the JCR query is lightweight and ensures the nav is always current.

/aem-academy/core/src/main/java/biz/netcentric/academy/core/models/SiteNavigationModel.java (academy.core)package biz.netcentric.academy.core.models;

import com.day.cq.wcm.api.Page;
import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.models.annotations.DefaultInjectionStrategy;
import org.apache.sling.models.annotations.Model;
import org.apache.sling.models.annotations.ScriptVariable;
import org.apache.sling.models.annotations.injectorspecific.ValueMapValue;

import javax.annotation.PostConstruct;
import java.util.ArrayList;
import java.util.Iterator;
import java.util.List;

/**
 * Sling Model for the Academy Site Navigation component.
 *
 * Automatically discovers all child pages of the current language root
 * and builds a typed list of NavItems for HTL rendering.
 * If navRootPath is configured in the dialog, it is used instead.
 */
@Model(
    adaptables            = SlingHttpServletRequest.class,
    defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL
)
public class SiteNavigationModel {

    // currentPage is injected from the HTL script variable scope (module 07)
    @ScriptVariable
    private Page currentPage;

    // Optional: author-configured root path override (from the dialog)
    @ValueMapValue(name = "navRootPath")
    private String navRootPath;

    // ── Internal state ────────────────────────────────────────────────────────
    private List<NavItem> navItems;
    private Page           siteRoot;

    // ─────────────────────────────────────────────────────────────────────────
    // Inner class — one entry in the navigation list
    // ─────────────────────────────────────────────────────────────────────────
    public static class NavItem {
        private final String       title;
        private final String       path;
        private final boolean      active;
        private final List<NavItem> children;

        public NavItem(String title, String path,
                       boolean active, List<NavItem> children) {
            this.title    = title;
            this.path     = path;
            this.active   = active;
            this.children = children != null ? children : new ArrayList<>();
        }

        public String        getTitle()       { return title; }
        public String        getPath()        { return path; }
        public boolean       isActive()       { return active; }
        public List<NavItem> getChildren()    { return children; }
        public boolean       isHasChildren()  { return !children.isEmpty(); }
    }

    // ─────────────────────────────────────────────────────────────────────────
    // Initialisation — runs after all @ValueMapValue and @ScriptVariable fields
    // are populated (PostConstruct — module 06)
    // ─────────────────────────────────────────────────────────────────────────
    @PostConstruct
    private void init() {
        navItems = new ArrayList<>();

        // 1. Find the navigation root
        if (navRootPath != null && !navRootPath.isEmpty()) {
            // Author override: use the configured path
            siteRoot = currentPage.getPageManager().getPage(navRootPath);
        } else {
            // Auto-detect: walk up from the current page to depth 3.
            // Depth 3 = /content/[site]/[language] — the language root.
            siteRoot = currentPage;
            while (siteRoot != null && siteRoot.getDepth() > 3) {
                siteRoot = siteRoot.getParent();
            }
        }

        if (siteRoot == null) return;

        // 2. Iterate direct children of the root — each becomes a nav item
        Iterator<Page> children = siteRoot.listChildren();
        while (children.hasNext()) {
            Page child = children.next();
            if (child.isHideInNav()) continue;  // respect the hideInNav flag
            navItems.add(buildNavItem(child));
        }
    }

    // ─────────────────────────────────────────────────────────────────────────
    // Build a NavItem from a Page, including one level of children (dropdown)
    // ─────────────────────────────────────────────────────────────────────────
    private NavItem buildNavItem(Page page) {
        // Navigation Title takes priority over regular Title (module 02)
        String title = page.getNavigationTitle() != null
            ? page.getNavigationTitle()
            : page.getTitle();
        if (title == null) title = page.getName();  // last-resort fallback

        // Active = current page is this page or a descendant of it
        boolean isActive = currentPage.getPath().startsWith(page.getPath());

        // Recurse ONE level for dropdown sub-items
        List<NavItem> childItems = new ArrayList<>();
        Iterator<Page> subPages = page.listChildren();
        while (subPages.hasNext()) {
            Page sub = subPages.next();
            if (sub.isHideInNav()) continue;
            boolean subActive = currentPage.getPath().startsWith(sub.getPath());
            childItems.add(new NavItem(
                sub.getNavigationTitle() != null
                    ? sub.getNavigationTitle() : sub.getTitle(),
                sub.getPath() + ".html",
                subActive,
                new ArrayList<>()  // no third level — keeps the nav usable
            ));
        }

        return new NavItem(title, page.getPath() + ".html", isActive, childItems);
    }

    // ─────────────────────────────────────────────────────────────────────────
    // Public accessors — called by the HTL template
    // ─────────────────────────────────────────────────────────────────────────
    public List<NavItem> getNavItems()    { return navItems; }
    public String         getSiteTitle()  {
        return siteRoot != null ? siteRoot.getTitle() : "";
    }
    public String         getSiteRootPath() {
        return siteRoot != null ? siteRoot.getPath() + ".html" : "#";
    }
}
📖 Why this code?

Every annotation and method in this model maps back to a specific module — this is the capstone, so it deliberately touches multiple areas.

  • @Model(adaptables = SlingHttpServletRequest.class) — adapts from the request, not from a Resource, because we need access to the full request context including the currentPage script variable. Adapting from Resource alone would lose the script variable injection.
  • @ScriptVariable private Page currentPage — HTL sets currentPage as a script-scope variable in the page rendering context. Because the navigation component is rendered within that context, this injection works. This is the same mechanism covered in module 07's advanced section.
  • @ValueMapValue(name = "navRootPath") — reads the navRootPath property from the component's content node (set via the dialog). Combined with defaultInjectionStrategy = OPTIONAL, null is returned when the author left the field empty, which the init() method handles gracefully.
  • siteRoot.getDepth() > 3 — walking up to depth 3 targets /content/[site]/[language]. Depth is zero-indexed from the JCR root: /=0, /content=1, /content/academy-mini=2, /content/academy-mini/en=3. This is why the language root is at depth 3.
  • page.isHideInNav() — reads the hideInNav boolean property from jcr:content. Authors set this in Page Properties → Navigation → "Hide in navigation." Respecting it is the correct behaviour — never iterate pages without checking this flag.
  • page.getNavigationTitle() — reads jcr:content/navTitle. This lets authors set a shorter label for the nav without changing the page title. The fallback chain (navTitle → title → name) guarantees something is always returned.
  • No caching, no query — listChildren() reads directly from the JCR node tree using Jackrabbit's node iteration API. This is O(n) where n is the number of child pages, which is typically <20 for a site nav. It's fast enough to run on every request. If you had hundreds of nav items, you'd use the Core Components Navigation model instead.

📖 Why this code?

This template is deliberately thin — every decision lives in the model. The HTL only answers "where does it go?"

  • data-sly-use.nav="...SiteNavigationModel" — triggers request.adaptTo(SiteNavigationModel.class). Sling Models handles injection and @PostConstruct. The result is bound to nav for the rest of the template.
  • data-sly-use.clientlib="/libs/granite/sightly/templates/clientlib.html" — loads AEM's built-in clientlib HTL template. The two data-sly-call statements below it inject the CSS and JS for the academy.navigation category directly into the component's output, rather than relying on the page to include them. This makes the component self-contained — it works wherever it's dropped.
  • class="academy-nav__item ${item.active ? ...} ${item.hasChildren ? ...}" — HTL evaluates both ternary expressions independently and concatenates them. Empty strings produce no extra spaces in the output. This is the correct HTL pattern for multiple conditional classes (module 09).
  • data-sly-test="${item.hasChildren}" — completely removes the <ul class="academy-nav__dropdown"> element from the output when there are no children. This is different from CSS display:none — there is genuinely no DOM node, which benefits screen readers and avoids unnecessary markup.
  • aria-current="${item.active ? 'page' : false}" — HTL omits an attribute entirely when its value is false. So non-active links have no aria-current attribute at all, which is the correct accessibility pattern.
  • <!--/* ... */--> — HTL-style comments (module 09). Never sent to the browser. Use them for developer notes without polluting page source.

📖 Why this code?

The CSS is BEM-structured and fully self-contained — it won't leak into the rest of the page.

  • Every rule is scoped to .academy-nav — the block name. No global selectors. This means the component can be dropped onto any page (Sites page, Forms Portal, standalone page) without interfering with other CSS on the page.

4f — Clientlib: JavaScript

/apps/academy/clientlibs/navigation/js.txt (academy.ui.apps)#base=js
navigation.js
/apps/academy/clientlibs/navigation/js/navigation.js (academy.ui.apps)(function () {
  'use strict';

  var nav    = document.querySelector('.academy-nav');
  if (!nav) return;

  var toggle = nav.querySelector('[data-nav-toggle]');
  var list   = nav.querySelector('[data-nav-list]');

  // ── Mobile menu open/close ─────────────────────────────────────────────
  if (toggle && list) {
    toggle.addEventListener('click', function () {
      var isOpen = list.classList.toggle('academy-nav__list--open');
      toggle.classList.toggle('academy-nav__toggle--open', isOpen);
      toggle.setAttribute('aria-expanded', String(isOpen));
    });

    // Close when user clicks anywhere outside the nav
    document.addEventListener('click', function (e) {
      if (!nav.contains(e.target)) {
        list.classList.remove('academy-nav__list--open');
        toggle.classList.remove('academy-nav__toggle--open');
        toggle.setAttribute('aria-expanded', 'false');
      }
    });
  }

  // ── Mobile dropdown toggles (tap parent link to expand sub-items) ──────
  nav.querySelectorAll('.academy-nav__item--has-dropdown').forEach(function (item) {
    var link = item.querySelector('.academy-nav__link');
    if (!link) return;

    link.addEventListener('click', function (e) {
      // Only intercept on narrow viewports — let CSS handle desktop hover
      if (window.innerWidth > 768) return;
      e.preventDefault();
      var wasOpen = item.classList.contains('open');
      // Close all other open dropdowns
      nav.querySelectorAll('.academy-nav__item--has-dropdown.open')
         .forEach(function (el) { el.classList.remove('open'); });
      // Toggle this one
      if (!wasOpen) item.classList.add('open');
    });
  });

  // ── Keyboard navigation (arrow keys for menu items) ───────────────────
  var menuItems = Array.from(
    nav.querySelectorAll('.academy-nav__link, .academy-nav__dropdown-link')
  );
  menuItems.forEach(function (link, idx) {
    link.addEventListener('keydown', function (e) {
      var next = null;
      if (e.key === 'ArrowRight' || e.key === 'ArrowDown') {
        next = menuItems[idx + 1];
      } else if (e.key === 'ArrowLeft' || e.key === 'ArrowUp') {
        next = menuItems[idx - 1];
      } else if (e.key === 'Escape') {
        nav.querySelectorAll('.academy-nav__item--has-dropdown.open')
           .forEach(function (el) { el.classList.remove('open'); });
        if (toggle) toggle.focus();
      }
      if (next) { e.preventDefault(); next.focus(); }
    });
  });

}());
📖 Why this code?

The JavaScript follows the site's existing clientlib pattern from module 16 — an IIFE, no framework dependencies, defensive null checks.

  • IIFE ((function () { ... }())) — Immediately Invoked Function Expression. Creates a private scope so no variables leak onto window. The nav script cannot conflict with any other script on the page.
  • if (!nav) return — the first thing, always. If the component isn't on the page (e.g. on an error page or a redirect page), the script exits immediately rather than throwing errors.
  • window.innerWidth > 768 in the click handler — desktop and mobile use different interaction patterns. On desktop, CSS hover handles the dropdown. On mobile, a tap on the parent link expands the sub-items. Checking viewport width at click time (not at load time) correctly handles device rotation.
  • Keyboard navigation — arrow keys move focus between nav items, Escape closes dropdowns. This is WCAG 2.1 AA compliance for keyboard users. Without it, keyboard-only users cannot navigate the dropdown. It's included here as a baseline — production implementations should also add role="navigation" and full ARIA attributes, already present in the HTML template.

Part 5 — Wire the navigation into every page

The navigation component needs to appear on every page without authors having to add it manually. The correct pattern is to include it in the page component's header partial — it renders once per page, automatically, for the entire site.

/apps/academy/components/page/partials/header.html (academy.ui.apps)<!--/*
  header.html — included by the page body template.
  This is the persistent chrome around every page's content area.
  The navigation component is data-sly-include'd here so it appears
  on every page with no authoring required.
*/-->
<header class="site-header">
  <sly data-sly-resource="${'navigation'
                            @ resourceType='academy/components/navigation',
                              cssClassName=''}"/>
</header>
📖 Why this code?

This is the standard AEM pattern for non-authorable chrome — elements that appear on every page but aren't managed in the page editor.

  • data-sly-resource triggers a full Sling dispatch for the navigation component — complete with its own script resolution, Sling Model adaptation, and clientlib injection. This is different from data-sly-include (which only pastes another script's output): data-sly-resource goes through the complete rendering pipeline, giving the navigation its own edit overlay in author mode.
  • resourceType='academy/components/navigation' — since the <header> element has no JCR content node with a sling:resourceType, we supply the type explicitly. Sling renders the navigation component using this resource type with the current request's context.
  • In the page component hierarchy (sling:resourceSuperType="core/wcm/components/page/v3/page"), AEM automatically includes partials/header.html at the top of the <body> via Core's page template. If your page component uses a different structure, include the header partial wherever your layout template assembles the page.

📖 Why this code?

customheaderlibs.html and the body partial serve different purposes — knowing which to use prevents a common placement mistake.

  • customheaderlibs.html is rendered inside <head>. Use it for CSS clientlibs, meta tags, and preloads. Never put interactive JavaScript here that depends on document.querySelector — the DOM doesn't exist yet when <head> is parsed.
  • The body partial (partials/header.html) is rendered at the top of <body>. Use it for visible UI components like the navigation bar. The navigation JavaScript (which queries the DOM) is deferred to the bottom of the component output, after the nav HTML exists.

Part 7 — Extend the navigation: ideas for going further

extension ideas — each one maps to a module you've completedIDEA 1 — Persist nav root via Context-Aware Config (module 15)
  Instead of a dialog field per component instance, store the navigation
  root in a CA Config at /conf/academy-mini/:
    @Configuration(name = "Navigation Settings")
    public @interface NavigationConfig {
      String navRootPath() default "";
    }
  The model reads it via ConfigurationBuilder — all navigation instances
  on the site share one configuration, changed in one place.

IDEA 2 — Cache nav items in a Sling Job (module 18)
  listChildren() is fast for <20 pages, but for a site with 200+ nav items,
  schedule a Sling Job to pre-compute the nav tree and store it as a JSON
  node under /var/academy/nav-cache. The model reads from cache first,
  falls back to live computation. Invalidate the cache on page creation/deletion
  via a ResourceChangeListener (module 16).

IDEA 3 — Add search to the nav bar
  Add a <form> to the navigation.html template with a text input.
  Wire it to a path-based search servlet (module 10) at /bin/academy/search
  that queries AEM's QueryBuilder for matching pages.

IDEA 4 — Breadcrumb component
  Same SiteNavigationModel pattern, but instead of listing children,
  walk UP from currentPage to the root, building a list of ancestors.
  The breadcrumb shows the path: Home / Courses / AEM Basics.

IDEA 5 — Analytics integration (module 25-26)
  Add data-acdl attributes to each nav link:
    data-acdl-event="nav:click"
    data-acdl-label="${item.title}"
  In navigation.js, push to ACDL on click:
    window.adobeDataLayer.push({ event: "nav:click",
      eventInfo: { value: { navLabel: label, navPath: href } } });
  Tags rule: ACDL Event Listener → "nav:click" → Set Variables + s.tl().
📖 Why this code?

Each extension idea is a module review in disguise.

  • Idea 1 applies module 15 (CA Config): the nav root is content-hierarchy–aware configuration. A sub-site at /content/academy-mini/microsite/en automatically gets different config from the main site.
  • Idea 2 applies modules 16 and 18: a ResourceChangeListener invalidates the cache; a Sling Job refreshes it asynchronously without blocking page requests. This is the correct pattern for any computed value that's expensive to recalculate on every request.
  • Idea 5 applies modules 25-26 directly: adding analytics tracking to the nav connects the developer's work (pushing to ACDL) to the Analytics Engineer's Tags configuration. The nav click event is one of the most valuable interactions to track — it shows which sections users navigate to most and where they go after landing on a page.
