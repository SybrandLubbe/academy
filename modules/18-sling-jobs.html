Sling Jobs

Module 12's WeatherModel made a synchronous outbound HTTP call inside a Sling Model and flagged it as something to fix later. This is later — the Sling Jobs API is the production-correct way to do that work in the background instead.

What you'll learn

  • What a Sling Job is, and how it differs from the listeners and schedulers in module 16
  • Registering a job — immediate vs. scheduled
  • Writing a job consumer that does the actual work
  • Configuring a job queue's behavior

What a Sling Job is

A Sling Job is a unit of work, identified by a topic string and a set of properties, placed into a persistent queue and picked up by whichever component registered to handle that topic. The "persistent" part is what separates it from the scheduler in module 16: if the instance restarts mid-job, the job isn't lost — it's retried according to the queue's configuration, which makes it the right tool for anything that genuinely must complete eventually, not just "run when convenient."

Writing a job consumer

This component does the actual weather fetch — the logic module 12 ran inline, moved here so it runs off the request thread entirely:

/aem-academy/core/src/main/java/biz/netcentric/academy/jobs/WeatherRefreshJobExecutor.java (academy.core)package biz.netcentric.academy.jobs;

import org.apache.sling.api.resource.LoginException;
import org.apache.sling.api.resource.ModifiableValueMap;
import org.apache.sling.api.resource.Resource;
import org.apache.sling.api.resource.ResourceResolver;
import org.apache.sling.api.resource.ResourceResolverFactory;
import org.apache.sling.event.jobs.Job;
import org.apache.sling.event.jobs.consumer.JobExecutionContext;
import org.apache.sling.event.jobs.consumer.JobExecutionResult;
import org.apache.sling.event.jobs.consumer.JobExecutor;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Reference;

import java.util.Collections;

@Component(
        service = JobExecutor.class,
        property = "job.topics=academy/weather/refresh"
)
public class WeatherRefreshJobExecutor implements JobExecutor {

    @Reference
    private ResourceResolverFactory resourceResolverFactory;

    @Override
    public JobExecutionResult process(Job job, JobExecutionContext context) {
        String city = (String) job.getProperty("city");
        String cachePath = (String) job.getProperty("cachePath");

        try (ResourceResolver resolver = resourceResolverFactory
                .getServiceResourceResolver(Collections.singletonMap(
                        ResourceResolverFactory.SUBSERVICE, "academy-weather-writer"))) {

            // re-use the geocode/fetch logic from module 12's WeatherModel here
            double temperature = fetchTemperatureFor(city);

            Resource cacheResource = resolver.getResource(cachePath);
            if (cacheResource != null) {
                ModifiableValueMap props = cacheResource.adaptTo(ModifiableValueMap.class);
                props.put("temperature", temperature);
                resolver.commit();
            }
            return context.result().succeeded().build();

        } catch (LoginException e) {
            return context.result().message("No service resource resolver: " + e.getMessage()).failed().build();
        } catch (Exception e) {
            return context.result().message(e.getMessage()).failed().build();
        }
    }

    private double fetchTemperatureFor(String city) {
        return 0; // delegate to the geocode/fetch helpers from module 12
    }
}
📖 Why this code?

A complete Sling Job executor — the implementation that runs when a job is dequeued. Notice the security and resource management patterns.

  • implements JobExecutor — the interface with one method, process(Job job, JobExecutionContext context). AEM calls this when a job with the matching topic is pulled from the queue.
  • ResourceResolverFactory.SUBSERVICE, "academy-weather-writer" — accesses the repository using a service user, not the admin user. This is the required security pattern for background jobs — using admin credentials in production code is a security misconfiguration. The service user must be configured in ui.config with minimal required permissions.
  • context.result().succeeded() vs context.result().failed() — the return value tells the job queue whether to mark the job done or retry it (according to the queue's queue.retries config). Always return a result — letting the method end without returning causes the job to be retried indefinitely.
  • job.getProperty("city", String.class) — reads the custom properties passed when jobManager.addJob(topic, properties) was called. Job properties are persisted to the repository, so they survive an AEM restart.
Common pitfall getServiceResourceResolver(...) requires a service user mapping to be configured first (an OSGi config that grants the named subservice — academy-weather-writer here — permission to log in as a service user with appropriate ACLs). It's a separate piece of setup from the job itself, and forgetting it is the most common reason a background job fails with a login exception that looks unrelated to the actual business logic.

Registering a job: scheduled vs. immediate

Trigger an immediate job the moment something happens — for instance, right after an author saves the Weather component's dialog:

triggering an immediate job@Reference
private JobManager jobManager;

public void requestRefresh(String city, String cachePath) {
    Map<String, Object> props = new HashMap<>();
    props.put("city", city);
    props.put("cachePath", cachePath);
    jobManager.addJob("academy/weather/refresh", props);
}
📖 Why this code?

Triggering a one-off job — the "fire and forget" pattern for handing heavy work off from a synchronous request thread.

  • @Reference private JobManager jobManager — the OSGi service that manages the job queue. Inject it wherever you need to add jobs.
  • jobManager.addJob("academy/weather/refresh", props) — adds the job to the queue immediately. The first argument is the topic — a slash-separated string that must match the JobConsumer.PROPERTY_TOPICS property on your executor. Think of it as a message queue topic name.
  • The props map carries the data the executor needs. Properties must be serializable to basic types (String, int, boolean, arrays thereof) — complex objects are not supported.
  • After this line returns, the method continues immediately. The job runs asynchronously on a background thread managed by the queue — the calling thread is not blocked.

Register a scheduled job once, typically from a component's @Activate method, to have it run repeatedly without anything triggering it each time:

registering a recurring job@Activate
protected void activate() {
    Map<String, Object> props = new HashMap<>();
    props.put("city", "Lisbon");
    props.put("cachePath", "/content/academy/weather-cache/lisbon");

    jobManager.createJob("academy/weather/refresh")
            .properties(props)
            .schedule()
            .cron("0 */15 * * * ?")  // every 15 minutes
            .add();
}
📖 Why this code?

Registering a recurring scheduled job — the production-correct alternative to a synchronous call in @PostConstruct for periodic work like weather cache refresh.

  • jobManager.createJob(topic).properties(props).schedule().cron("0 */15 * * * ?").add() — creates a durable scheduled job. Unlike the Sling Scheduler (which uses in-memory Quartz), a scheduled Sling Job persists to the repository — if AEM restarts between executions, the schedule survives.
  • cron("0 */15 * * * ?") — every 15 minutes. */15 means "every N minutes." The schedule is stored with the job definition.
  • Calling this in @Activate means the schedule is registered when the component starts. The corresponding @Deactivate should call scheduler.unschedule("academy-weather-refresh") to remove it.
  • The executor processes the job asynchronously — @Activate returns immediately; the first execution happens at the next scheduled time.

With this in place, WeatherModel from module 12 could be rewritten to simply read temperature off the cache resource — no outbound HTTP call on the render path at all, and a page that loads instantly regardless of whether Open-Meteo is having a slow day.

Queue configuration

A job's queue controls how it's actually processed — how many run in parallel, what happens on failure, and whether order matters. Configure it as an OSGi factory configuration:

/aem-academy/ui.config/src/main/content/jcr_root/apps/academy/osgiconfig/config/org.apache.sling.event.jobs.QueueConfiguration~weatherqueue.cfg.json (academy.ui.config){
    "queue.name": "academy-weather-queue",
    "queue.topics": ["academy/weather/*"],
    "queue.type": "UNORDERED",
    "queue.maxparallel": 5,
    "queue.retries": 3,
    "queue.retrydelay": 2000
}
📖 Why this code?

The queue configuration file that controls how jobs on the academy/weather/* topic are processed.

  • "queue.topics": ["academy/weather/*"] — the wildcard * means this queue handles any topic starting with academy/weather/. Multiple executors with different sub-topics can share one queue configuration.
  • "queue.type": "UNORDERED" — jobs can run in parallel. Use ORDERED if later jobs must wait for earlier ones to complete (e.g. sequential pipeline steps).
  • "queue.maxparallel": 5 — up to 5 weather refresh jobs can execute simultaneously. Set this based on the external API's rate limit — hammering an API with 50 concurrent calls will get you rate-limited.
  • "queue.retries": 3 and "queue.retrydelay": 2000 — if process() returns failed(), the framework retries up to 3 times with a 2-second delay between attempts. Useful for transient network failures.

queue.type matters most: UNORDERED processes jobs in parallel with no guaranteed order (fine here — one city's refresh doesn't depend on another's), while ORDERED processes jobs on the same topic strictly one at a time, which you'd want if later jobs depend on earlier ones having finished. queue.retries and queue.retrydelay control what happens when process() returns a failed result — exactly the safety net that makes jobs more durable than the plain scheduler from module 16.

Try it Wire up the scheduled job above for two or three cities, confirm the cache resources update on their own every 15 minutes by watching their temperature property in CRXDE Lite, then rewrite WeatherModel to read from the cache instead of calling Open-Meteo directly.
