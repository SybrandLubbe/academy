Context-Aware Configurations

Module 5 covered OSGi configuration scoped by run mode — the same value for every site on an instance. Context-Aware Configuration solves a different problem: a value that differs per site on the same instance, resolved by where in the content tree you're asking from.

What you'll learn

  • What problem Context-Aware Configuration (CA Config) solves that run modes don't
  • Defining a configuration with an OSGi annotation interface
  • Reading it from a resource or request via ConfigurationBuilder
  • Unit testing code that depends on a CA Config
  • Installing and using the WCM IO Context-Aware Configuration Editor

The problem it solves

Imagine an analytics tracking ID, a social media handle, or a third-party API key that needs to be different for every site an AEM instance hosts — run-mode configuration can't help, because run mode describes the environment (author vs. publish), not the content being requested. CA Config resolves a value by walking up the content hierarchy from a given resource (typically a page) until it finds a matching configuration, usually stored under /conf and linked to a site via sling:configRef.

Defining a configuration

A configuration is just an annotation interface, similar in shape to the @ObjectClassDefinition pattern from modules 4 and 5:

/aem-academy/core/src/main/java/biz/netcentric/academy/config/WeatherConfig.java (academy.core)package biz.netcentric.academy.config;

import org.apache.sling.caconfig.annotation.Configuration;
import org.apache.sling.caconfig.annotation.Property;

@Configuration(label = "Weather Component Settings")
public @interface WeatherConfig {

    @Property(label = "Default country")
    String defaultCountry() default "Portugal";

    @Property(label = "Cache duration (minutes)")
    int cacheDurationMinutes() default 30;
}

No @Component or @Designate is needed here — CA Config's own framework discovers @Configuration-annotated interfaces automatically; there's nothing to register by hand.

Reading a configuration

Adapt a resource or request to ConfigurationBuilder, then ask it for your annotation type:

inside a Sling Modelimport org.apache.sling.caconfig.ConfigurationBuilder;
import org.apache.sling.models.annotations.injectorspecific.Self;

@Self
private ConfigurationBuilder configurationBuilder;

private String resolveDefaultCountry() {
    WeatherConfig config = configurationBuilder.as(WeatherConfig.class);
    return config.defaultCountry();
}

If module 12's WeatherModel used this instead of leaving the country blank, every site under a given /conf configuration could default to its own country without a single line of branching code in the model itself.

Context-aware resources, briefly

Under the hood, CA Config resolution walks from the current resource up through its parents, following each page's sling:configRef property to locate the relevant config tree under /conf — falling back to a global default if no site-specific value exists. You rarely need to interact with that resolution chain directly; ConfigurationBuilder handles it, which is precisely the point.

Unit testing CA Config

AemContext from module 14 has a plugin for this — enable it when building the context, then write the configuration values directly into the mock /conf tree:

/aem-academy/core/src/test/java/biz/netcentric/academy/config/WeatherConfigTest.java (excerpt) (academy.core)private final AemContext context = new AemContext(ContextPlugins.CACONFIG);

@Test
void resolvesDefaultCountryFromCaConfig() {
    context.create().resource("/conf/academy/sling:configs/biz.netcentric.academy.config.WeatherConfig",
            "defaultCountry", "Germany");
    context.create().resource("/content/academy/page", "sling:configRef", "/conf/academy");

    Resource page = context.resourceResolver().getResource("/content/academy/page");
    WeatherConfig config = page.adaptTo(ConfigurationBuilder.class).as(WeatherConfig.class);

    assertEquals("Germany", config.defaultCountry());
}

WCM IO Context-Aware Configuration Editor

Out of the box, CA Config values can only be edited as raw repository content under /conf — fine for a developer in CRXDE Lite, unworkable for the content authors and administrators who actually need to change a tracking ID. The WCM IO Context-Aware Configuration Editor is a free, open-source tool that adds a proper UI for this.

Installation

Add it as a Maven dependency in your all module's content package (or install the released package directly via Package Manager for a quick local trial), then redeploy. It ships its own UI bundle and content package — no custom code is needed on your side beyond having defined your @Configuration annotation interfaces.

Using the editor

Once installed, a "Configuration" entry appears in the AEM tools console, letting an author or administrator browse configurations by site and edit the fields your @Property labels describe — without ever opening CRXDE Lite. The form fields are generated directly from your annotation interface, so WeatherConfig above would show "Default country" and "Cache duration (minutes)" as labeled inputs automatically.

Common pitfall Forgetting that a page needs a sling:configRef (set automatically by editable templates' site root configuration, or manually for test content) pointing at a /conf path before CA Config resolution has anywhere to look. Without it, ConfigurationBuilder silently falls back to your annotation's default values — which can look identical to "it's working" until you actually need a non-default value.
