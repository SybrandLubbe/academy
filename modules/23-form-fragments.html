Authoring, Templates, Rules & Form Data Model

Module 22 mapped the landscape. This module is where you build in it. You'll walk through creating a form from scratch, understand why templates and themes are kept separate, see how fragments enforce reuse, learn every Rule Editor action type, write Custom Functions with JSDoc, and connect a form to a backend system via the Form Data Model.

What you'll learn

  • The authoring workflow — how a form goes from blank to published
  • Templates vs Themes — why the separation matters
  • Form Fragments — reuse by reference, not copy-paste, and why the publish lifecycle trips people up
  • Rule Editor — every condition type and action type, with the gotcha that breaks rules silently
  • Custom Functions — JSDoc annotations, clientlib category, and the four main use cases
  • Form Data Model — data source types, prefill binding, submit-back, and security

Creating an Adaptive Form — the authoring workflow

authoring workflow — six decisions in order
Step 1 — Navigate to the Forms console
         http://localhost:4502/aem/forms
         Forms & Documents → Create → Adaptive Form

Step 2 — Choose a template
         Pick a Core Components template (never a Foundation template for new work).
         The template determines: which fields are pre-placed, which fields authors
         can add, and which fields are locked by the template author.

Step 3 — Set form metadata
         Title       → human-readable name (appears in Forms Portal listings)
         Name        → JCR node name (URL-safe, no spaces, set it once — changing it
                        after publish breaks all inbound links)
         Theme       → the CSS client library that styles the form
         Config Container → which Cloud Services config to use
                            (ties the form to a specific FDM and Analytics property)

Step 4 — Author fields in the page editor
         Drag Core Components from the component palette.
         Set Name property on every field before writing any Rule Editor rules.
         Use panels to group related fields.

Step 5 — Configure Form Container (the root component)
         Data Model tab → bind to a Form Data Model or JSON schema
         Prefill Service → set to your DataXMLProvider OSGi service
         Submit Action  → choose built-in or your custom GuideSubmitAction
         Thank You Page → path to redirect after successful submission

Step 6 — Preview and Publish
         Preview: append ?wcmmode=disabled to the form URL to see it as end users do.
         Publish: publishes the form AND all referenced fragments to Publish.
📖 Why this code?
  • Step 3 — Name is permanent. The Name becomes the JCR node name and the URL path segment. Changing it after the form goes live requires a redirect and breaks bookmarks, deep links, and analytics tracking. Use kebab-case, no spaces, set it once.
  • Step 4 — Name before Rules. The Rule Editor references fields by their Name property, not their label. If you write a rule referencing dateOfBirth and someone later renames the field to dob, the rule breaks silently — no error, no validation, the rule just stops firing.
  • Step 5 — Config Container scopes which FDM, Analytics property, and reCAPTCHA config the form uses — same CAConfig pattern from module 15.
  • Step 6 — Preview with ?wcmmode=disabled bypasses the authoring overlay. Without it, the rule editor, submit button, and validation all behave differently than in production.

Templates vs Themes — the separation

templates and themes — what each one does
TEMPLATE
  Defines: which Core Components can be added to the form
  Defines: which panels are pre-placed and locked vs editable
  Defines: content policies controlling field configuration options
  Stored at: /conf/your-project/settings/wcm/templates/
  Created by: developer or advanced author in Template Editor

  Analogy: a printed form with some fields already filled (pre-placed,
           locked) and blank lines where authors add their own fields.

THEME
  Defines: CSS for every Core Component BEM class the form emits
  Stored at: /content/dam/formsanddocuments/themes/ (DAM)
             or deployed as a clientlib under /apps/your-project/clientlibs/
  Applied via: the Theme field on the form's Basic properties tab
  One theme can brand dozens of forms.

KEY RULE: Every form starts from a template.
          Themes are optional styling.
          Swap the theme → form looks different. Structure is unchanged.
          Restructure the template → CSS doesn't change.
📖 Why this code?
  • The template/theme split is identical to the AEM Sites pattern: editable templates in /conf, the rendering (CSS/JS) in separate clientlibs. If you've customised a Sites template, you already know this.
  • Core Components emit BEM-compliant CSS classes. The theme clientlib targets those classes — e.g. .cmp-adaptiveform-textinput__label. Because BEM classes are stable across versions (Adobe's versioning policy), your theme CSS survives Core Component upgrades.
  • Choose deliberately: editable templates (authors can modify layout) vs static templates (developers control structure in code). Most enterprise projects use editable templates with a locked initial structure and an open editable region.

Form Fragments — reuse by reference

fragment storage and reference in the JCR
STORAGE
/content/dam/formsanddocuments/
├── company-fragments/
│   ├── address-block/          ← reusable address panel (3 fields + rules)
│   ├── gdpr-consent/           ← checkbox + legal text (locked — legal owns it)
│   └── employment-details/     ← employer name, start date, job title
└── loan-application/           ← a complete form (not a fragment)

FRAGMENT REFERENCE in a consuming form (CRXDE view)
/content/dam/formsanddocuments/loan-application/jcr:content/
  guideContainer/rootPanel/personalSection/addressSection
    sling:resourceType = "core/fd/components/form/fragment/v1/fragment"
    fragmentPath       = "/content/dam/formsanddocuments/company-fragments/address-block"
                                    ↑ path reference only — NOT a copy of content

WHAT HAPPENS AT RENDER TIME
  AEM resolves fragmentPath → fetches current fragment content → renders inline.
  Update the fragment + republish → every consuming form shows the new version.

DETACHING A FRAGMENT (right-click → Detach in the editor)
  Converts the reference to a local copy.
  Future updates to the original fragment NO LONGER propagate.
📖 Why this code?
  • Fragments have their own publish lifecycle. A form referencing an unpublished fragment renders without that section in production. Publishing a form does not automatically publish its fragments — use "Activate with References" or publish fragments separately first. This is the single most common Forms deployment mistake.
  • The fragmentPath property is a plain JCR string — a path. Sling resolves it at render time. This is the same pattern as a fileReference on an image component pointing at a DAM asset. No magic — just path resolution.
  • One fragment can be bound to different data schemas in different forms — an address fragment prefills from billing address in one form and delivery address in another, by setting different FDM bindings on the container.

Rule Editor — condition → action patterns

Rule Editor — complete action reference
CONDITIONS (the WHEN clause — what triggers the rule)
  field equals value | is not equal to | is empty | is not empty
  field is valid | is not valid
  checkbox is checked | is not checked
  button is clicked
  form initialises (runs once on load)
  custom function returns [value]

ACTIONS (the THEN clause — what happens)
  Show / Hide               → panel, field, or section
  Enable / Disable          → field or button
  Validate                  → run field-level validation manually
  Set Value of              → field = literal | field | FDM property | function output
  Set Property of           → field.label | field.placeholder | dropdown.options
  Invoke a Service          → call an FDM operation (GET prefill, POST check)
  Submit / Reset            → submit or reset the form programmatically
  Navigate to               → next/previous panel in a wizard layout
  Dispatch Event            → fire a custom analytics event

COMMON PATTERNS

Pattern 1 — conditional field visibility
  WHEN maritalStatus equals "Married" THEN show spouseDetailsPanel
  WHEN maritalStatus is not equal to "Married" THEN hide spouseDetailsPanel

Pattern 2 — computed value
  WHEN annualIncome changes THEN set monthlyIncome = annualIncome / 12

Pattern 3 — disable submit until terms accepted
  WHEN agreeToTerms is not checked THEN disable submitButton

Pattern 4 — cascade dropdown (country → province)
  WHEN country changes
  THEN invoke FDM service "getProvincesForCountry" with input = country
  THEN set options of provinceDropdown = service output

IMPORTANT: switching from code editor → visual editor CLEARS custom code.
           Write complex logic in Custom Functions (next section), not inline.
📖 Why this code?
  • Rules run in the browser. No server round-trip — show/hide feels instant. But this also means rules are not a security boundary. Always validate server-side in your submit action. Never trust browser-side validation alone.
  • Pattern 4 (cascade dropdown) via FDM service is the correct integration pattern. Hardcoding all province/country combinations in JavaScript is fragile and hard to maintain. Let the FDM call a data service.
  • Never write logic in the inline Code Editor if you can avoid it. Code entered inline is stored as a string property on the node — no version control, no unit testing, no IDE support. Move it to a Custom Function in a clientlib.
  • You can restrict the Code Editor mode to a specific AEM user group in OSGi config. Do this in production — business analysts should use visual mode only.

Custom Functions — JSDoc, clientlibs, and the four use cases

Custom Function clientlib setup
/apps/your-project/clientlibs/forms-custom-functions/
  jcr:primaryType = cq:ClientLibraryFolder
  categories      = ["fd.customfunctions"]  ← required; this is how AEM discovers them
  allowProxy      = true                    ← required; serves JS on publish tier

  js.txt          ← lists JS files to include
    #base=js
    validators.js

  js/validators.js ← your actual functions
📖 Why this code?
  • The category "fd.customfunctions" is the discovery key. AEM Forms scans all active clientlibs with this category and exposes their functions in the Rule Editor's "Custom Functions" palette. A different category means the Rule Editor ignores the file entirely — this is the most common reason a Custom Function doesn't appear.
  • allowProxy = true exposes the clientlib at /etc.clientlibs/ on the publish tier. Without it, the JS isn't served to end users and the function silently fails at runtime.
Custom Functions — four use cases with JSDoc annotations
// USE CASE 1: Data Validation
/**
 * Validates a South African 13-digit ID number (Luhn checksum).
 * @name validateSAId
 * @param {string} idNumber - The 13-digit SA ID to validate
 * @return {boolean}        - true = valid; string = error message to display
 */
function validateSAId(idNumber) {
    if (!idNumber || idNumber.length !== 13 || isNaN(idNumber)) {
        return "SA ID must be exactly 13 digits.";
    }
    var digits = idNumber.split("").map(Number);
    var sum = digits.reduce(function(acc, d, i) {
        return i % 2 === 0 ? acc + d : acc + (d * 2 > 9 ? d * 2 - 9 : d * 2);
    }, 0);
    return (sum % 10 === 0) ? true : "Invalid SA ID — checksum failed.";
}

// USE CASE 2: Dynamic Calculation
/**
 * Calculates age in full years from a date-of-birth string.
 * @name calculateAge
 * @param {string} dob - Date of birth in YYYY-MM-DD format
 * @return {number}    - Age in years
 */
function calculateAge(dob) {
    var birth = new Date(dob), now = new Date();
    var age = now.getFullYear() - birth.getFullYear();
    var m = now.getMonth() - birth.getMonth();
    if (m < 0 || (m === 0 && now.getDate() < birth.getDate())) { age--; }
    return age;
}

// USE CASE 3: Data Transformation
/**
 * Formats a raw bank account number as XX-XXXXXX-XXX (SA format).
 * @name formatAccountNumber
 * @param {string} raw - Unformatted account number digits
 * @return {string}    - Formatted string or original if invalid
 */
function formatAccountNumber(raw) {
    var clean = (raw || "").replace(/\D/g, "");
    if (clean.length !== 11) { return raw; }
    return clean.slice(0,2) + "-" + clean.slice(2,8) + "-" + clean.slice(8);
}

// USE CASE 4: External Integration
/**
 * Looks up company name via a proxied Sling servlet (avoids CORS).
 * @name lookupCompanyName
 * @param {string} regNumber - Company registration number
 * @return {string}          - Company name or empty string
 * @async
 */
async function lookupCompanyName(regNumber) {
    try {
        var resp = await fetch("/bin/company-lookup?reg=" + encodeURIComponent(regNumber));
        if (!resp.ok) { return ""; }
        return (await resp.json()).companyName || "";
    } catch (e) { return ""; }
}
📖 Why this code?
  • JSDoc annotations are mandatory. The Rule Editor discovers functions by scanning for /** */ comment blocks. A function with no JSDoc is invisible. At minimum you need an empty /** */ block — always add @name, @param, and @return so authors know what to pass in.
  • Return conventions for validators: return true for valid, return a string error message for invalid. AEM Forms displays the string as the field's validation error. Never throw an exception — the Rule Editor swallows it silently.
  • Use @private on helper functions to exclude them from the Rule Editor palette while still making them available as internal helpers called by your public functions.
  • Use Case 4 proxies through a Sling servlet to avoid CORS and to keep the external API endpoint hidden from the browser. The servlet is a standard @SlingServlet from module 10.

Form Data Model — connecting to enterprise data

FDM data source types and when to use each
Data Source Type        When to use
─────────────────────── ──────────────────────────────────────────────────
RESTful web service     Any modern REST API with a Swagger 2.0 / OpenAPI 3
                        spec. Most common for new projects.

SOAP web service        Legacy systems with a WSDL. Common in banking and
                        insurance.

OData service           Microsoft Dynamics, SharePoint, SAP.

JDBC database           Direct DB connection. Use only when no REST layer
                        exists. Tightly couples AEM to the DB schema.

AEM User Profile        Logged-in user's profile properties. Good for
                        prefilling name, email, preferred language.

FDM setup — five steps from data source to bound form
Step 1 — Configure the data source
         Tools → Cloud Services → Data Sources → Create
         Type: RESTful Web Service
         Swagger file: upload to DAM first, then select path
         Authentication: Basic / OAuth2 / API Key / None
         Base URL: https://api.example.com/v1

Step 2 — Create the Form Data Model
         AEM Forms → Data Integrations → Create → Form Data Model
         Select the data source from Step 1
         Expose operations:
           Read  → GET /customers/{customerId}  → "Read Customer"
           Write → POST /applications           → "Submit Application"

Step 3 — Test the FDM operations
         Use the "Test Service" button in the FDM editor.
         Verify data shapes before binding to a form.
         Catch a broken Swagger spec here, not after form build.

Step 4 — Bind the FDM to a form
         Form Container → Data Model tab → Select Form Data Model

Step 5 — Bind individual fields
         Open each field's dialog → Bind Reference tab
         Drag from the FDM object tree or type the path:
           applicant.firstName → binds text input to firstName property
         Set Read Service on Form Container for prefill.
         Set Write Service in the submit action configuration.
📖 Why this code?
  • REST over JDBC. JDBC creates a direct schema dependency — a column rename in the DB breaks the FDM silently at runtime. A REST API absorbs that change in the service layer. JDBC also requires firewall rules allowing AEM to connect directly to the database, increasing the attack surface.
  • Test before binding (Step 3). The FDM editor has a "Test Service" button that calls the real API from within AEM. Use it. Catching a broken Swagger spec at Step 3 is far cheaper than debugging it after the form is fully built.
  • Prefill binding paths are case-sensitive. A field bound to applicant.firstName must exactly match the JSON property path in the API response. A case mismatch silently leaves the field blank.
  • Use run-mode config for URLs. The data source Base URL should differ between Dev, Stage, and Prod. Store it in run-mode OSGi config folders — same pattern from module 5. Never hardcode the production API URL.
  • Least privilege for credentials. Configure each data source with the minimum permissions: read-only account for prefill sources, write account only for submit-back operations. Credentials are encrypted in Tools → Cloud Services → Data Sources.
Try it Write a Custom Function called validateEmail that returns true if the string contains a single @ with characters before and after, and returns a string error message otherwise. Package it in a clientlib with category "fd.customfunctions". Deploy to AEM and open the Rule Editor on a text input — verify your function appears in the "Custom Functions" palette. Wire it: WHEN email field changes THEN validate using validateEmail. Preview with ?wcmmode=disabled and confirm the error message appears for an invalid email.
