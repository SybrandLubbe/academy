Authoring, Templates, Rules & Form Data Model

What you'll learn

  • The authoring workflow — how a form goes from blank to published
  • Templates vs Themes — why the separation matters and how it maps to Sites concepts
  • Form Fragments — reuse by reference, not copy-paste, and why the publish lifecycle trips people up
  • Rule Editor — every condition type and action type, with the gotcha that breaks rules silently
  • Custom Functions — JSDoc annotations, clientlib category, and the four main use cases
  • Form Data Model — data source types, prefill binding, submit-back, and security

Creating an Adaptive Form — the authoring workflow

Adaptive Forms are built in the AEM Forms authoring console, not in the Sites page editor. The workflow is similar to creating a Sites page but with Forms-specific configuration.

authoring workflow — six decisions in order

Step 1 — Navigate to the Forms console
         http://localhost:4502/aem/forms
         Forms & Documents → Create → Adaptive Form

Step 2 — Choose a template
         Pick a Core Components template (never a Foundation template for new work).
         The template determines: which fields are pre-placed, which fields authors
         can add, and which fields are locked by the template author.

Step 3 — Set form metadata
         Title       → human-readable name (appears in Forms Portal listings)
         Name        → JCR node name (URL-safe, no spaces, set it once — changing it
                        after publish breaks all inbound links)
         Theme       → the CSS client library that styles the form
         Config Container → which Cloud Services config to use
                            (ties the form to a specific FDM and Analytics property)

Step 4 — Author fields in the page editor
         Drag Core Components from the component palette.
         Set Name property on every field before writing any Rule Editor rules.
         Use panels to group related fields.

Step 5 — Configure Form Container (the root component)
         Data Model tab → bind to a Form Data Model or JSON schema
         Prefill Service → set to your DataXMLProvider OSGi service
         Submit Action  → choose built-in or your custom GuideSubmitAction
         Thank You Page → path to redirect after successful submission

Step 6 — Preview and Publish
         Preview: append ?wcmmode=disabled to the form URL to see it as end users do.
         Publish: publishes the form AND all referenced fragments to Publish.
📖 Why this code?
  • Step 3 — Name is permanent. The Name becomes the JCR node name and the URL path segment. Changing it after the form goes live requires a redirect and breaks bookmarks, deep links, and analytics tracking. Set it thoughtfully the first time.
  • Step 4 — Name before Rules. The Rule Editor references fields by their Name property, not their label. If you write a rule referencing dateOfBirth and someone later renames the field to dob, the rule breaks silently — no error, no validation, the rule just stops firing. Always name fields first.
  • Step 5 — Config Container. This is an AEM Cloud Service config (the same CAConfig pattern from module 15). It scopes which FDM, Analytics property, and reCAPTCHA config the form uses. One environment can have multiple config containers pointing at different environments' APIs.
  • Step 6 — Preview with ?wcmmode=disabled bypasses the authoring overlay. Without it, the rule editor, submit button, and validation all behave differently than in production.

Templates vs Themes — the separation

AEM Forms separates structure from styling. This is the same principle as Sites page templates and editable templates, applied to forms.

templates and themes — what each one does

TEMPLATE
  Defines: which Core Components can be added to the form
  Defines: which panels are pre-placed and locked vs editable
  Defines: content policies controlling field configuration options
  Stored at: /conf/your-project/settings/wcm/templates/
  Created by: developer or advanced author in Template Editor

  Analogy: a printed form with some fields already filled (pre-placed, locked)
           and blank lines where authors add their own fields (editable area)

THEME
  Defines: CSS for every Core Component BEM class the form emits
  Stored at: /content/dam/formsanddocuments/themes/ (DAM, not /conf)
             or deployed as a clientlib under /apps/your-project/clientlibs/
  Applied via: the Theme field on the form's Basic properties tab
  One theme can brand dozens of forms. Changing the theme changes all of them.

  Analogy: a stylesheet. Swap the stylesheet, the form looks different.
           The structure (which fields exist) doesn't change.

KEY RULE: Every form starts from a template. Themes are optional styling.
          You can restyle without touching the form. You can restructure the
          template without changing CSS.
📖 Why this code?
  • The template/theme split is identical to the AEM Sites pattern: editable templates live in /conf, the rendering (CSS/JS) is separate clientlibs. If you've customised a Sites template, you already know this.
  • Core Components emit BEM-compliant CSS classes. The theme clientlib targets those classes. Example: .cmp-adaptiveform-textinput__label. Because BEM classes are stable across versions (Adobe's versioning policy), your theme CSS survives Core Component upgrades.
  • Choose deliberately between editable templates (authors can modify layout) and static templates (developers control structure in code). Most enterprise projects use editable templates with locked initial structure and an open editable region for forms practitioners.
  • Themes are transported as packages between AEM instances — same as any JCR content. Move a theme from Dev to Stage to Prod using a content package.

Form Fragments — reuse by reference, not copy-paste

A fragment is a saved, reusable subset of a form — address panels, consent blocks, employment details — stored in the DAM and referenced, not copied, into other forms.

fragment storage and reference in the JCR

STORAGE
/content/dam/formsanddocuments/
├── company-fragments/
│   ├── address-block/          ← reusable address panel (3 fields + validation rules)
│   │   └── jcr:content/guideContainer/...
│   ├── gdpr-consent/           ← checkbox + legal text, locked — legal cannot change it
│   └── employment-details/     ← panel with employer name, start date, job title
└── loan-application/           ← a complete form (not a fragment)

FRAGMENT REFERENCE in a consuming form (CRXDE view)
/content/dam/formsanddocuments/loan-application/jcr:content/
  guideContainer/rootPanel/personalSection/addressSection
    jcr:primaryType   = "nt:unstructured"
    sling:resourceType= "core/fd/components/form/fragment/v1/fragment"
    fragmentPath      = "/content/dam/formsanddocuments/company-fragments/address-block"
                                    ↑ path reference only — NOT a copy of content

WHAT HAPPENS AT RENDER TIME
  AEM resolves fragmentPath → fetches current fragment content → renders inline.
  Update the fragment + republish → every consuming form shows the new version.

DETACHING A FRAGMENT (right-click → Detach in the editor)
  Converts the reference to a local copy.
  Future updates to the original fragment NO LONGER propagate.
  Use when you need a one-off variant — but prefer parameterisation over detaching.
📖 Why this code?
  • Fragments have their own publish lifecycle. A form referencing an unpublished fragment renders without that section in production. The publish step for a form publishes the form node — you must separately publish fragments, or use the "Include Referenced Content" option on publication. This is the single most common Forms deployment mistake.
  • The fragmentPath property is a plain JCR string — a path. At render time, Sling resolves it. This is the same pattern as a fileReference on an image component pointing at a DAM asset. No magic — just path resolution.
  • One fragment can be bound to different data schemas when included in different forms — an address fragment can prefill from a billing address in one form and a delivery address in another, by setting different FDM bindings on the container.
  • Fragments enable collaborative authoring: a legal team owns the consent fragment (locked), a UX team owns the address block, and individual form teams can compose without duplicating. This is the "change once, reflect everywhere" principle from module 12's component overlay concept, applied to form content.

Rule Editor — condition → action patterns

The Rule Editor is the authoring tool for form behaviour. It generates JavaScript but authors never see the code. Developers step in only for Custom Functions (next section).

Rule Editor — complete condition and action reference

CONDITIONS (the WHEN clause — what triggers the rule)
  field equals value        → "maritalStatus" equals "Married"
  field is not equal to     → "country" is not equal to "ZA"
  field is empty / not empty
  field is valid / not valid
  checkbox is checked / not checked
  button is clicked
  form initialises (runs once on load)
  custom function returns   → validateSAId(idNumber) returns true

ACTIONS (the THEN clause — what happens)
  Show / Hide               → panel, field, or section
  Enable / Disable          → field or button
  Validate                  → run field-level validation manually
  Set Value of              → field.value = literal | field value | FDM property | custom function output
  Set Property of           → field.label | field.placeholder | dropdown.options
  Invoke a Service          → call an FDM operation (GET for prefill, POST for check)
  Submit / Reset            → submit or reset the form programmatically
  Navigate to               → next/previous panel in a wizard layout
  Dispatch Event            → fire a custom analytics event

COMMON PATTERNS

Pattern 1 — conditional field visibility
  WHEN maritalStatus equals "Married" THEN show spouseDetailsPanel
  WHEN maritalStatus is not equal to "Married" THEN hide spouseDetailsPanel

Pattern 2 — computed field value
  WHEN annualIncome changes THEN set monthlyIncome = annualIncome / 12

Pattern 3 — disable submit until terms accepted
  WHEN agreeToTerms is not checked THEN disable submitButton

Pattern 4 — cascade dropdown (country → province)
  WHEN country changes
  THEN invoke FDM service "getProvincesForCountry" with input = country
  THEN set options of provinceDropdown = service output

Pattern 5 — cross-field validation
  WHEN dateOfBirth changes THEN set age = calculateAge(dateOfBirth)
  WHEN age changes THEN if age < 18 THEN show error on dateOfBirth field

IMPORTANT: switching from code editor → visual editor CLEARS custom code.
           Write code in Custom Functions (next section), not inline.
📖 Why this code?
  • Rules run in the browser. No server round-trip. This is why show/hide feels instant. But it also means rules are not a security boundary — always validate server-side in your submit action. Never trust browser-side validation alone.
  • The 'this' operator makes a rule portable. Writing WHEN this changes instead of WHEN specificFieldName changes means the rule survives a field rename. Use it wherever the rule is on the same component it references.
  • Pattern 4 — cascade dropdown via FDM service is the correct integration pattern for dependent dropdowns. The alternative (hardcoding all province/country combinations in JavaScript) is fragile and hard to maintain. Let the FDM call a data service.
  • Never write logic in the inline Code Editor if you can avoid it. Code entered inline is stored as a string property on the node — no version control, no unit testing, no IDE support. Move it to a Custom Function in a clientlib (see next section).
  • The Rule Editor is available to all authors by default. You can restrict the Code Editor mode to a specific AEM user group in OSGi config — do this in production. Business analysts should use visual mode; only developers should have code mode access.

Custom Functions — JSDoc, clientlibs, and the four use cases

Custom Functions let you extend the Rule Editor with JavaScript functions authors can call by name. They are packaged as AEM clientlibs and discovered automatically — no registration step.

Custom Function structure — clientlib setup

/apps/your-project/clientlibs/forms-custom-functions/
  jcr:primaryType   = cq:ClientLibraryFolder
  categories        = ["fd.customfunctions"]  ← required; this is how AEM discovers them
  allowProxy        = true

  js.txt            ← lists JS files to include
    #base=js
    validators.js
    calculators.js
    integrations.js

  js/validators.js  ← your actual functions (see below)
📖 Why this code?
  • The category "fd.customfunctions" is the discovery key. AEM Forms scans all active clientlibs with this category and exposes their functions in the Rule Editor's "Custom Functions" palette. A different category means the Rule Editor ignores the file entirely — this is the most common reason a Custom Function doesn't appear.
  • allowProxy = true exposes the clientlib at /etc.clientlibs/ on the publish tier. Without it, the JS isn't served to end users and the function silently fails at runtime.
Custom Functions — four use cases with JSDoc annotations

// ─────────────────────────────────────────────────────────────────
// USE CASE 1: Data Validation
// ─────────────────────────────────────────────────────────────────
/**
 * Validates a South African 13-digit ID number using Luhn checksum.
 * @name validateSAId
 * @param {string} idNumber - The 13-digit SA ID to validate
 * @return {boolean}        - true = valid; string = error message to display
 */
function validateSAId(idNumber) {
    if (!idNumber || idNumber.length !== 13 || isNaN(idNumber)) {
        return "SA ID must be exactly 13 digits.";
    }
    var digits = idNumber.split("").map(Number);
    var sum = digits.reduce(function(acc, d, i) {
        return i % 2 === 0 ? acc + d : acc + (d * 2 > 9 ? d * 2 - 9 : d * 2);
    }, 0);
    return (sum % 10 === 0) ? true : "Invalid SA ID — checksum failed.";
}

// ─────────────────────────────────────────────────────────────────
// USE CASE 2: Dynamic Calculation
// ─────────────────────────────────────────────────────────────────
/**
 * Calculates age in full years from a date-of-birth string.
 * @name calculateAge
 * @param {string} dob - Date of birth in YYYY-MM-DD format
 * @return {number}    - Age in years
 */
function calculateAge(dob) {
    var birth = new Date(dob);
    var now   = new Date();
    var age   = now.getFullYear() - birth.getFullYear();
    var m     = now.getMonth() - birth.getMonth();
    if (m < 0 || (m === 0 && now.getDate() < birth.getDate())) {
        age--;
    }
    return age;
}

// ─────────────────────────────────────────────────────────────────
// USE CASE 3: Data Transformation / Formatting
// ─────────────────────────────────────────────────────────────────
/**
 * Formats a raw bank account number as XX-XXXXXX-XXX (SA format).
 * @name formatAccountNumber
 * @param {string} raw - Unformatted account number digits
 * @return {string}    - Formatted string or original if invalid
 */
function formatAccountNumber(raw) {
    var clean = (raw || "").replace(/\D/g, "");
    if (clean.length !== 11) { return raw; }
    return clean.slice(0,2) + "-" + clean.slice(2,8) + "-" + clean.slice(8);
}

// ─────────────────────────────────────────────────────────────────
// USE CASE 4: External Integration (call REST API from browser)
// ─────────────────────────────────────────────────────────────────
/**
 * Looks up a company name for a given registration number via the
 * company-lookup Sling servlet (proxied to avoid CORS).
 * @name lookupCompanyName
 * @param {string} regNumber - Company registration number
 * @return {string}          - Company name or empty string
 * @async
 */
async function lookupCompanyName(regNumber) {
    try {
        var resp = await fetch("/bin/company-lookup?regNumber=" + encodeURIComponent(regNumber));
        if (!resp.ok) { return ""; }
        var data = await resp.json();
        return data.companyName || "";
    } catch (e) {
        return "";
    }
}
📖 Why this code?
  • JSDoc annotations are mandatory. The Rule Editor discovers functions by scanning for /** */ comment blocks. A function with no JSDoc is invisible in the Rule Editor. At minimum you need an empty /** */ block — but always add @name, @param, and @return so authors know what to pass in.
  • Return conventions for validators: return true for valid; return a string error message for invalid. AEM Forms displays the string as the field's validation error. Never throw an exception — the Rule Editor will swallow it silently.
  • Use @private on helper functions you don't want authors to see. Private functions are excluded from the Rule Editor palette but still available as internal helpers called by your public functions.
  • Use @memberof to namespace your functions: @memberof YourCompany groups them in the Rule Editor and prevents name collisions with other teams' functions. Essential on projects with multiple development teams.
  • Use Case 4 (external integration) proxies through a Sling servlet to avoid CORS and to keep the external API endpoint hidden from the browser. The servlet is a standard @SlingServlet — the same pattern from module 10.
  • Synchronous over async where possible. Adobe's guidance is to prefer synchronous operations in Rule Editor functions because async functions inside the visual Rule Editor can behave unexpectedly when chained. Use async only when absolutely necessary (external call), and handle errors defensively.

Form Data Model — connecting to enterprise data

The Form Data Model (FDM) is a DAO/ORM-like abstraction layer. It describes external data in AEM's own terms so forms never call APIs directly.

FDM data source types and when to use each

Data Source Type        When to use it
─────────────────────── ──────────────────────────────────────────────────
RESTful web service     Any modern REST API. Requires Swagger 2.0 or
                        OpenAPI 3.0 spec. Most common for new projects.

SOAP web service        Legacy systems with a WSDL. Still common in
                        banking and insurance. Painful but supported.

OData service           Microsoft Dynamics, SharePoint, SAP. AEM handles
                        the OData protocol natively.

JDBC database           Direct DB connection — MySQL, PostgreSQL, Oracle.
                        Use only when no REST layer exists. Tightly couples
                        AEM to the DB schema — avoid if REST is available.

AEM User Profile        Logged-in user's profile properties.
                        Good for pre-filling name, email, preferred language.
                        Requires authenticated session — not for anonymous forms.
📖 Why this code?
  • REST first. If a JDBC database and a REST API both expose the same data, always use the REST API. JDBC creates a direct schema dependency — a column rename in the database breaks the FDM silently. A REST API absorbs that change in the service layer.
  • Data source credentials are stored in Tools → Cloud Services → Data Sources as encrypted OSGi configurations. Apply least privilege: configure each data source with a read-only account where possible, and a write account only for submit-back operations.
FDM setup — five steps from data source to bound form

Step 1 — Configure the data source
         Tools → Cloud Services → Data Sources → Create
         Type: RESTful Web Service
         Swagger file: upload to DAM first, then select path
         Authentication: Basic / OAuth2 / API Key / None (per environment)
         Base URL: https://api.example.com/v1

Step 2 — Create the Form Data Model
         AEM Forms → Data Integrations → Create → Form Data Model
         Select data source created in Step 1
         Expose operations:
           Read  → GET /customers/{customerId}  = "Read Customer"
           Write → POST /applications           = "Submit Application"

Step 3 — Test the FDM operations in the FDM editor
         Use the "Test Service" button to call the API from within AEM.
         Verify data shapes before binding to a form.

Step 4 — Bind the FDM to a form
         Form Container → Data Model tab → Select Form Data Model → pick your FDM

Step 5 — Bind individual fields
         Open each field's dialog → Bind Reference tab
         Drag and drop from the FDM object tree, or type the path:
           applicant.firstName → binds text input to the firstName property
         Set Read Service on the Form Container for prefill.
         Set Write Service in the submit action configuration.
📖 Why this code?
  • Step 2 — Build the model first, bind fields later. The FDM is the contract between the form and the data source. Design it to match the data your form actually needs, not the full API surface. Expose only the operations required.
  • Step 3 — Test before binding. The FDM editor has a "Test Service" button that calls the real API from within AEM. Use it. Catching a broken Swagger spec or wrong authentication at Step 3 is far cheaper than debugging it after the form is fully built.
  • Prefill XML format. When you use the FDM Prefill Service, AEM calls your Read operation, maps the response to the bound fields, and renders the form pre-populated. The field binding path (applicant.firstName) must exactly match the JSON property path in the API response. A mismatch silently leaves the field blank.
  • Use run-mode config for URLs. The data source Base URL should differ between Dev, Stage, and Prod environments. Store it in run-mode OSGi config folders (config.dev, config.stage, config.prod) — the same pattern from module 5. Never hardcode the production API URL in a config stored on the author instance.
  • FDM vs custom prefill service. The out-of-the-box FDM Prefill Service covers most standard cases. Write a custom DataXMLProvider OSGi service only when you need logic that the FDM can't express — for example, combining data from three different APIs before prefilling.
Try it — Write a Custom Function called validateEmail that returns true if the string contains a single @ symbol with characters before and after, and returns a string error message otherwise. Package it in a clientlib with category "fd.customfunctions". Deploy to AEM and open the Rule Editor on a text input field — verify your function appears in the "Custom Functions" palette. Then wire it: WHEN email field changes THEN validate using validateEmail. Preview the form and confirm the error message appears when you enter an invalid email.
