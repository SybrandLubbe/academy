Form Fragments & Sample Code

Form Fragments are reusable form sections — an address block, a GDPR consent panel, an IBAN field group — defined once and included in any number of forms. Update the fragment and every form that references it updates automatically. This module also walks through a complete annotated Adaptive Form so all the pieces make sense together.

What you'll learn

  • What fragments are, where they live, and why they're better than copy-paste
  • How a fragment reference works in the JCR, and what "detaching" means
  • JSON schema binding — tying fields to a typed data contract
  • A complete annotated sample form showing how components connect
  • How the prefill service pre-populates form data on load

What is a form fragment?

A form fragment is a saved, reusable subset of a form — panels, fields, and their rules — stored in the DAM under /content/dam/formsanddocuments. The critical difference from copy-paste is inheritance: including a fragment in a form creates a reference, not a copy. Add a field to the fragment, republish it, and every form that references it shows the new field automatically.

fragment storage in the repository/content/dam/formsanddocuments/
├── academy-fragments/
│   ├── address-block/          ← reusable address panel
│   │   └── jcr:content/guideContainer/... ← the actual form fields
│   └── gdpr-consent/           ← GDPR checkbox + legal text panel
│       └── jcr:content/...
└── loan-application/           ← a complete form (not a fragment)
    └── jcr:content/...
📖 Why this code?

Fragments live under /content/dam/formsanddocuments because AEM Forms uses the DAM (Digital Asset Manager) as its storage layer for form assets.

  • Fragments have their own publish lifecycle. A form referencing an unpublished fragment renders without that section in production — authors often forget this step.
  • Fragments are independently versioned, so you can roll back to a previous version if a change breaks consuming forms.

Fragment reference in the JCR

what a fragment reference looks like in CRXDE Lite/content/dam/formsanddocuments/loan-application/jcr:content/
  guideContainer/rootPanel/addressSection
    jcr:primaryType = "nt:unstructured"
    sling:resourceType = "core/fd/components/form/fragment/v1/fragment"
    fragmentPath = "/content/dam/formsanddocuments/academy-fragments/address-block"
                              ↑ path reference only — NOT a copy of the content
📖 Why this code?

The fragmentPath property is the entire relationship — a path reference, not inline content.

  • At render time, AEM resolves fragmentPath, fetches the fragment's current content, and renders it inline. This is why updates propagate automatically.
  • If you detach a fragment (right-click → Detach Fragment in the editor), AEM converts the reference to a local copy. From that point it's independent — it receives no future fragment updates, but you can customise it freely.

JSON schema — a typed data contract for your form

sample JSON schema for a loan application{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "LoanApplication",
  "type": "object",
  "properties": {
    "applicant": {
      "type": "object",
      "properties": {
        "firstName":   { "type": "string", "maxLength": 50 },
        "lastName":    { "type": "string", "maxLength": 50 },
        "dateOfBirth": { "type": "string", "format": "date" },
        "email":       { "type": "string", "format": "email" }
      },
      "required": ["firstName", "lastName", "email"]
    },
    "loanAmount":  { "type": "number", "minimum": 1000, "maximum": 500000 },
    "loanPurpose": {
      "type": "string",
      "enum": ["HomePurchase", "CarLoan", "PersonalLoan", "BusinessLoan"]
    }
  },
  "required": ["applicant", "loanAmount"]
}
📖 Why this code?

JSON schema gives your form a typed, validated data contract. The submitted JSON will always match this shape when schema validation is enabled.

  • "format": "email" — AEM Forms generates client-side email format validation automatically from this property. No separate validation rule needed.
  • "required": [...] — fields bound to required properties show an asterisk and trigger a submit-time error when empty.
  • "enum": [...] — a dropdown bound to loanPurpose automatically restricts its options to these four values.
  • The schema is stored in the DAM and referenced from the Form Container's Data Model configuration.

  │
  ├── .../rootPanel/applicantPanel     ← panel grouping applicant fields
  │     sling:resourceType = "core/fd/components/form/panel/v1/panel"
  │     name  = "applicantPanel"
  │     title = "About You"
  │
  ├── .../applicantPanel/firstName     ← text input field
  │     sling:resourceType = "core/fd/components/form/textinput/v2/textinput"
  │     name       = "firstName"
  │     label.value= "First Name"
  │     dataRef    = "applicant.firstName"  ← bound to JSON schema path
  │     required   = true
  │
  └── .../gdprPanel                    ← fragment reference
        sling:resourceType = "core/fd/components/form/fragment/v1/fragment"
        fragmentPath = "/content/dam/formsanddocuments/academy-fragments/gdpr-consent"
📖 Why this code?

This structure maps directly to what you author visually — every drag-and-drop in the page editor creates a node in this tree.

  • dataRef = "applicant.firstName" — binds this field to the firstName property inside the applicant object in the JSON schema. The submitted JSON will have {"applicant": {"firstName": "..."}}.
  • prefillService — references a Java class by fully-qualified name. AEM calls this when the form loads, before rendering, to pre-populate fields.

Prefill service — pre-populating form data

/aem-academy/core/src/main/java/biz/netcentric/academy/forms/LoanPrefillService.java (academy.core)package biz.netcentric.academy.forms;

import com.adobe.forms.common.service.DataXMLOptions;
import com.adobe.forms.common.service.DataXMLProvider;
import com.adobe.forms.common.service.FormsException;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Reference;
import java.io.InputStream;
import java.io.ByteArrayInputStream;
import java.nio.charset.StandardCharsets;

@Component(service = DataXMLProvider.class,
           immediate = true)
public class LoanPrefillService implements DataXMLProvider {

    @Reference
    private CustomerService customerService;

    @Override
    public String getServiceName() {
        return "LoanPrefillService";  // matches prefillService property on form
    }

    @Override
    public String getServiceDescription() {
        return "Loan Application Prefill from CRM";  // label in Form Container dialog
    }

    @Override
    public InputStream getDataXMLForDataRef(DataXMLOptions options)
            throws FormsException {
        String customerId = options.getAdaptiveForm().getValueOf("customerId");
        CustomerData data = customerService.lookup(customerId);
        String xml = "<data><applicant>"
            + "<firstName>" + data.getFirstName() + "</firstName>"
            + "<email>" + data.getEmail() + "</email>"
            + "</applicant></data>";
        return new ByteArrayInputStream(xml.getBytes(StandardCharsets.UTF_8));
    }
}
📖 Why this code?

A prefill service is a standard OSGi component — everything from module 4 applies. The Forms-specific part is implementing DataXMLProvider.

  • @Component(service = DataXMLProvider.class, immediate = true) — registers in the registry under DataXMLProvider. AEM Forms discovers all registered implementations and lists them in the Form Container's dialog by their getServiceDescription() label.
  • immediate = true — needed so the service registers before the first form renders. Without it, the service may not appear in the dialog dropdown immediately after deploy.
  • The return value is an XML InputStream matching the form's schema. AEM maps values to fields automatically.
