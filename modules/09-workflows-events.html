Workflows & Event Handling

Sometimes a single request/response isn't enough — a content change needs to trigger something else, either with a human in the loop or entirely on its own. AEM gives you three different tools for that, and picking the right one matters.

What you'll learn

  • The difference between a workflow, an event listener, and a scheduled job
  • Writing a custom workflow process step
  • Reacting to repository changes with ResourceChangeListener
  • Running code on a timer with the Sling Scheduler
  • Why long-running work shouldn't run inline inside a listener

Three different automation tools

A workflow suits a human-in-the-loop or multi-step process with visible state — "Request for Activation" is the classic example, modeled visually, able to pause for approval. An event listener reacts immediately and silently to a repository change, with no visible state at all — auto-tagging a page the moment it's created, for instance. A scheduled job runs on a timer, independent of any specific content change — a nightly report being the obvious case.

Mental model Ask: does a person need to see and act on this step? Use a workflow. Should it just happen automatically when something changes? Use a listener. Does it need to run on a clock rather than a trigger? Use a scheduler.

A custom workflow step

A workflow step is a plain OSGi component implementing WorkflowProcess, registered with a label that shows up when authors build a workflow model in the UI:

AcademyTaggingStep.javapackage biz.netcentric.academy._09;

import com.adobe.granite.workflow.WorkflowException;
import com.adobe.granite.workflow.WorkflowSession;
import com.adobe.granite.workflow.exec.WorkItem;
import com.adobe.granite.workflow.exec.WorkflowProcess;
import com.adobe.granite.workflow.metadata.MetaDataMap;
import org.osgi.service.component.annotations.Component;

@Component(
        service = WorkflowProcess.class,
        property = "process.label=Academy: Add Review Tag"
)
public class AcademyTaggingStep implements WorkflowProcess {

    @Override
    public void execute(WorkItem workItem, WorkflowSession workflowSession, MetaDataMap metaDataMap)
            throws WorkflowException {
        String payloadPath = workItem.getWorkflowData().getPayload().toString();
        // resolve payloadPath, add a "needs-review" tag, save
    }
}

Reacting to changes with ResourceChangeListener

This is the modern replacement for the older JCR ObservationListener API — a simpler interface scoped to specific paths and change types:

AcademyChangeListener.javapackage biz.netcentric.academy._09;

import org.apache.sling.api.resource.observation.ResourceChange;
import org.apache.sling.api.resource.observation.ResourceChangeListener;
import org.osgi.service.component.annotations.Component;

import java.util.List;

@Component(
        service = ResourceChangeListener.class,
        property = {
                ResourceChangeListener.PATHS + "=/content/academy",
                ResourceChangeListener.CHANGES + "=ADDED",
                ResourceChangeListener.CHANGES + "=CHANGED"
        }
)
public class AcademyChangeListener implements ResourceChangeListener {

    @Override
    public void onChange(List<ResourceChange> changes) {
        changes.forEach(change ->
                System.out.println(change.getType() + ": " + change.getPath()));
    }
}

Scheduled jobs

For work that runs on a clock rather than in response to anything, the Sling Scheduler accepts a cron-like expression and calls your code directly:

NightlyReportTask.java (excerpt)@Activate
protected void activate() {
    scheduler.schedule(this, scheduler.EXPR()
            .expression("0 0 2 * * ?")  // 2am daily
            .name("academy-nightly-report")
            .canRunConcurrently(false));
}
Common pitfall Code inside onChange runs synchronously on the thread that triggered the change — a slow listener can visibly delay authoring or replication. Hand off anything heavier than a quick check to a Sling Job (JobManager.addJob(...)) instead of doing the real work inline.
Try it Deploy AcademyChangeListener scoped to /content/academy, then watch the log (tail -f on the error log, or the Felix console's log viewer) while you author a change under that path in the AEM UI.
