OSGi: Bundles, Services & Components

This is the part of AEM that looks most like "normal" Java backend work — until you hit your first wiring problem and need to know what's actually happening underneath the annotations.

What you'll learn

  • What a bundle is, and its lifecycle states
  • The difference between a service and a component
  • How dependency injection works via @Reference
  • How OSGi configuration works, and where to manage it
  • How to read the Felix Web Console when something won't start

Bundles: deployable units

A bundle is a JAR file with extra metadata in its manifest describing what Java packages it exports (makes available to others) and imports (needs from others). OSGi uses this metadata to resolve dependencies between bundles and load them in the right order. Bundles move through a defined lifecycle:

bundle lifecycleINSTALLED → RESOLVED → STARTING → ACTIVE
                                          ↓
                                      STOPPING → RESOLVED

A bundle stuck in INSTALLED or RESOLVED instead of ACTIVE almost always means a missing dependency — some package it imports isn't being exported by anything currently active. That's the single most common first debugging step for "my code isn't running" issues.

Services and components

Inside a bundle, you write components — plain Java classes annotated to participate in OSGi. A component typically implements a service interface, and OSGi maintains a service registry that other components can query or have services injected into them automatically.

GreetingService.javapublic interface GreetingService {
    String greet(String name);
}
GreetingServiceImpl.java@Component(service = GreetingService.class)
public class GreetingServiceImpl implements GreetingService {

    @Override
    public String greet(String name) {
        return "Hello, " + name;
    }
}

Declaring service = GreetingService.class is what publishes this implementation to the registry under that interface. Anything else that needs it can ask for it by interface, never knowing or caring which implementation it gets — that's the whole point: implementations can be swapped without touching the consumers.

Dependency injection with @Reference

To consume a service, declare a field annotated @Reference. OSGi finds a matching implementation in the registry and injects it before the component activates:

GreetingServlet.java@Component(service = Servlet.class)
public class GreetingServlet extends SlingSafeMethodsServlet {

    @Reference
    private GreetingService greetingService;

    @Override
    protected void doGet(SlingHttpServletRequest req, SlingHttpServletResponse resp)
            throws IOException {
        resp.getWriter().write(greetingService.greet("world"));
    }
}

If no implementation of GreetingService is active when this component tries to start, OSGi will hold the component back from activating (unless the reference is explicitly marked optional). This is a deliberate safety mechanism — it prevents you from ever holding a null reference to a required service — but it's also why "bundle won't activate" so often traces back to a missing or misbehaving dependency several layers down.

Mental model Interfaces are contracts published to a registry. Implementations register against them with @Component. Consumers ask for them with @Reference. Nobody but the registry knows which concrete class is actually wired in.

Lifecycle methods

Components can hook into their own lifecycle with @Activate, @Modified, and @Deactivate annotated methods — useful for setup/teardown work like opening a connection pool or scheduling a background task, and for reacting live when a component's configuration changes without a full restart.

OSGi configuration

Components often need configurable values — a timeout, an API endpoint, a feature flag — without hardcoding them. The standard pattern pairs an annotation-defined config type with @Designate:

GreetingConfig.java@ObjectClassDefinition(name = "Greeting Service Configuration")
public @interface GreetingConfig {
    String prefix() default "Hello";
}
GreetingServiceImpl.java (configurable)@Component(service = GreetingService.class)
@Designate(ocd = GreetingConfig.class)
public class GreetingServiceImpl implements GreetingService {

    private String prefix;

    @Activate
    protected void activate(GreetingConfig config) {
        this.prefix = config.prefix();
    }

    @Override
    public String greet(String name) {
        return prefix + ", " + name;
    }
}

Once deployed, this configuration is editable per-environment through the OSGi Configuration Manager (Felix Web Console → Configuration, or /system/console/configMgr) — meaning a value can differ between your local instance, staging, and production without touching code.

Common pitfall Editing a configuration in the Felix console on author does not affect publish, and vice versa — they're separate JVMs with separate configurations (echoing module 1). Configuration changes made by hand in one environment also tend to get lost on the next deployment unless they're captured as a proper config file (a .cfg.json) checked into your project's repository.

Reading the Felix console

When something isn't working, /system/console/bundles shows every bundle's state and, for anything not Active, why — usually an unsatisfied import. /system/console/components shows the same idea one level down, for individual components rather than whole bundles. Getting comfortable reading these two screens will save you far more debugging time than guessing from stack traces alone.

Try it On a local AEM instance, open /system/console/bundles and find a bundle that is not Active. Click into it to see which import is unsatisfied, and reason about why that dependency might be missing.
