OSGi: Bundles, Services & Components

OSGi is the plugin system that powers AEM. Every piece of Java code you write lives inside an OSGi bundle, and every service you register is tracked in an OSGi registry. Once you understand this, the annotations stop looking like magic and start making sense.

What you'll learn

  • What a bundle is and why it is not just a regular JAR
  • What the bundle lifecycle states mean, and how to read them when something is broken
  • The difference between a component and a service
  • How @Component and @Reference wire things together without new keywords
  • Why you always split an interface from its implementation
  • How lifecycle hooks (@Activate, @Deactivate) let you react to startup and shutdown
  • Where to look when a component simply refuses to start

The big picture: AEM as a city of plugins

Imagine a city. Each building in the city provides a service — a bakery provides bread, a pharmacy provides medicine, a post office handles parcels. The city has a directory (the service registry) that lists every service currently available. When you need bread, you look up "bakery" in the directory — you don't care which specific bakery fulfils the order.

OSGi works exactly like this:

  • Each bundle is a building — a self-contained unit of code that can be installed, started, stopped, and updated without restarting the whole city (AEM).
  • Each service is what a bundle offers to the city — a named capability others can use.
  • The service registry is the city directory — it tracks what is available, and wires consumers to providers automatically.

Bundles: not just a JAR

Your core module compiles to a .jar file. But it's not an ordinary JAR — it's an OSGi bundle: a JAR with extra lines in its META-INF/MANIFEST.MF that declare exactly what Java packages it makes available to others (Export-Package) and what it needs from other bundles (Import-Package).

MANIFEST.MF snippet — you never write this by hand, Maven generates itBundle-SymbolicName: biz.netcentric.academy.core
Bundle-Version: 1.0.0
Export-Package: biz.netcentric.academy.core.services;version="1.0.0"
Import-Package: org.apache.sling.api;version="[2.0,3)",
                org.osgi.service.component.annotations;version="[1.4,2)"
📖 Why this code?

This is the OSGi bundle manifest — the metadata that makes a JAR file an OSGi bundle rather than an ordinary JAR. You never write this by hand; the bnd Maven plugin generates it from your source code annotations during the build.

  • Export-Package — lists the Java packages this bundle makes available to other bundles. Only exported packages can be referenced by other bundles' code. Packages not listed here are private to this bundle.
  • Import-Package — lists every package this bundle needs from other bundles, with version ranges. OSGi checks these at deploy time. If any import isn't satisfied by an active bundle, this bundle won't reach the ACTIVE state.
  • Version ranges like [2.0,3) mean "2.0 or later, but less than 3.0" — square bracket = inclusive, round bracket = exclusive.

When you run mvn clean install -PautoInstallSinglePackage, Maven uses the bnd plugin to scan your classes and generate this manifest automatically. You configure what gets exported in bnd.bnd, but you rarely need to touch it.

The bundle lifecycle — what the Felix console is telling you

Every bundle travels through defined states. When something isn't working, the Felix console tells you exactly which state the bundle is stuck in:

bundle lifecycle statesINSTALLED   → bundle jar uploaded to AEM, dependencies not yet checked
     ↓
RESOLVED    → all Import-Package dependencies satisfied (but code not running yet)
     ↓
STARTING    → @Activate methods running
     ↓
ACTIVE      ← this is what you want. Your code is live.
     ↓
STOPPING    → @Deactivate methods running (on uninstall or AEM shutdown)
     ↓
RESOLVED
📖 Why this code?

Every OSGi bundle moves through these states in order. Knowing what each state means tells you exactly where a deployment is stuck when something isn't working.

  • INSTALLED — the JAR was uploaded but package-level dependencies (from Import-Package) haven't been checked yet.
  • RESOLVED — all Import-Package dependencies are satisfied. The class loader can find everything. But no code is running yet.
  • ACTIVE — this is the target state. All @Activate methods have run, all @Reference fields are injected, and the component is live and serving requests.
  • If a bundle is stuck at RESOLVED instead of ACTIVE, it typically means an @Reference field has no active provider — go to /system/console/components to see which service is missing.
Bundle stuck at INSTALLED or RESOLVED? This almost always means a missing import — some package your code needs isn't exported by any active bundle. Go to /system/console/bundles, click on your bundle, and read the "Unsatisfied imports" section. That package name is your clue: either a dependency is missing from your pom.xml, or the bundle that provides it isn't active either.

Components vs Services — the critical distinction

These two words mean specific things in OSGi, and they're often confused:

  • A component is a Java class annotated with @Component. It is a unit of code that OSGi manages — it can be started, stopped, and configured.
  • A service is a capability that a component publishes to the registry so other components can use it. Publishing a service is optional — a component doesn't have to offer one.

In practice, almost every component you write will publish a service, but the distinction matters: the component is the living Java object; the service is the contract (usually an interface) it registers under.

Your first service — step by step

Let's build a complete, working service from scratch. We need three files:

Step 1: Define the contract as an interface. This is what consumers will depend on — they will never import the implementation class.

/aem-academy/core/src/main/java/biz/netcentric/academy/osgiexample/GreetingService.java (academy.core)package biz.netcentric.academy.osgiexample;

/**
 * A service that produces greeting strings.
 * This interface is the contract — consumers use only this, never the implementation.
 */
public interface GreetingService {
    String greet(String name);
}
📖 Why this code?

A plain Java interface with no framework annotations. This is the public contract — the only thing consumers ever import from your service layer.

  • Having no annotations here is deliberate. An interface is just a Java contract; OSGi doesn't need to know about it at this level. The framework annotations go on the implementation class only.
  • By depending only on this interface (never on GreetingServiceImpl directly), every consumer is automatically isolated from implementation details. When you need to add logging, caching, or a completely different backend, you change the implementation and nothing else needs to change.

Step 2: Write the implementation. The @Component annotation is what makes OSGi aware of this class, and service = GreetingService.class is what registers it in the service registry under that interface.

/aem-academy/core/src/main/java/biz/netcentric/academy/osgiexample/GreetingServiceImpl.java (academy.core)package biz.netcentric.academy.osgiexample;

import org.osgi.service.component.annotations.Component;

@Component(service = GreetingService.class)  // ← registers in the registry
public class GreetingServiceImpl implements GreetingService {

    @Override
    public String greet(String name) {
        return "Hello, " + name + "!";
    }
}
📖 Why this code?

This is the OSGi service implementation — the class that actually runs. The annotations are what connect it to the OSGi runtime.

  • @Component(service = GreetingService.class) — the most important annotation here. @Component alone just manages the lifecycle (start/stop). The service attribute is what publishes this class in the OSGi service registry, keyed by the GreetingService interface. Without service = ..., the component activates but nothing can find it via @Reference.
  • implements GreetingService — Java compile-time enforcement that this class really does satisfy the interface contract. OSGi doesn't check this at runtime; the Java compiler does.

Step 3: Consume the service somewhere. @Reference tells OSGi: "find me whoever registered as GreetingService and inject it here before this component starts."

/aem-academy/core/src/main/java/biz/netcentric/academy/osgiexample/GreetingServlet.java (academy.core)package biz.netcentric.academy.osgiexample;

import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.api.SlingHttpServletResponse;
import org.apache.sling.api.servlets.SlingSafeMethodsServlet;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Reference;

import javax.servlet.Servlet;
import javax.servlet.ServletException;
import java.io.IOException;

@Component(
    service = Servlet.class,
    property = "sling.servlet.paths=/bin/academy/osgi-greet"
)
public class GreetingServlet extends SlingSafeMethodsServlet {

    @Reference                              // ← OSGi injects this automatically
    private GreetingService greetingService;

    @Override
    protected void doGet(SlingHttpServletRequest req, SlingHttpServletResponse resp)
            throws ServletException, IOException {
        resp.setContentType("text/plain");
        // We call the interface — we have NO idea (and don't care) which
        // implementation is actually behind it.
        resp.getWriter().write(greetingService.greet("world"));
    }
}
📖 Why this code?

This servlet demonstrates OSGi dependency injection — consuming a service without knowing its implementation.

  • @Reference private GreetingService greetingService — OSGi looks up the registry at component activation time, finds the active GreetingService implementation (our GreetingServiceImpl), and injects it. The servlet never calls new GreetingServiceImpl(). If no implementation is active, this servlet won't activate either — preventing a NullPointerException at runtime.
  • sling.servlet.paths=/bin/academy/osgi-greet — registering by path (rather than resourceType) is suitable for utility endpoints like this that aren't tied to a specific content type. The path prefix /bin/ is conventionally used for non-content endpoints in AEM.
Why @Reference instead of "new GreetingServiceImpl()"? Using new would hardcode a dependency on the concrete class. Using @Reference means OSGi looks up whoever registered as GreetingService — today that's GreetingServiceImpl, tomorrow you could swap in PersonalisedGreetingServiceImpl without touching a single line in GreetingServlet. This decoupling also makes unit testing possible: you can register a fake implementation in your test, and the servlet will use it automatically.

What happens when you deploy — the full sequence

what mvn clean install does, step by step1. Maven compiles your .java files → .class files
2. bnd plugin reads @Component / @Reference annotations on your classes
3. bnd generates OSGi metadata (MANIFEST.MF + /OSGI-INF/*.xml descriptor files)
4. Everything is packaged into academy.core-1.0.0.jar
5. That JAR is wrapped into a content package and installed to AEM via HTTP
6. AEM's OSGi runtime (Felix) loads the bundle → state moves to RESOLVED
7. Felix checks all @Reference fields — if every required dependency is satisfied
   the component activates → state moves to ACTIVE
8. Your service is now in the registry. Any component with @Reference GreetingService
   gets it injected.
📖 Why this code?

This sequence shows everything that happens between running mvn clean install and your code being live in AEM. Understanding this removes the mystery from build problems.

  • Steps 1–3: Maven compiles Java and the bnd plugin scans your @Component and @Reference annotations. It generates an OSGI-INF/ folder of XML descriptor files — these are what OSGi actually reads, not your annotations directly. Your annotations are just a convenient source format.
  • Steps 5–6: The content package is installed to AEM via HTTP (the autoInstallSinglePackage profile). AEM's embedded Felix OSGi runtime loads the bundle.
  • Step 7: Felix checks every @Reference field. Only when all are satisfied does the component move to ACTIVE. This is why a missing dependency causes a component to silently not start rather than throwing an exception.

Lifecycle hooks: @Activate, @Modified, @Deactivate

Sometimes you need to run code when a component starts or stops — opening a database connection, scheduling a background task, or reading configuration values. These three annotations hook into the lifecycle:

lifecycle hooks in practice@Component(service = GreetingService.class)
@Designate(ocd = GreetingConfig.class)
public class GreetingServiceImpl implements GreetingService {

    private String prefix;

    @Activate   // called when the component starts AND when config changes
    @Modified   // (you can put both on the same method)
    protected void activate(GreetingConfig config) {
        this.prefix = config.prefix();  // read config value once, store it
    }

    @Deactivate
    protected void deactivate() {
        // clean up resources — close connections, cancel timers, etc.
    }

    @Override
    public String greet(String name) {
        return prefix + ", " + name + "!";
    }
}
📖 Why this code?

These three lifecycle annotations let a component run code at specific points in its existence. Understanding when they're called prevents subtle bugs.

  • @Activate — called when the component starts AND again when its OSGi configuration changes (if you also add @Modified). Read config values here and store them as fields — don't read config in every method call.
  • @Modified — can be placed on the same method as @Activate. If a user changes the configuration in the Felix console, OSGi calls this method with the new config values — without stopping and restarting the whole bundle.
  • @Deactivate — called when the bundle stops or when AEM shuts down. Release resources here: close database connections, cancel scheduled tasks, shut down thread pools. Omitting this causes resource leaks.
  • private String prefix — storing the config value as a field means it's only read once (on activate), not on every greet() call.

Adding configuration to a service

Hard-coded values (API keys, timeouts, feature flags) are a problem. The standard OSGi pattern is a configuration annotation type:

/aem-academy/core/src/main/java/biz/netcentric/academy/osgiexample/GreetingConfig.java (academy.core)package biz.netcentric.academy.osgiexample;

import org.osgi.service.metatype.annotations.AttributeDefinition;
import org.osgi.service.metatype.annotations.ObjectClassDefinition;

@ObjectClassDefinition(name = "Greeting Service Configuration")
public @interface GreetingConfig {

    @AttributeDefinition(name = "Greeting prefix", description = "Prefix added before every greeting")
    String prefix() default "Hello";
}
📖 Why this code?

This is an OSGi configuration annotation type. In Java, @interface declares an annotation type — here, OSGi repurposes this syntax as a configuration schema.

  • @ObjectClassDefinition — marks this annotation type as an OSGi configuration descriptor. The name attribute becomes the human-readable label in the Felix console (/system/console/configMgr).
  • @AttributeDefinition — metadata for each configuration property: its label in the UI, an optional description, and constraints like min/max values.
  • String prefix() default "Hello" — each method in the @interface becomes a configuration property. The method name is the property key, the return type is the value type, and default is the fallback if no config is deployed.
  • The public @interface syntax looks unusual but it's standard Java. The bnd plugin reads it and generates the OSGi metatype XML that makes the Felix console form appear.

Add @Designate(ocd = GreetingConfig.class) to your implementation (as shown above) and the configuration type is automatically picked up. You can now edit the prefix at /system/console/configMgr without touching code or redeploying.

Where to look when things break

The Felix web console has two URLs you must memorise:

  • /system/console/bundles — lists every bundle and its state. A bundle not in ACTIVE state will tell you what import is unsatisfied when you click it.
  • /system/console/components — lists every OSGi component inside all active bundles. If a component shows unsatisfied references, it means a @Reference field has no active provider. Click the component to see exactly which reference is missing.
Common pitfall: editing config in the Felix console The Felix console is great for checking things and for testing a config value quickly. But any change you make there is stored only in the repository on that one instance — it is not in your source code, and it will be overwritten on the next deployment. Always check config changes into ui.config as .cfg.json files (covered in detail in module 5).
Try it — build the full example
  1. Create GreetingService.java (interface) and GreetingServiceImpl.java at the paths shown above.
  2. Create GreetingServlet.java and deploy: mvn clean install -PautoInstallSinglePackage from /aem-academy.
  3. Visit /system/console/components and find GreetingServlet. Confirm it shows active.
  4. Visit http://localhost:4502/bin/academy/osgi-greet. You should see Hello, world!
  5. Now add GreetingConfig.java and update GreetingServiceImpl to use it. Redeploy and change the prefix in /system/console/configMgr. Hit the endpoint again.
