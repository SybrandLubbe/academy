Groovy Console

Sometimes you need to fix or migrate content once — relabel a property across a thousand pages, backfill a new field — and writing, building, and deploying a full OSGi bundle for a script you'll run exactly one time is real overkill. The Groovy Console exists for exactly that gap.

What you'll learn

  • Just enough Groovy syntax to read and write the scripts you'll actually use
  • Installing the AEM Groovy Console
  • Writing a script that walks content and updates it safely

Just enough Groovy

Groovy compiles to the same JVM bytecode as Java and can call any Java API directly — everything you already know about ResourceResolver, Resource, and the JCR API from earlier modules still applies. The differences that matter for short scripts: semicolons are optional, types are usually inferred with def instead of declared explicitly, and string interpolation uses "${expression}" inside double-quoted strings:

Java vs. Groovy, the same idea// Java
String message = "Hello, " + name + "!";

// Groovy
def message = "Hello, ${name}!"

Closures (Groovy's lambdas) read similarly to Java streams but with looser syntax — resources.each { resource -> println resource.path } instead of a full stream pipeline. For a one-off script, that's genuinely all the Groovy-specific syntax you need; the actual content logic is the same AEM APIs you've used throughout this curriculum.

Installing the Groovy Console

The AEM Groovy Console is a community-maintained, open-source AEM add-on — not part of the product itself. Download the released content package (a .zip) matching your AEM version from its GitHub releases page, then install it the same way as any content package: AEM's Package Manager (/crx/packmgr) → Upload Package → select the file → Install.

Common pitfall Never install the Groovy Console on a production publish instance. It grants whoever has access to it the ability to run arbitrary code with full repository permissions — treat it strictly as an author/development-environment tool, and remove it before going live if it was only needed for a migration.

Writing a script

Once installed, the console UI gives you a script editor and a "Run" button. The console pre-binds a few useful variables for you, most importantly a ResourceResolver — you don't need to obtain one yourself. A typical migration script walks a content subtree and updates a property, with a dry-run flag so you can see what would change before committing it:

Groovy Console script — backfill a missing propertydef dryRun = true
def rootPath = "/content/academy"

def root = resourceResolver.getResource(rootPath)
def updated = 0

root.listChildren().each { page ->
    def content = page.getChild("jcr:content")
    if (content != null && content.valueMap.get("academyReviewed") == null) {
        println "Would update: ${content.path}"
        if (!dryRun) {
            def props = content.adaptTo(org.apache.sling.api.resource.ModifiableValueMap)
            props.put("academyReviewed", false)
            updated++
        }
    }
}

if (!dryRun) {
    resourceResolver.commit()
}

println "Done. Dry run: ${dryRun}, updated: ${updated}"

Run it once with dryRun = true and read the output carefully before flipping it to false — this single habit is what separates a safe content migration from an afternoon spent restoring from backup.

Try it Write a dry-run-first script that lists every page under /content/academy missing a jcr:title, without modifying anything — confirm the output looks right before anyone on the team writes a version that actually changes content.
