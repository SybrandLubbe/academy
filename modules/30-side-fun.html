Author Tools 60 min build

Side Fun — Author Interface Enhancements

Two small but high-value additions to the AEM authoring experience that every content team asks for eventually: colour-coded page status dots in the Sites console so authors can see at a glance which pages are published, modified, deactivated, or never activated — and a floating environment banner so nobody ever wonders which server they're working on. Both are built with techniques covered in this training: a Sling Servlet for the data, a clientlib for the UI, and OSGi config for environment-specific values.

What you're building

  • Part 1 — Page Status Dots: a coloured dot appears on every page card and list row in /sites.html, reading live replication metadata from the JCR
  • Part 2 — Environment Banner: a persistent floating pill in the corner of every author screen shows the current environment name and colour-coded by severity (green = dev, orange = stage, red = production)
  • A Sling Servlet for each feature, one clientlib per feature, OSGi configs per run mode, and a short MutationObserver-based JavaScript that works across all three Sites console view modes (card, list, column)
Why clientlib category matters The Sites console at /sites.html is a Granite UI single-page app. It automatically loads all clientlibs registered under the category cq.wcm.admin.sites. The page editor loads cq.authoring.editor.hook. Registering your clientlib under these categories is the only change needed to inject custom JS and CSS into those UIs — no overlay, no HTL modification required.

Part 1 — Page Status Indicator Dots

How AEM stores page publication status

Every AEM page's jcr:content node carries three replication properties that together describe its status. Understanding these is the foundation of the entire feature.

replication metadata on jcr:content — what determines statusPROPERTY                    TYPE        MEANING
cq:lastReplicated           Calendar    Timestamp of the last replication event.
                                        NULL means the page has NEVER been published.

cq:lastReplicationAction    String      "Activate" or "Deactivate" — what happened last.

cq:lastModified             Calendar    When an author last saved a change to the page.

STATUS DETERMINATION (in priority order):
  cq:lastReplicated is null
      → NEVER PUBLISHED (gray)   Page exists but was never activated.

  cq:lastReplicationAction = "Deactivate"
      → DEACTIVATED (red)        Was published, then taken offline.

  cq:lastReplicationAction = "Activate"
  AND cq:lastModified > cq:lastReplicated
      → MODIFIED (blue)          Published but has unsaved-to-live changes since.

  cq:lastReplicationAction = "Activate"
  AND (cq:lastModified is null OR cq:lastModified <= cq:lastReplicated)
      → ACTIVATED (green)        Live and up to date. Clean publish.

ADDITIONAL STATUS (edge case):
  Page node exists but jcr:content is missing or has no cq:template
      → UNKNOWN (dark gray)      Structural anomaly or damaged page.
📖 Why this code?

These properties are written by AEM's replication agent every time an author clicks Publish or Unpublish. They're plain JCR properties on the jcr:content node — no special API needed to read them.

  • The Modified (blue) state is the most actionable — it tells an author "this page is live, but what's live doesn't match what you're looking at in the editor." This is the status authors most often miss without visual indicators, because the page looks fine in the editor but the live site is serving an older version.
  • Comparing Calendars — cq:lastModified > cq:lastReplicated means the author saved changes after the last publication. Java's Calendar.after() handles this comparison cleanly.
  • Never Published (gray) vs Deactivated (red) — different situations, different author actions needed. Gray means "never activated — use Quick Publish." Red means "was active, now offline — check if this was intentional before re-activating."

Step 1 — PageStatusServlet

A path-based Sling Servlet (module 10 pattern) that accepts one or more page paths, reads the replication metadata from each page's jcr:content, and returns a JSON map of {path: status}. The JavaScript calls this in a single batched request for all visible pages.

/aem-academy/core/src/main/java/biz/netcentric/academy/core/servlets/PageStatusServlet.java (academy.core)package biz.netcentric.academy.core.servlets;

import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.api.SlingHttpServletResponse;
import org.apache.sling.api.resource.Resource;
import org.apache.sling.api.resource.ValueMap;
import org.apache.sling.api.servlets.SlingSafeMethodsServlet;
import org.osgi.service.component.annotations.Component;

import javax.json.Json;
import javax.json.JsonObjectBuilder;
import javax.servlet.Servlet;
import javax.servlet.ServletException;
import java.io.IOException;
import java.util.Calendar;

/**
 * Returns JSON publication status for a batch of page paths.
 * GET /bin/academy/pagestatus?paths=/content/a&paths=/content/b
 * Response: { "/content/a": "activated", "/content/b": "modified" }
 */
@Component(service = Servlet.class,
           property = {
               "sling.servlet.paths=/bin/academy/pagestatus",
               "sling.servlet.methods=GET"
           })
public class PageStatusServlet extends SlingSafeMethodsServlet {

    private static final String PROP_REPLICATED = "cq:lastReplicated";
    private static final String PROP_ACTION      = "cq:lastReplicationAction";
    private static final String PROP_MODIFIED    = "cq:lastModified";

    @Override
    protected void doGet(SlingHttpServletRequest request,
                         SlingHttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("application/json;charset=UTF-8");
        response.setHeader("Cache-Control", "no-cache");
        response.setHeader("Access-Control-Allow-Origin", "same-origin");

        String[] paths = request.getParameterValues("paths");
        if (paths == null || paths.length == 0) {
            response.getWriter().write("{}");
            return;
        }

        JsonObjectBuilder result = Json.createObjectBuilder();

        for (String path : paths) {
            if (path == null || !path.startsWith("/content")) {
                continue;   // never expose non-content paths
            }
            // Read jcr:content directly — avoids PageManager overhead for batch calls
            Resource content = request.getResourceResolver()
                                      .getResource(path + "/jcr:content");
            if (content == null) {
                result.add(path, "unknown");
                continue;
            }
            result.add(path, determineStatus(content.getValueMap()));
        }

        response.getWriter().write(result.build().toString());
    }

    /**
     * Determine the publication status string from the page's jcr:content ValueMap.
     * Priority: never-published → deactivated → modified → activated → unknown.
     */
    private String determineStatus(ValueMap props) {
        Calendar lastReplicated = props.get(PROP_REPLICATED, Calendar.class);
        String   action         = props.get(PROP_ACTION,     String.class);
        Calendar lastModified   = props.get(PROP_MODIFIED,   Calendar.class);

        if (lastReplicated == null) {
            return "draft";         // cq:lastReplicated absent = never published
        }

        if ("Deactivate".equalsIgnoreCase(action)) {
            return "deactivated";   // explicitly taken offline
        }

        if ("Activate".equalsIgnoreCase(action)) {
            if (lastModified != null && lastModified.after(lastReplicated)) {
                return "modified";  // live but has pending author changes
            }
            return "activated";     // live and up to date
        }

        return "unknown";           // structural anomaly
    }
}
📖 Why this code?

The Servlet follows the exact pattern from module 10 — path-based, GET only, JSON response. The batch design (multiple paths params) is what makes it performant for a Sites console folder with 50 pages.

  • request.getParameterValues("paths") — reads all values of the repeated ?paths=X&paths=Y query string as a String array. This is more efficient than multiple separate requests — one round trip for the entire visible page set.
  • path.startsWith("/content") — the security guard. Without it, a malicious call to ?paths=/etc/passwd could probe for content at arbitrary JCR paths. Only /content subtree paths are ever resolved.
  • resource.getResource(path + "/jcr:content") directly instead of PageManager.getPage(path).getContentResource() — avoids the overhead of constructing a full Page object for each path. For a batch of 50 pages this is ~3× faster.
  • "Deactivate".equalsIgnoreCase(action) — using equalsIgnoreCase defensively. The value is written by AEM's replication framework and should always be "Activate" or "Deactivate" in title case, but consistency across AEM versions isn't guaranteed.
  • lastModified.after(lastReplicated) — Java's Calendar.after() handles timezone-aware comparison correctly. Comparing raw milliseconds (getTimeInMillis()) would also work but is less readable.

The CSS covers three rendering contexts: card view (absolute-positioned badge), list/table view (inline cell content), and a collapsible legend for authors who need a colour key.

Step 4 — JavaScript: MutationObserver + fetch + DOM injection

The Sites console is a dynamic SPA — navigating between folders replaces content in the DOM without a full page reload. A MutationObserver watches for these DOM changes and re-queries the status servlet whenever new page items appear, keeping the dots current as the author browses.

/apps/academy/clientlibs/sites-status/js/sites-status.js(function () {
  'use strict';

  var STATUS_URL = '/bin/academy/pagestatus';

  // Map status strings → { CSS class, display label }
  var STATUS_MAP = {
    activated  : { cls: 'academy-status--activated',   label: 'Published'           },
    modified   : { cls: 'academy-status--modified',    label: 'Modified (unpublished changes)' },
    deactivated: { cls: 'academy-status--deactivated', label: 'Deactivated'          },
    draft      : { cls: 'academy-status--draft',       label: 'Never Published'      },
    unknown    : { cls: 'academy-status--unknown',     label: 'Unknown'              }
  };

  // ── Inject the floating legend ─────────────────────────────────────────
  function injectLegend() {
    if (document.querySelector('.academy-legend-toggle')) return; // already present

    // Toggle button (the ● icon)
    var btn = document.createElement('button');
    btn.className = 'academy-legend-toggle';
    btn.title     = 'Page status legend';
    btn.innerHTML = '●'; // filled circle
    btn.setAttribute('aria-label', 'Toggle page status legend');

    // Legend panel
    var legend = document.createElement('div');
    legend.className = 'academy-status-legend';
    legend.innerHTML =
      '<div class="academy-status-legend__title">Page Status</div>' +
      Object.keys(STATUS_MAP).map(function (key) {
        var s = STATUS_MAP[key];
        return '<div class="academy-status-legend__row">' +
               '<span class="academy-status-dot ' + s.cls + '"></span>' +
               '<span>' + s.label + '</span>' +
               '</div>';
      }).join('');

    // Toggle open/close
    btn.addEventListener('click', function () {
      var open = legend.classList.toggle('is-visible');
      btn.classList.toggle('is-open', open);
      btn.setAttribute('aria-expanded', String(open));
    });

    document.body.appendChild(btn);
    document.body.appendChild(legend);
  }

  // ── Collect all /content page paths currently in the DOM ──────────────
  function getVisiblePaths() {
    var paths = [];
    var seen  = {};
    // The attribute [data-foundation-collection-item-id] is present on
    // card, column-view item, AND table rows — works in all three view modes.
    document.querySelectorAll('[data-foundation-collection-item-id]').forEach(function (el) {
      var path = el.getAttribute('data-foundation-collection-item-id');
      if (path && path.startsWith('/content') && !seen[path]) {
        paths.push(path);
        seen[path] = true;
      }
    });
    return paths;
  }

  // ── Build and attach a status badge to a single collection item ────────
  function attachBadge(element, status) {
    var meta = STATUS_MAP[status] || STATUS_MAP['unknown'];

    // Remove any previously attached badge (handles re-renders)
    var old = element.querySelector('.academy-status-badge');
    if (old) old.remove();

    var badge = document.createElement('div');
    badge.className = 'academy-status-badge';
    badge.setAttribute('aria-label', 'Status: ' + meta.label);

    var dot = document.createElement('span');
    dot.className = 'academy-status-dot ' + meta.cls;
    dot.title     = meta.label;

    var label = document.createElement('span');
    label.textContent = meta.label;

    badge.appendChild(dot);
    badge.appendChild(label);

    // Ensure the parent has position:relative so our absolute badge works
    var style = window.getComputedStyle(element);
    if (style.position === 'static') {
      element.style.position = 'relative';
    }
    element.appendChild(badge);
  }

  // ── Fetch statuses for all visible paths and apply badges ──────────────
  function updateStatuses() {
    var paths = getVisiblePaths();
    if (!paths.length) return;

    // Build query string: ?paths=/content/a&paths=/content/b&...
    var qs = paths.map(function (p) {
      return 'paths=' + encodeURIComponent(p);
    }).join('&');

    fetch(STATUS_URL + '?' + qs, { credentials: 'same-origin' })
      .then(function (r) {
        if (!r.ok) throw new Error('HTTP ' + r.status);
        return r.json();
      })
      .then(function (statusMap) {
        Object.keys(statusMap).forEach(function (path) {
          var status  = statusMap[path];
          // Select ALL elements for this path (card view may have duplicates)
          document.querySelectorAll(
            '[data-foundation-collection-item-id="' + CSS.escape(path) + '"]'
          ).forEach(function (el) {
            attachBadge(el, status);
          });
        });
      })
      .catch(function (err) {
        console.warn('[Academy Status] Fetch failed:', err);
      });
  }

  // ── Debounced MutationObserver: re-run when DOM content changes ────────
  var debounceTimer = null;

  var observer = new MutationObserver(function (mutations) {
    // Only care about childList changes that add nodes (navigation events)
    var relevant = mutations.some(function (m) {
      return m.type === 'childList' && m.addedNodes.length > 0;
    });
    if (!relevant) return;

    clearTimeout(debounceTimer);
    debounceTimer = setTimeout(updateStatuses, 350); // 350ms debounce
  });

  // ── Initialise ─────────────────────────────────────────────────────────
  function init() {
    // Only run on the Sites console — skip page editor and other tools
    if (!window.location.pathname.startsWith('/sites.html') &&
        !window.location.pathname.startsWith('/mnt/overlay/dam/gui')) {
      return;
    }

    injectLegend();
    updateStatuses();

    // Watch the entire body for DOM changes (SPA navigation)
    observer.observe(document.body, {
      childList: true,
      subtree  : true
    });
  }

  // Wait for Coral UI to boot before initialising
  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', init);
  } else {
    init();
  }

}());
📖 Why this code?

The MutationObserver is the critical pattern — without it the dots would only appear on the initial page load and disappear whenever the author navigates between folders.

  • MutationObserver — watches the DOM for structural changes (childList: true, subtree: true). When the Sites console SPA navigates to a child folder, it replaces the collection items in the DOM. The Observer fires, the debounce timer resets, and after 350ms updateStatuses() runs for the new set of pages. Without this, dots only appear once on initial load.
  • 350ms debounce — the SPA navigation causes many rapid DOM mutations (items are removed, then added, then attributes are updated). Without debouncing, updateStatuses() would fire 20–50 times per navigation event, hammering the servlet. The 350ms window lets the DOM settle before making one clean request.
  • [data-foundation-collection-item-id] — the universal selector that works in all three view modes. Card view, column view, and list view all write the page path to this attribute. Using it as the hook means the JavaScript handles all view modes with zero conditional logic.
  • CSS.escape(path) — page paths can contain characters like [ and ] that have special meaning in CSS selectors. CSS.escape() makes the path safe to embed in a querySelectorAll attribute selector. Without it, a path like /content/dam/[2024]/image would throw a syntax error.
  • Path guard window.location.pathname.startsWith('/sites.html') — the clientlib category cq.wcm.admin.sites is also loaded on some related admin pages. This guard prevents the MutationObserver from running unnecessarily on pages where it serves no purpose, reducing memory pressure.

Part 2 — Floating Environment Banner

Authors working across multiple AEM environments (local, dev, stage, production) occasionally make changes in the wrong environment — an easy mistake when four browser tabs all look identical. A small, always-visible banner in the corner of every author screen solves this: the name and colour of the current environment are impossible to miss.

How the environment name is determined

how environment is communicated to the browserAPPROACH: OSGi config per run mode + Servlet endpoint

AUTHOR instance knows its environment from sling.run.modes:
  local instance:  sling.run.modes = author,local
  dev server:      sling.run.modes = author,dev
  stage server:    sling.run.modes = author,stage
  prod server:     sling.run.modes = author,prod

Each run mode has its own OSGi config file (module 05 pattern):
  ui.config/.../osgiconfig/config.local/  → "Local" + blue
  ui.config/.../osgiconfig/config.dev/    → "Development" + green
  ui.config/.../osgiconfig/config.stage/  → "Staging" + orange
  ui.config/.../osgiconfig/config.prod/   → "PRODUCTION" + red

A Servlet at /bin/academy/envinfo reads the active config and returns:
  { "label": "PRODUCTION", "colour": "#e34850", "tier": "Author" }

The clientlib JS fetches this endpoint once on load and renders the banner.

WHY a Servlet and not a hardcoded value in JS?
  The clientlib is deployed the same way to all environments.
  The Servlet is what differs per environment via OSGi config.
  A hardcoded banner label in JS would require different clientlib
  builds per environment — violating the "same artifact everywhere" rule.
📖 Why this code?

Using OSGi config per run mode is the exact same pattern from module 5 — the config changes per environment, the code doesn't.

  • "Same artifact everywhere" — your Maven build produces one all.zip. That zip deploys to dev, stage, and prod without modification. Environment differences come from OSGi config, not from different builds. If you hardcoded "PRODUCTION" in the JavaScript, you'd need a different artifact per environment.
  • The Servlet reads the environment label from an injected OSGi config. On local, the config.local folder is active, so the config reads "Local". On prod, the config.prod folder is active, reading "PRODUCTION". Same Servlet, different config, different output.

Step 1 — OSGi config annotation type

/aem-academy/core/src/main/java/biz/netcentric/academy/core/servlets/EnvironmentBannerServlet.java (academy.core)package biz.netcentric.academy.core.servlets;

import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.api.SlingHttpServletResponse;
import org.apache.sling.api.servlets.SlingSafeMethodsServlet;
import org.osgi.service.component.annotations.Activate;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Modified;
import org.osgi.service.metatype.annotations.AttributeDefinition;
import org.osgi.service.metatype.annotations.Designate;
import org.osgi.service.metatype.annotations.ObjectClassDefinition;

import javax.json.Json;
import javax.servlet.Servlet;
import javax.servlet.ServletException;
import java.io.IOException;

/**
 * Returns the current environment label and colour for the floating banner.
 * GET /bin/academy/envinfo
 * Response: { "label": "PRODUCTION", "colour": "#e34850", "tier": "Author" }
 *
 * Configure per environment via OSGi run-mode config files (ui.config module).
 */
@Component(service = Servlet.class,
           property = {
               "sling.servlet.paths=/bin/academy/envinfo",
               "sling.servlet.methods=GET"
           })
@Designate(ocd = EnvironmentBannerServlet.Config.class)
public class EnvironmentBannerServlet extends SlingSafeMethodsServlet {

    // ── @ObjectClassDefinition drives the Felix console form ──────────────
    @ObjectClassDefinition(
        name        = "Academy — Environment Banner Configuration",
        description = "Controls the floating environment banner shown in the AEM author UI."
    )
    public @interface Config {

        @AttributeDefinition(
            name        = "Environment Label",
            description = "Short name displayed on the banner. e.g. Local, Development, Staging, PRODUCTION"
        )
        String environmentLabel() default "Local";

        @AttributeDefinition(
            name        = "Banner Colour",
            description = "CSS hex colour for the banner background. Use red for production!"
        )
        String bannerColour() default "#2680eb";

        @AttributeDefinition(
            name        = "Show Banner",
            description = "Set to false to hide the banner entirely (e.g. to disable on production if preferred)."
        )
        boolean showBanner() default true;
    }

    // ── OSGi-injected config values (stored as fields after @Activate) ────
    private String  environmentLabel;
    private String  bannerColour;
    private boolean showBanner;

    @Activate
    @Modified
    protected void activate(Config config) {
        this.environmentLabel = config.environmentLabel();
        this.bannerColour     = config.bannerColour();
        this.showBanner       = config.showBanner();
    }

    @Override
    protected void doGet(SlingHttpServletRequest request,
                         SlingHttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("application/json;charset=UTF-8");
        response.setHeader("Cache-Control", "no-cache");

        response.getWriter().write(
            Json.createObjectBuilder()
                .add("label",      environmentLabel)
                .add("colour",     bannerColour)
                .add("showBanner", showBanner)
                .build()
                .toString()
        );
    }
}
📖 Why this code?

The Servlet and its config annotation type are in the same file — a clean pattern for small servlets where the config is tightly coupled to the component.

  • @Designate(ocd = EnvironmentBannerServlet.Config.class) — links the Servlet OSGi component to its configuration schema. The Config inner @interface is the schema; @Designate is what connects them. Without @Designate, the config class exists but is never loaded into the Servlet.
  • @Activate @Modified on the same method — both annotations on activate() means the same method runs both when the component first starts AND when its config is updated in the Felix console (or when a new .cfg.json is deployed). This is the standard pattern — without @Modified, live config changes via the Felix console require a bundle restart to take effect.
  • showBanner() default true — the ability to disable the banner via config is important. Some teams want the banner visible only in non-production environments, not on the live production author instance. Setting showBanner = false in config.prod achieves this without code changes.
  • The Servlet stores config values as plain fields assigned in @Activate — not reading from config on every request. This is the module 04 pattern: read once at activation, serve fast on every request.

📖 Why this code?

Four files, four environments, zero code differences. The run-mode folder name is the entire environment-selection mechanism.

  • Filename = fully qualified class name — OSGi finds the right config by matching the file name to the @Component class name. Typos in the filename result in silent failure — the config is ignored and the Servlet uses its default values. Always copy-paste the class name rather than typing it.
  • Red for PRODUCTION — the colour choice is intentional and important. Authors who accidentally open a production tab alongside a dev tab need an instant visual signal, not a subtle difference. Red creates appropriate caution.
  • AEMaaCS note — on AEM as a Cloud Service, the run modes are author.dev, author.stage, author.prod (combined with tier). Use config.author.dev/, config.author.stage/, and config.author.prod/ as the folder names for AEMaaCS deployments.

📖 Why this code?
  • z-index: 999999 — the AEM page editor uses its own high z-index values for overlays and sidebars (typically in the 9000–90000 range). Using 999999 ensures the banner sits above all AEM chrome. If it ever disappears behind an AEM toolbar, increase this value.
  • Pulsing animation for production — @keyframes academy-pulse creates a subtle heartbeat on the dot. For non-critical environments (local, dev), the animation is disabled — animation: none. For staging and production the pulse draws the eye, reinforcing that this environment requires care. A purely visual choice with a real UX benefit.
  • opacity: 0; transform: translateY(-6px) on the banner — the banner starts invisible and slightly above its final position. When JS adds is-visible, the CSS transition animates it into place. This prevents a flash of unstyled content and gives a polished reveal once the server config is fetched.
  • Minimised state — authors who find the banner distracting can minimise it to a single coloured dot by clicking the × button. The colour still communicates the environment; the text is hidden. The dot is clickable to restore. This respects authors' workflow while maintaining the safety signal.

Step 5 — Banner JavaScript

/apps/academy/clientlibs/env-banner/js/env-banner.js(function () {
  'use strict';

  var ENV_URL       = '/bin/academy/envinfo';
  var STORAGE_KEY   = 'academy.envBannerMinimised';
  var BANNER_ID     = 'academy-env-banner';

  // ── Create and mount the banner element ───────────────────────────────
  function createBanner(label, colour) {
    var existing = document.getElementById(BANNER_ID);
    if (existing) existing.remove();

    var banner = document.createElement('div');
    banner.id            = BANNER_ID;
    banner.className     = 'academy-env-banner';
    banner.style.background = colour;
    banner.setAttribute('data-env', label.toLowerCase());
    banner.setAttribute('role',     'status');
    banner.setAttribute('aria-label', 'Current environment: ' + label);

    // Pulsing dot
    var dot = document.createElement('span');
    dot.className = 'academy-env-banner__dot';

    // Label text
    var text = document.createElement('span');
    text.className   = 'academy-env-banner__text';
    text.textContent = label;

    // Dismiss/minimise button
    var closeBtn = document.createElement('button');
    closeBtn.className   = 'academy-env-banner__close';
    closeBtn.innerHTML   = '×';
    closeBtn.title       = 'Minimise banner';
    closeBtn.setAttribute('aria-label', 'Minimise environment banner');

    banner.appendChild(dot);
    banner.appendChild(text);
    banner.appendChild(closeBtn);
    document.body.appendChild(banner);

    // ── Minimise / restore behaviour ────────────────────────────────────
    var minimised = sessionStorage.getItem(STORAGE_KEY) === 'true';

    function applyMinimisedState() {
      if (minimised) {
        banner.classList.add('is-minimised');
        banner.title = 'Click to restore environment banner (' + label + ')';
      } else {
        banner.classList.remove('is-minimised');
        banner.title = '';
      }
    }

    closeBtn.addEventListener('click', function (e) {
      e.stopPropagation();
      minimised = true;
      sessionStorage.setItem(STORAGE_KEY, 'true');
      applyMinimisedState();
    });

    banner.addEventListener('click', function () {
      if (!minimised) return;
      minimised = false;
      sessionStorage.removeItem(STORAGE_KEY);
      applyMinimisedState();
    });

    applyMinimisedState();

    // Animate in after a brief tick (allows CSS transitions to work)
    requestAnimationFrame(function () {
      requestAnimationFrame(function () {
        banner.classList.add('is-visible');
      });
    });
  }

  // ── Fetch config from the servlet and render ───────────────────────────
  function init() {
    fetch(ENV_URL, { credentials: 'same-origin' })
      .then(function (r) {
        if (!r.ok) throw new Error('HTTP ' + r.status);
        return r.json();
      })
      .then(function (data) {
        if (data.showBanner === false) return; // disabled in OSGi config
        createBanner(data.label || 'Author', data.colour || '#505050');
      })
      .catch(function (err) {
        // Banner is a nice-to-have — never log to console on prod
        // Uncomment the next line during development:
        // console.warn('[Academy EnvBanner] Could not load config:', err);
      });
  }

  // Run after DOM is available
  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', init);
  } else {
    init();
  }

}());
📖 Why this code?

The banner JavaScript is deliberately minimal — fetch config, render DOM, handle two user interactions. It deliberately avoids any framework dependency.

  • sessionStorage.getItem(STORAGE_KEY) — stores the minimised state for the current browser session only. sessionStorage is cleared when the tab closes, so the banner is always fully visible when an author opens a fresh tab. Using localStorage would persist the minimised state across sessions and logins, which could leave authors permanently without the banner — exactly the risk the feature was built to prevent.
  • requestAnimationFrame(function() { requestAnimationFrame(function() { ... }) }) — the double RAF is the canonical trick for triggering CSS transitions on elements added to the DOM. A single RAF fires before the browser has painted the initial state, so the transition has nothing to animate from. Two RAFs guarantee one paint cycle has completed, giving the transition a start state (opacity: 0) to animate from.
  • e.stopPropagation() on the close button — without this, clicking × also fires the banner's own click handler (which would immediately restore the minimised state the × just set). stopPropagation prevents the event from bubbling up from button to banner.
  • Silent catch block — the commented-out console.warn is intentional. On production, logging every failed auth request (if the /bin/academy/envinfo path is blocked by Dispatcher for anonymous users) would pollute the browser console. Enable the log only during development.
  • data.showBanner === false — strict equality check. If the servlet returns anything other than the exact JSON boolean false (including the string "false"), the banner renders. This means a misconfigured or empty response still shows a banner rather than silently hiding it.

📖 Why this code?

Verifying the Servlet endpoints directly with curl before opening the browser is always faster than debugging why a feature doesn't appear visually.

  • If the Servlet returns 404, the @Component(service = Servlet.class) path property is wrong, or the bundle hasn't activated yet. Check /system/console/bundles first.
  • If the Servlet returns 401, the path isn't accessible to the author. Check Dispatcher rules on a non-local environment, or ensure the Sling authenticator doesn't require full admin for this path.
  • If dots don't appear in the UI but the Servlet responds correctly, open Browser DevTools → Network tab and check for the /bin/academy/pagestatus request. If it's not there, the clientlib category is wrong. If it's there but dots are missing, check the Console tab for JavaScript errors.
Try it — test all five status states
  1. Gray dot (Never Published) — create a new page, don't publish it. Open the Sites console. The page should show a gray "Never Published" dot immediately.
  2. Green dot (Activated) — publish the page via Quick Publish. Refresh the Sites console. The dot should change from gray to green within 1–2 seconds (one MutationObserver cycle after the page reloads).
  3. Blue dot (Modified) — open the published page in the editor, change its title, and save without republishing. Go back to Sites console. The dot should change to blue — the live page is now out of date.
  4. Red dot (Deactivated) — right-click the page → Manage Publication → Unpublish. The dot becomes red. This confirms that cq:lastReplicationAction = "Deactivate" is correctly detected.
  5. Legend toggle — click the ● button in the bottom-left of the Sites console. The colour legend should appear with all five status descriptions. Click again to dismiss it.
  6. Environment banner — the blue "Local" pill should be in the top-right of the screen. Click the × to minimise it to a dot. Click the dot to restore it. Open a new tab — the banner should be fully visible again (sessionStorage cleared).
