Dispatcher, Caching & Deployment

Module 1 introduced the dispatcher conceptually. Here's the configuration itself — the rules that decide what gets cached, what's allowed through to AEM at all, and how an authored change actually reaches a visitor's browser.

What you'll learn

  • The shape of a dispatcher farm: cache, rules, filter, invalidate
  • How an authored change becomes a refreshed cache entry
  • The deny-by-default security model behind the filter section
  • Where dispatcher config fits in a release alongside code and content

Anatomy of dispatcher.any

dispatcher.any (sketch)/farms
{
    /academy
    {
        /clientheaders { ... }
        /cache
        {
            /rules      { ... }   # what's cacheable
            /invalidate { ... }   # what gets removed on a flush
        }
        /filter { ... }            # security allow-list
        /statfileslevel "3"
    }
}

Each section has one job: /cache/rules decides what's allowed to be cached at all, /cache/invalidate decides what gets thrown out when content changes, and /filter decides what's allowed to reach AEM in the first place — a security concern, not a caching one.

Caching rules

A typical rule set allows most paths but explicitly denies anything carrying a query string, since query strings usually mean personalized or parameterized output that shouldn't be cached for everyone:

/cache/rules/0001 { /glob "*"   /type "allow" }
/0002 { /glob "*?*" /type "deny"  }

statfileslevel controls how deep the dispatcher checks a folder's .stat file timestamp to decide whether cached content under that path still needs revalidating — it's usually the first thing worth checking when cache invalidation seems to be "not reaching" some nested path.

Invalidation: how a publish actually clears the cache

This closes the loop from module 1's replication explanation: when a page is activated, a flush agent on publish sends an invalidation request to the dispatcher, which deletes the matching cached files so the next visitor regenerates fresh output. /cache/invalidate decides exactly which file types that flush removes — commonly *.html, while leaving heavier assets like images untouched to avoid an expensive mass re-fetch over something that didn't actually change.

The filter: deny by default

/filter is a security allow-list, not a caching decision — every incoming request must match an explicit allow rule or it's rejected before it ever reaches AEM. The standard pattern is deny everything, then allow only the specific extensions, selectors, and paths your application actually serves:

/filter/0001 { /type "deny"  /url "*" }
/0002 { /type "allow" /url "/content/academy/*.html" }
/0003 { /type "allow" /url "/content/academy/*.json" /method "GET" }
Common pitfall A filter copy-pasted from a tutorial without trimming the unused rules is one of the most common findings in an AEM security review. Every selector and extension your application doesn't actually use should be explicitly denied, not just left unmatched at the bottom.

Where this fits in a deployment

A typical release moves up to three independently deployable things: the code package (your bundles), the content package, and the dispatcher configuration — and they don't have to ship together. A dispatcher-only change (tightening a filter rule, adjusting a cache TTL) is lower-risk and faster to roll out than a full code deploy precisely because it doesn't touch the running AEM JVMs at all.

Try it Write a filter rule that allows GET requests to *.json under /content/academy but denies every other selector/extension combination on that path. In one sentence, explain why that's safer than the wide-open, allow-most-things filter many starter projects ship with by default.
