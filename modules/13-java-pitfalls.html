Java Best Practices & Pitfalls

The Java Primer covered the syntax. This module covers the mistakes that compile fine, pass code review on a quick glance, and then surface as a confusing bug three weeks later — the ones experienced AEM developers have usually been bitten by at least once.

What you'll learn

  • Why a broken equals/hashCode pair silently breaks HashSet/HashMap
  • The difference between Comparable and a Comparator, and why they should agree with equals
  • A practical rule of thumb for interfaces vs. abstract classes
  • Stream pitfalls that throw at runtime instead of compile time
  • How to actually attach a debugger to a running AEM instance

Collections: Hash vs. Comparable

A HashSet or HashMap decides where an object lives using its hashCode(), then confirms a match with equals(). If a class overrides one but not the other, both structures break in ways that don't throw an exception — they just quietly stop working correctly:

a broken equals/hashCode pairpublic class Student {
    private final String id;

    public Student(String id) {
        this.id = id;
    }

    @Override
    public boolean equals(Object obj) {
        if (!(obj instanceof Student)) return false;
        return id.equals(((Student) obj).id);
    }
    // no hashCode() override - still uses Object's identity-based hash
}

Set<Student> set = new HashSet<>();
set.add(new Student("s1"));
set.contains(new Student("s1"));  // false! different hash bucket entirely
📖 Why this code?

This code demonstrates a classic Java contract violation — implementing equals() without a matching hashCode().

  • @Override public boolean equals(Object obj) — the Java specification requires that if two objects are equal according to equals(), they must produce the same value from hashCode(). This class breaks that contract.
  • The consequence: a HashSet or HashMap uses hashCode() to decide which bucket to put an object in, then uses equals() to check for exact matches within that bucket. If two equal objects hash to different buckets, they're never compared with equals() — the set thinks they're different even though equals() would say otherwise.
  • The fix: always override both together. Most IDEs generate a correct pair automatically. The Objects.hash(field1, field2, ...) utility method makes it easy.

Two "equal" students end up in different hash buckets, so contains() never even calls equals() to compare them. The rule is absolute: if you override equals(), override hashCode() too, built from the same fields. Most IDEs generate both together for exactly this reason — use that instead of writing either by hand.

Common pitfall Never use a mutable field in hashCode() for an object you intend to store in a HashSet/HashMap key. If that field changes after insertion, the object's hash bucket no longer matches where it was originally stored — contains() and remove() will fail to find it, and it effectively becomes unreachable garbage.

Comparable is a different contract entirely — it defines a natural ordering, used by Collections.sort(), TreeSet, and TreeMap. A Comparator defines an alternative ordering without changing the class itself:

natural order vs. an alternative onepublic class Student implements Comparable<Student> {
    private final String surname;

    @Override
    public int compareTo(Student other) {
        return this.surname.compareTo(other.surname);  // natural order: by surname
    }
}

// elsewhere, an alternative order without touching the class:
students.sort(Comparator.comparing(Student::getFirstName));
📖 Why this code?

Two approaches to ordering — one built into the class, one external and reusable.

  • implements Comparable<Student> — declares a natural order for this class. Collections.sort(), TreeSet, and TreeMap will use compareTo() automatically. Use this for the ordering that makes the most semantic sense for the type.
  • Comparator.comparing(Student::getFirstName) — creates an alternative ordering externally, without modifying the Student class. Use Comparators for secondary sort orders, context-specific orderings, or when you don't control the class.
  • Important: if you use a TreeSet, it uses compareTo() to determine equality (not equals()). Two students with the same surname but different IDs would be considered duplicates by a TreeSet sorted by surname.

If compareTo() returns 0 for two objects that equals() says are not equal, a TreeSet will silently drop one of them — it uses compareTo(), not equals(), to decide what counts as a duplicate. Keep the two consistent unless you have a specific reason not to, and document it loudly if you do.

Interfaces vs. abstract classes

Both let you define a type that multiple classes share, but they answer different questions. An interface says "any of these unrelated classes can do this" — a contract, with no shared state. An abstract class says "these classes are fundamentally the same kind of thing, sharing common state and behavior" — closer to inheritance in the classic sense. A class can implement many interfaces but extend only one class, which is usually the deciding factor in practice.

Mental model In AEM specifically, default to interfaces for Sling Models (you saw why in modules 6 and 12 — composition via @Via only works against an interface boundary) and for OSGi services (modules 4 and 5). Reach for an abstract class only when several implementations genuinely share non-trivial code, not just a shared method signature.

Streams

Streams read well, but a few behaviors surprise developers coming from loops. A stream can only be consumed once:

IllegalStateException: stream has already been operated upon or closedStream<String> names = list.stream();
names.forEach(System.out::println);
names.count();  // throws - the stream was already consumed above
📖 Why this code?

Streams are single-use — this is one of the most surprising behaviors for developers coming from collections.

  • A Java Stream is not a data structure. It's a pipeline of operations applied lazily to a source. Once a terminal operation (forEach, count, collect) consumes the stream, the pipeline is closed and the stream is in a terminal state.
  • Attempting to use a consumed stream throws IllegalStateException: stream has already been operated upon or closed — the error message is clear once you know what to look for.
  • The fix: create a new stream from the source each time: list.stream().forEach(...) and list.stream().count() — two separate stream instantiations from the same List.

A null inside a stream pipeline throws a NullPointerException at the point it's dereferenced, not at the point it entered the stream — which can make the stack trace point somewhere unhelpful. Filter nulls out explicitly rather than assuming a collection has none:

filtering nulls before they cause troublelist.stream()
        .filter(java.util.Objects::nonNull)
        .map(Student::getSurname)
        .collect(java.util.stream.Collectors.toList());
📖 Why this code?

A defensive pattern for Stream pipelines that might encounter null values in the source collection.

  • Objects::nonNull — a method reference to Objects.nonNull(obj), which returns true if the argument is not null. This filter removes any null elements from the stream before they reach map() — where a null would cause a NullPointerException.
  • Always filter nulls at the start of a pipeline, not mid-stream. Filtering early is cleaner and avoids NPEs in map() or sorted() where the error message would be confusing.
  • If null values in the source are a bug rather than expected data, consider using a different approach: fix the null at its source, or use an assertion to fail loudly rather than silently filtering.

And avoid mutating variables outside the stream from inside a lambda — it compiles only for effectively-final locals, but the pattern (a counter, a list being built up by a forEach) is almost always better expressed as a proper collector. If you find yourself reaching for an external mutable variable inside .forEach(), that's usually a sign the logic belongs in .map()/.collect() instead.

Debugging an AEM instance

Set a breakpoint in your IDE as usual, then attach to the running AEM process instead of launching it from the IDE — AEM almost always runs as a separate process started from the command line or a quickstart script. Most AEM start scripts (including the local SDK quickstart) accept debug JVM options via an environment variable or a flag, exposing a standard Java debug port your IDE can attach a remote debugger to.

Once attached, two habits make AEM debugging far less painful: set conditional breakpoints (most IDEs let you right-click a breakpoint and add a condition like city.equals("Lisbon")) instead of stepping through every request to find the one you care about, and break long stream/lambda chains into named, separately-callable methods before debugging them — stepping through an inline lambda chain in a debugger is far harder to follow than stepping through a method with a name.

Common pitfall Reaching for a full IDE remote-debug session for something a log statement would answer in ten seconds. The Felix console's Sling Log Support (/system/console/slinglog) lets you set a package's log level to DEBUG on a running instance with no restart and no redeploy — reach for that first, and reach for the debugger when you genuinely need to inspect live object state.
Try it Take the WeatherModel from module 12, deliberately break its equals/hashCode contract on a small wrapper class around its results, and reproduce the "lost in a HashSet" bug from this module's first example with real output in front of you.
