ACS Commons

By this point you've hand-built a workflow step, a job queue, and a couple of OSGi services. A lot of common variations on exactly that work have already been solved, tested, and packaged — that's what ACS Commons is.

What you'll learn

  • What ACS Commons is and isn't
  • How to deploy it into a project
  • A handful of its most useful features, and when to reach for each

What it is

ACS Commons is a free, open-source collection of AEM utilities, tools, and reusable components maintained by Adobe Consulting Services and the wider AEM community. It isn't a single feature — it's closer to a toolbox of dozens of small, independent additions covering gaps that show up repeatedly across AEM projects: dispatcher cache flushing rules, bulk content workflows, redirect management, and quite a bit more, all of it open source and free to inspect, fork, or read for implementation patterns even if you don't install it directly.

Mental model Before building a custom solution to a problem that feels generic — "I need to bulk-process thousands of pages," "I need a redirect map," "I need to flush the dispatcher cache on a schedule" — check whether ACS Commons already has a maintained, tested answer. It very often does.

Deploying it

Two common approaches, depending on the project. For a quick local trial, download the released content package from the GitHub releases page and install it through Package Manager, the same as the Groovy Console in module 20. For a real project, add it as a proper Maven dependency to your all module so it deploys alongside your own code as part of the standard build, rather than being installed as a separate manual step that's easy to forget when setting up a new environment.

Features worth knowing first

A handful of tools tend to earn their place on almost every project. The Ensure Oak Index framework lets you define custom Oak query indexes as content, deployed and verified the same way as any other package — useful the moment a custom query pattern needs an index that doesn't already exist. Dispatcher Flush Rules give you fine-grained control over what gets invalidated on replication, building directly on the dispatcher concepts from module 19. The Bulk Workflow Manager runs a workflow model (module 17) against thousands of resources matching a query, with throttling and progress tracking built in — exactly the kind of large-scale content operation that's tedious and risky to script by hand. On-Deploy Scripts provide a structured way to run one-time migration code automatically as part of a deployment, a safer and more auditable alternative to running an ad-hoc Groovy Console script (module 20) for anything that needs to happen exactly once per environment. And the Redirect Manager gives content authors a UI for managing URL redirects without needing a developer to hand-edit dispatcher rules for every change.

Try it Install ACS Commons locally, then use the Bulk Workflow Manager to run a simple, harmless workflow model (even just module 17's exercise model) against every page under /content/academy, and compare that experience to hand-writing the same loop in the Groovy Console from module 20.
