Workflow Design & Custom Steps

Module 16 wrote a single custom workflow step. This module fills in everything around it: what a workflow actually is as two separate concepts, how non-developers design one visually, and the practices that keep a custom step from breaking in production.

What you'll learn

  • Workflow model vs. workflow instance — a distinction that explains a lot of confusing behavior if you miss it
  • The ways a workflow gets triggered
  • How the visual workflow editor and its stages fit together
  • The workflow Java API beyond a single step, and how to write one that doesn't break under retries

Model vs. instance

A workflow model is the design — the sequence of steps, stored as content under /var/workflow/models (or /conf/.../workflow/models on more recent AEM versions), edited once and reused many times. A workflow instance is one specific run of that model against one specific payload — created the moment a workflow is triggered, carrying its own state (which step it's on, who it's assigned to, what data it's accumulated) independently of every other instance running the same model. The model is the recipe; the instance is one dish actually being cooked from it.

Mental model If a workflow seems to be "stuck" for one specific page but works for everything else, you're looking at a problem with one instance, not the model — check that page's specific workflow instance state rather than re-checking the model design, which is shared and almost certainly fine.

Triggering workflows

A workflow instance is created in a few standard ways: manually, by an author selecting "Start Workflow" on a page; automatically, via a launcher configured to start a model whenever content matching a path and event type changes (the workflow equivalent of the ResourceChangeListener from module 16, but visually configured rather than coded); or programmatically, by calling the Workflow Java API directly from your own code when a business event happens.

Workflow design: the editor and stages

Authors and architects design workflow models visually in AEM's Workflow Model Editor, dragging steps onto a canvas and connecting them in sequence — no code required for the structure itself. A model is organized into stages (sometimes shown as swimlanes or sections), letting a complex approval process be broken into readable phases like "Draft Review," "Legal Approval," and "Publish" rather than one long flat chain of steps. Standard step types available in the editor include a Participant Step (assigns a task to a person or group and pauses until they act on it), a Dynamic Participant Step (assignee resolved by script), and a Process Step — which runs the custom Java code you write.

Custom workflow: the Java API

A Process Step in the editor maps to a WorkflowProcess implementation — the same interface module 16 introduced. Here's a fuller version showing the parts a single-purpose example skipped: reading metadata passed in from the model, and updating the workflow's own data so a later step can use what this one computed.

/aem-academy/core/src/main/java/biz/netcentric/academy/workflow/AcademyApprovalStep.java (academy.core)package biz.netcentric.academy.workflow;

import com.adobe.granite.workflow.WorkflowException;
import com.adobe.granite.workflow.WorkflowSession;
import com.adobe.granite.workflow.exec.WorkItem;
import com.adobe.granite.workflow.exec.WorkflowProcess;
import com.adobe.granite.workflow.metadata.MetaDataMap;
import org.osgi.service.component.annotations.Component;

@Component(
        service = WorkflowProcess.class,
        property = "process.label=Academy: Approval Check"
)
public class AcademyApprovalStep implements WorkflowProcess {

    @Override
    public void execute(WorkItem workItem, WorkflowSession workflowSession, MetaDataMap args)
            throws WorkflowException {

        String payloadPath = workItem.getWorkflowData().getPayload().toString();
        String requiredRole = args.get("requiredApproverRole", "content-author");

        boolean approved = checkApproval(payloadPath, requiredRole);

        // store a result other steps (or a later "if" branch in the model) can read
        workItem.getWorkflow().getWorkflowData().getMetaDataMap()
                .put("academyApproved", approved);
    }

    private boolean checkApproval(String payloadPath, String requiredRole) {
        // real approval logic goes here
        return true;
    }
}
📖 Why this code?

A more complete workflow step implementation showing how steps read configuration, access the payload, and pass data forward to later steps.

  • args.get("PROCESS_ARGS", String.class) — reads the "Process Arguments" text configured on this step inside the Workflow Model Editor's step dialog. This lets authors parameterize the step without changing code — different workflow models can use the same step class with different arguments.
  • workItem.getWorkflowData().getPayload() — the content path (e.g. a page path) this workflow instance is acting on. Every step in the workflow sees the same payload.
  • workItem.getWorkflow().getWorkflowData().getMetaDataMap().put("approvedBy", ...) — writes a value to the workflow instance's metadata map. Steps further down the workflow can read this value to make routing decisions (e.g. an OR-split that checks if approval was given).
  • The implementation is deliberately idempotent — calling it twice produces the same result as calling it once. AEM can retry failed steps, so non-idempotent steps (like "send email") need extra guards to prevent double execution.

args.get(...) reads metadata configured on the step itself inside the visual editor (an architect can set requiredApproverRole per workflow model without touching code), and writing into getMetaDataMap() is how one step hands data forward to whatever runs after it.

Best practices for custom steps

Make a step idempotent — AEM can retry a failed step, so running execute() twice for the same work item should never cause duplicate side effects (sending two emails, creating two tasks). Throw a WorkflowException deliberately when a step genuinely cannot proceed, rather than swallowing the error — a workflow stuck in an unclear state is far worse to debug than one that visibly failed with a clear reason. And keep a step's actual logic in a separate, unit-testable service (module 14) rather than writing it inline in execute() — the same "thin model, real logic in a service" advice from module 7, applied here.

Try it Build the model in the Workflow Model Editor with a Participant Step followed by AcademyApprovalStep above, set requiredApproverRole on the Process Step's own configuration, and trigger it manually on a test page to confirm the metadata gets written.
