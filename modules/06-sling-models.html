Sling Models

A Sling Model is the glue between a JCR content node and the Java object that a template or servlet actually uses. Without models, your render scripts would be full of messy repository-reading code. With models, the script just calls getTitle() and gets a String.

What you'll learn

  • Why Sling Models exist — the problem they solve
  • The @Model annotation and what "adaptation" means in plain English
  • The five most important injector annotations and exactly when to use each one
  • Required vs. optional injection — and what that silent null from adaptTo() actually means
  • How to derive values with @PostConstruct
  • How to expose a model as JSON without writing any servlet code

The problem without Sling Models

Imagine you have a Teaser content node with a title, a description, and an image. Without a model, an HTL template has to do its own data-fetching:

the old way — reading data directly in a template (messy, untestable)<!-- HTL without a model — the template has to know about ValueMaps,
     child nodes, type casting... this is not the template's job -->
<div>
    <h2>${properties.jcr:title}</h2>
    <p>${properties.description}</p>
</div>
📖 Why this code?

This shows the problem Sling Models solve. Reading properties directly in HTL is not wrong, but it doesn't scale.

  • ${properties.jcr:title} — accesses the properties object that HTL automatically exposes (the node's ValueMap). This works for simple cases but forces the template to know property names, deal with missing values, format types, and contain presentation logic.
  • The comment "this is not the template's job" is the key design principle: templates should only decide what to show and how to lay it out. Deciding what the data is and preparing it is the model's job.
  • This approach also cannot be unit tested — you'd need a running AEM instance to verify it works.

This is fragile. The template has to know property names, deal with type coercions, handle missing values, and truncate long text — all presentation logic tangled up with data access. And none of it is unit-testable.

With a Sling Model, the template becomes clean:

with a model — the template only does presentation<div data-sly-use.teaser="biz.netcentric.academy._05.TeaserModel">
    <h2>${teaser.title}</h2>
    <p>${teaser.shortDescription}</p>
</div>
📖 Why this code?

The clean version — with a Sling Model, the template only makes presentation decisions.

  • data-sly-use.teaser="biz.netcentric.academy._05.TeaserModel" — this single attribute does everything: it calls resource.adaptTo(TeaserModel.class), runs all injection, calls @PostConstruct, and binds the result to the name teaser.
  • ${teaser.title} — calls model.getTitle(). HTL automatically maps property access to getter methods — title maps to getTitle(), shortDescription maps to getShortDescription().
  • The template has no knowledge of the jcr:title property name, the 80-character truncation, or null handling — all of that is encapsulated in the model.

The model handles all the data-reading. The template only handles presentation. This is exactly the same Model-View principle you'd use in any other MVC framework — Sling Models are AEM's "M."

Overview — what is "adaptation"?

The word "adaptation" sounds fancy but it is simple: it is Sling's way of converting one object into another. You already use it — resource.adaptTo(ValueMap.class) converts a Resource into a ValueMap. A Sling Model is simply a custom adaptation target that you define.

adaptation in plain English// "Sling, please take this Resource and give me a TeaserModel from it"
TeaserModel model = resource.adaptTo(TeaserModel.class);

// If everything went well, model is a fully populated TeaserModel object.
// If a required field had nothing to inject, model is null.

// The exact same mechanism, also using adaptTo:
ValueMap props = resource.adaptTo(ValueMap.class);  // built into Sling
Page page = resource.adaptTo(Page.class);           // built into AEM
📖 Why this code?

This code reveals that "adaptation" isn't special Sling Models magic — it's a general Sling mechanism you already use.

  • resource.adaptTo(TeaserModel.class) — calls the same generic adaptation mechanism as resource.adaptTo(ValueMap.class) or resource.adaptTo(Page.class). Sling Models registers an AdapterFactory that intercepts calls where the target type has a @Model annotation.
  • The return value is either a fully populated instance or null — never an exception. null means a required field couldn't be injected. This silent failure is important to understand because it can cause blank rendering with no error in the logs at default log levels.

01 · Sling Models & Adaptation — your first model

Let's build TeaserModel step by step and explain every annotation as we add it:

/aem-academy/core/src/main/java/biz/netcentric/academy/_05/TeaserModel.java (academy.core)package biz.netcentric.academy._05;

import org.apache.sling.api.resource.Resource;
import org.apache.sling.models.annotations.DefaultInjectionStrategy;
import org.apache.sling.models.annotations.Exporter;
import org.apache.sling.models.annotations.Model;
import org.apache.sling.models.annotations.injectorspecific.ChildResource;
import org.apache.sling.models.annotations.injectorspecific.ValueMapValue;
import javax.annotation.PostConstruct;

@Model(
    adaptables            = Resource.class,             // what we adapt FROM
    resourceType          = "academy/components/teaser", // which component uses this
    defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL  // explained below
)
@Exporter(name = "jackson", extensions = "json")        // enables .model.json
public class TeaserModel {

    @ValueMapValue                 // reads the "title" property from the content node
    private String title;

    @ValueMapValue                 // reads "description"
    private String description;

    @ChildResource                 // resolves the "image" child node as a Resource
    private Resource image;

    private String shortDescription;  // derived — not read directly from the node

    @PostConstruct                 // runs AFTER injection is complete
    protected void init() {
        if (description != null && description.length() > 80) {
            shortDescription = description.substring(0, 80).trim() + "…";
        } else {
            shortDescription = description;
        }
    }

    // Getters — what the HTL template calls
    public String getTitle()            { return title; }
    public String getShortDescription() { return shortDescription; }
    public boolean hasImage()           { return image != null; }
}
📖 Why this code?

This is a full working Sling Model. Each annotation does a specific, distinct job — understanding what each one does independently is more useful than memorizing the whole class.

  • @Model(adaptables = Resource.class) — registers this class as an adapter for Resource. Only Resource objects can be adapted to this model; using a SlingHttpServletRequest would fail.
  • resourceType = "academy/components/teaser" — tells AEM which component's content this model belongs to. Not strictly required but enables HTL to find the model automatically by resource type.
  • defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL — makes all fields optional by default. Without this, a missing title property on the content node would cause the entire model to return null.
  • @Exporter(name = "jackson", extensions = "json") — registers a .model.json endpoint for this model using Jackson (a JSON library). Every public getter becomes a JSON field.
  • @ValueMapValue — reads the JCR property whose name matches the Java field name from the content node's ValueMap.
  • @ChildResource — resolves a child node named "image" as a Resource object. If you want to adapt it to another model, change the field type to that model's interface.

02 · Injecting Content into a Model — the injectors explained

Each annotation on a field tells Sling Models exactly where to pull the value from. Here are the five you'll use on almost every model:

@ValueMapValue Reads a property directly off the content node's ValueMap. The field name must match the property name exactly (or you can override with @ValueMapValue(name = "jcr:title")). This is by far the most common injector — use it for any simple title, description, boolean flag, or path.
@ChildResource Resolves a named child node as a Resource object. If the field type is another Sling Model interface, it adapts the child node to that model automatically. Use this when a component stores complex data in a sub-node (like an image or a link target).
@SlingObject Injects a Sling framework object — Resource, ResourceResolver, SlingHttpServletRequest, or SlingHttpServletResponse. Use this when you need to perform repository queries or resolve other resources inside the model.
@Self Injects the adaptable itself, typed as something else. Most commonly used to get another model adapted from the same resource — the foundation for the composition pattern in module 8. Example: @Self private ImageModel imageModel; inside a component that extends Image.
@Default Pairs with another injector to provide a fallback value when the property is missing. Example: @ValueMapValue @Default(values = "Untitled") private String title; — ensures title is never null.

Required vs. optional injection — why adaptTo() returns null

By default every injected field is required. If Sling can't inject a value into a required field, the whole adaptation fails and resource.adaptTo(TeaserModel.class) returns null. Not an exception — just a silent null. This is the most common debugging trap in Sling Models.

required vs optional — the difference matters a lot// REQUIRED (default)
// If "title" property doesn't exist on the node → adaptTo() returns null
@ValueMapValue
private String title;

// OPTIONAL at field level
// If "title" property doesn't exist → field stays null, adaptation succeeds
@ValueMapValue
@Optional
private String title;

// OPTIONAL for the whole class (what TeaserModel uses)
// Every field is optional unless explicitly marked @Required
@Model(defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL)
public class TeaserModel { ... }
📖 Why this code?

The injection strategy choice is a design decision that affects how a model behaves when content is incomplete.

  • REQUIRED (default, no annotation) — a missing property causes the whole model to fail. Use this for fields that are truly mandatory — a model that returns a half-baked object is worse than one that returns null and lets the template handle it cleanly.
  • @Optional on a field — this one field is optional; the model will still return a populated instance even if this property is missing. Use for genuinely optional content like an image or a subtitle.
  • defaultInjectionStrategy = OPTIONAL on the class — all fields are optional unless individually marked @Required. Use this when most fields are optional and you don't want to annotate every single one.
debugging null from adaptTo() When adaptTo() returns null, do this:
  1. Go to /system/console/slinglog in Felix
  2. Set log level DEBUG on logger org.apache.sling.models.impl
  3. Trigger the request again
  4. Read the log — it will tell you exactly which field failed injection and why

@PostConstruct — deriving values after injection

Sometimes you need to calculate something from the injected values — truncate a description, combine first and last name, or check if a date is in the future. @PostConstruct is the method that runs after all injection is complete, so you know every field is already populated.

@PostConstruct is always called after injection — never before@PostConstruct
protected void init() {
    // Safe to use title and description here — they are already injected
    // Never do I/O (HTTP calls, heavy queries) here — module 12 shows why
    this.displayTitle = title != null ? title.toUpperCase() : "No Title";
}
📖 Why this code?

@PostConstruct is the bridge between "data is injected" and "data is ready to use."

  • The method annotated with @PostConstruct is called after every @ValueMapValue, @ChildResource, and @OSGiService field has been populated. Only here are you guaranteed all fields exist.
  • Using it for pure data transformation (truncation, concatenation, type conversion) is correct. Using it for I/O (HTTP calls, database queries) is a mistake — it blocks the render thread on every page load. Module 18 shows the correct pattern for that.
  • The method can be protected void or private void. It doesn't matter what you name it — the annotation is what Sling Models looks for.

Exposing a model as JSON

Adding @Exporter(name = "jackson", extensions = "json") to a model (as TeaserModel has) means any request to the resource with the .model.json selector will return the model's getters as JSON — no servlet required.

the .model.json selector in actionRequest: GET /content/site/page/jcr:content/par/teaser.model.json

Response:
{
    "title": "Welcome to our site",
    "shortDescription": "We help companies achieve their goals through...",
    "hasImage": true
}

Only properties with public getters appear. Private fields are never exposed.
📖 Why this code?

This shows what the @Exporter annotation actually produces — a free JSON API endpoint for any Sling Model resource, with zero additional code.

  • The URL pattern <resource-path>.model.json is registered automatically by the framework when the bundle activates. No servlet registration, no web.xml, no routing config needed.
  • Only methods following the JavaBean getter convention (getXxx() or isXxx() for booleans) are serialized. Private fields are never directly accessible.
  • This is commonly used to feed client-side JavaScript components — the HTML renders a container div and a data-path attribute, and JavaScript fetches .model.json to hydrate it.
Try it Create TeaserModel at the path shown above. Add a Teaser component to a page in AEM, fill in a title and a long description. Then request .model.json on that component's resource path and verify the shortDescription is truncated correctly.
