The Submission Pipeline — what happens after Submit

A form submission is not a single event. It is a pipeline with six stages, each of which can be configured, extended, or broken independently.

end-to-end submission pipeline

Stage 1: Browser-side validation
  Client-side validators fire (Rule Editor rules + Custom Function validators).
  Required field checks run.
  The form does NOT submit if any validator returns an error string.
  ← This is a UX convenience, NOT a security control.

Stage 2: HTTP POST to Publish
  Browser POSTs multipart form data to the Publish instance.
  URL: /content/dam/formsanddocuments/[form-name]/jcr:content?guideContainerPath=...
  Attached files are included in the multipart body.

Stage 3: Server-side validation (ADD THIS — ALWAYS)
  Your submit action (or a sling filter) re-validates the payload.
  Never trust the browser. A determined user can bypass Stage 1 with curl.
  Reject invalid payloads with HTTP 400 before proceeding.

Stage 4: Submit action executes
  GuideSubmitAction.submitAction() runs on Publish.
  This is where your Java code lives:
    → POST JSON to downstream REST API
    → Write to JCR at /content/forms/fp (for workflow review)
    → Invoke FDM write operation
    → Custom logic: call a Sling Job for async heavy processing

Stage 5: Document of Record (DoR) generation
  AEM generates a flat, non-editable PDF of all submitted field values.
  Template: either the form's own XDP template or the auto-generated layout.
  Output: stored to payload path, DAM, or external storage.

Stage 6: Post-submit workflow / notification
  Optional: trigger an AEM Workflow on Author (review & approve).
  Optional: send email confirmation via AEM Mail Service.
  Optional: fire analytics event (tracked separately via Adobe Tags).
📖 Why this code?
  • Stage 3 is not optional. Browser-side validation is a UX improvement, not a security control. A curl command bypasses it entirely. Add server-side validation in your submit action before calling any downstream system.
  • Stage 4 runs on Publish. This surprises developers coming from Sites. The submit action is not a workflow step on Author — it runs on the Publish instance at POST time. Your OSGi service must be deployed and active on Publish.
  • Sling Jobs for heavy work. If Stage 4 calls a slow downstream API (5+ seconds), don't block the HTTP response. Dispatch a Sling Job (module 18) from the submit action, return a success response immediately, and let the job handle the backend call asynchronously. The user sees the thank-you page fast; the integration continues in the background.
  • Stage 6 workflows run on Author. If you trigger an AEM Workflow from a submit action on Publish, the payload must travel via reverse replication to Author before the workflow starts. Configure reverse replication agents — this is often forgotten in new environment setups.

Custom Submit Action — the Java implementation

/aem-academy/core/src/main/java/biz/netcentric/academy/forms/LoanSubmitAction.java

package biz.netcentric.academy.forms;

import com.adobe.aemds.guide.model.GuideSubmitInfo;
import com.adobe.aemds.guide.service.GuideSubmitAction;
import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.api.SlingHttpServletResponse;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Reference;
import java.io.IOException;
import javax.servlet.ServletException;

@Component(
    service   = GuideSubmitAction.class,  // AEM Forms discovers all implementations
    property  = { "guideDataModel=basic" } // "basic" = JSON schema + schema-less forms
)
public class LoanSubmitAction implements GuideSubmitAction {

    @Reference
    private LoanService loanService;   // keep the submit action THIN — delegate here

    @Override
    public String getServiceDescription() {
        return "Submit Loan to Core Banking";  // label in Form Container dialog
    }

    @Override
    public void submitAction(
            SlingHttpServletRequest  request,
            SlingHttpServletResponse response,
            GuideSubmitInfo          submitInfo) throws IOException, ServletException {

        // 1. Get submitted data
        String jsonData = submitInfo.getData();             // submitted form JSON

        // 2. Server-side validation (NEVER skip this)
        if (jsonData == null || jsonData.isEmpty()) {
            response.sendError(400, "Empty submission rejected.");
            return;
        }

        // 3. Delegate to business service — keep action thin and testable
        String applicationRef = loanService.submitApplication(jsonData);

        // 4. Redirect to thank-you page with confirmation reference
        String thankYouPath = submitInfo.getAdaptiveForm().getValueOf("thankYouPage");
        response.sendRedirect(
            request.getContextPath() + thankYouPath + "?ref=" + applicationRef
        );
    }
}
📖 Why this code?
  • @Component(service = GuideSubmitAction.class) — AEM Forms' engine calls bundleContext.getServiceReferences(GuideSubmitAction.class, null) to discover all implementations. Your component appears in the Form Container dialog automatically, labelled by getServiceDescription(). No XML config or registration step.
  • property = "guideDataModel=basic" — restricts this action to JSON schema and schema-less forms. Use "guideDataModel=xsd" for XSD-schema forms, or include both properties for universal compatibility: property = {"guideDataModel=basic", "guideDataModel=xsd"}.
  • Keep the action thin. The submit action is not a service — it is a wiring point. All business logic belongs in LoanService, which is independently testable with JUnit (module 14) without an AEM instance. The submit action is hard to test in isolation.
  • GuideSubmitInfo gives you: getData() (submitted JSON string), getAttachments() (file uploads), getAdaptiveForm() (form configuration, including custom properties you set in the Form Container dialog). Never parse the raw Sling request body — use this API.
  • The Maven dependency (aem-forms-sdk-api) must use <scope>provided</scope>. Bundling it causes class-loading conflicts at runtime because AEM already has it. Symptom: a ClassCastException when AEM tries to call your GuideSubmitAction method.

Document of Record — configuration and gotchas

A Document of Record (DoR) is a flat, archival PDF generated from the submitted form data. It is the digital equivalent of a filed paper form — legal evidence of what was submitted.

DoR configuration on the Form Container — Advanced tab

Document of Record Type
  Auto-generated DoR  → AEM generates a PDF layout from the form structure.
                         No extra template needed. Good for simple forms.
  Template-based DoR  → You supply an XDP (LiveCycle Designer) template.
                         Gives full control over PDF layout, branding, page breaks.

DoR Storage (set in submit action or workflow step)
  Payload-relative path:  ./DoR/output.pdf
    → Stored relative to the submission payload in /content/forms/fp/[submission-uuid]/
    → Default for JCR-stored submissions and workflow-based review flows.

  DAM path:               /content/dam/submissions/[form-name]/[date]/
    → Fixed DAM location; not payload-relative.
    → Good when you need to share the PDF via DAM-based permissions.

  External storage variable:
    → AEM passes the DoR to a custom OSGi service for external storage (S3, SharePoint).
    → The submit action receives the DoR InputStream and handles upload.

COMMON MISTAKE: setting a payload-relative path on a form that uses
"Submit to REST endpoint" — no payload node is created, so the path
resolves to nothing and DoR generation fails silently.
📖 Why this code?
  • DoR generation runs asynchronously from the submit action in most configurations. It does not block the HTTP response. If the DoR appears delayed in your testing, this is expected — it may take a few seconds to appear at the configured path.
  • Payload-relative paths only work when a payload node exists in the JCR — i.e., when the submit action stores the submission as a JCR node. The "Submit to REST endpoint" built-in action does NOT create a payload node. If you use a REST submit action, use a DAM path or external storage for the DoR.
  • XDP-based DoR gives you control over the PDF layout but requires a LiveCycle Designer XDP template. For most new projects, auto-generated DoR is sufficient and avoids the XDP tooling dependency.
  • Store the DoR path configuration in OSGi config per run-mode (config.stage, config.prod), not hardcoded in the form. The storage path for DoRs often differs between Dev/Stage/Prod.

Embedding Forms in AEM Sites

An Adaptive Form has its own URL under /content/dam/formsanddocuments/. Embedding it in a Sites page lets you surface the same form across multiple experiences without duplicating it.

two embedding approaches — choose based on your context

APPROACH 1: Adaptive Form Container component (new form on the Sites page)
  Resource type: core/fd/components/formsportal/embeddedform/v1/embeddedform
  When to use:   The form is the primary purpose of the Sites page.
                 Authors drag the component onto the page, author the form inline.
  CSS:           Form uses the page's theme — no separate form theme needed.
  Client libs:   AEM auto-includes form header/footer client libraries.

APPROACH 2: Adaptive Forms Embed (v2) component (reference an existing form)
  Resource type: core/fd/components/formsportal/embeddedform/v2/embeddedform
  When to use:   Reuse a form that already exists and is managed independently.
                 One campaign form surfaced on three different campaign landing pages.
  Author dialog: Select the form by DAM path (/content/dam/formsanddocuments/...).
  CSS:           Use customheaderlibs.html + customfooterlibs.html to load form deps.

CLIENT LIBRARY SPLIT when embedding in Sites:
  FORM clientlib     → form styling and validation (travels with the form)
    categories: ["your-project.form-theme"]
    Contains: BEM overrides, form-specific CSS

  SITES page clientlib → page chrome, navigation, footer
    Contains: page layout, header styles

  When form is embedded, add form's header/footer libs to Sites page:
  (In your Sites page component's customheaderlibs.html)
    <sly data-sly-call="${clientlib.css @ categories='your-project.form-theme'}" />
    <sly data-sly-call="${clientlib.js @ categories='your-project.form-theme'}" />

MULTIPLE FORMS on one page:
  Supported only if both forms have "Form covers entire width of the frame" checked
  in their embed component dialog. Otherwise CSS conflicts occur.
📖 Why this code?
  • Approach 2 is the power pattern. One enrollment form, authored once in the Forms console, embedded on the campaign landing page, the customer portal, and the mobile app's web view — all pointing at the same DAM path. Update the form once; all three surfaces reflect the change after republish.
  • CSS conflicts are the most common embedding bug. The Sites page's global CSS can override form component styles. The fix: scope your form theme CSS to a form container class — .adaptiveForm { ... } — so it never leaks into the page.
  • customheaderlibs.html and customfooterlibs.html are HTL files in your Sites page component (not the form). They include the form's client library dependencies in the page's <head>. If you skip this step, the embedded form renders without its CSS and JS — fields appear unstyled and rules don't fire.
  • For iFrame embedding (when the hosting app is not AEM — a React SPA, a legacy portal): append ?wcmmode=disabled to the form URL. Without it, the authoring overlay renders and the form is not interactive for end users.

Foundation → Core Components Migration

If you inherit a project running Foundation Components, here is the migration path. There is no automated conversion tool for form content — forms must be rebuilt from scratch on Core Component templates.

Foundation → Core migration — six steps

Step 1: Prerequisites (check these FIRST — nothing else works without them)
  AEM 6.5 LTS with Service Pack 16 (6.5.16.0) minimum.
  Maven AEM Archetype 41+ with Forms options enabled.
  Deploy the all package to ALL author AND publish instances.
  Verify in /system/console/bundles: com.adobe.cq.forms.core-components* = Active

Step 2: Enable Core Components on the AEM instance
  Set up an Archetype 41+ project with aemVersion=6.5.x, includeFormsenrollment=y.
  Enable themes support: add client lib references in customheaderlibs.html of your
  page component (see Embedding section above).
  Align core.forms versions in pom.xml to match your AEM Forms add-on version.

Step 3: Build and deploy
  mvn clean install -P autoInstallPackage
  Output: all/target/[appid].all-[version].zip → installs to author.
  Deploy manually (or via Cloud Manager / package manager) to all publish instances.
  COMMON MISTAKE: deploying only to author. Rules run on publish — must deploy both.

Step 4: Create Core Components templates
  Create new templates using the Adaptive Forms (Core Components) template type.
  Do NOT modify or extend Foundation templates — they are incompatible.
  The Template Editor is at: /conf/[your-config]/settings/wcm/templates/

Step 5: Rebuild forms on Core templates
  Open Forms console → Create → Adaptive Form → select Core Components template.
  Re-author all fields, panels, and rules from scratch.
  There is no migration of field-level rules or custom CSS — manual rebuild only.
  AEM Modernize Tools can assist with some structural migrations but NOT rule logic.

Step 6: Migrate custom code
  Custom scripts (Foundation widget APIs) → rewrite as Custom Functions (module 23).
  CSS/themes → rewrite targeting BEM classes; do not copy Foundation CSS.
  Fragments → rebuild on Core fragments (same DAM path is fine; node structure differs).
  Prefill services → interface is the same (DataXMLProvider); re-test thoroughly.
  Submit actions → interface is the same (GuideSubmitAction); re-test thoroughly.
  THEN run full regression: prefill, all rules, validation, submission, DoR.
📖 Why this code?
  • Step 1 is a hard prerequisite. Core Components simply don't work below SP16. Don't attempt Step 2 without confirming the service pack version in /system/console/bundles.
  • Forms are not convertible field-by-field. Foundation and Core Components use completely different node structures. You cannot move fields between them. Migration is a rebuild. Scope it as a development project, not a configuration task.
  • Custom scripts fail completely after migration. Foundation widget APIs (like guideBridge.getFocus() in the old style) do not exist in Core Components. Inventory every inline script in every Foundation form before starting. Map each one to a Core Components equivalent or Custom Function.
  • CSS cannot be ported directly. Foundation Components emit custom ad-hoc classes. Core Components emit BEM classes like cmp-adaptiveform-textinput__label. Porting means rewriting every selector. Budget time for this — it is always more work than it looks.
  • Fragments must be rebuilt. Foundation fragments and Core fragments have different node structures. The DAM path can stay the same, but the content inside the fragment node must be rebuilt on Core Components.
  • Regression-test the three critical paths: prefill (data flows in on load), all Rule Editor logic (show/hide, compute, validate), and submission (data flows out, DoR generates, thank-you page loads). Any of these can fail silently after migration.
  • Version alignment in pom.xml. core-forms-components-core version in pom.xml must match what your installed AEM Forms add-on provides. A mismatch causes NoClassDefFoundError at runtime. Check the installed version in /system/console/bundles and match it.

Analytics Integration

AEM Forms integrates with Adobe Analytics via Adobe Tags (Launch). Out-of-the-box events cover standard form lifecycle; custom events require Rule Editor wiring.

out-of-the-box analytics events — what you get for free

Event                   What it tracks
──────────────────────  ──────────────────────────────────────────────────
formRendered            Form opened (unique views + return visits)
formSubmit              Successful submission
formError               Client-side validation error triggered
formSave                Draft saved to Forms Portal
formHelp                Help icon clicked on a field
panelVisit              User navigated to a panel (wizard/tab forms)
fieldVisit              User focused a specific field

Reported metrics (in Adobe Analytics Workspace):
  Average fill time · Renditions · Submissions · Drafts · Abandonment rate
  Panel-level drop-off: which panel users abandon most
  Browser / OS / language distribution
  Field-level error counts (which fields cause most validation failures)
📖 Why this code?
  • Panel-level drop-off is the most valuable metric. It tells you exactly which section of a multi-step form users abandon. Combine it with field-level error counts to find the friction points. This data drives UX improvements — reduce abandonment by fixing what the data points at.
  • Analytics requires: an Adobe Analytics license + Adobe Tags (Launch) property + Forms Analytics config in AEM. All three must be in place. The most common reason analytics doesn't fire: the Tags property is configured on the author instance but not published to the publish instance.
custom analytics events — wiring via Rule Editor + Adobe Tags

Step 1: Define a custom event in the Rule Editor
  In Rule Editor on any field or button:
  WHEN [condition] THEN dispatch event "customFormEvent"
  Pass a data payload: { eventName: "formSectionComplete", section: "personalDetails" }

Step 2: Catch the custom event in Adobe Tags (module 25–26)
  Create a Data Element of type "Custom Code":
    return window.adobeDataLayer.getState().customFormEvent;
  Create a Rule triggered by "AEM Forms Event" event type
  Map the Data Element value to an Adobe Analytics eVar or event.

Step 3: Test in Adobe Tags Debug mode
  Load the form with the Tags Debugger enabled.
  Complete the section → verify the custom event fires in the debugger.
  Check the Analytics beacon in the Network tab: s.events should include your event.
📖 Why this code?
  • AEM Forms uses the Adobe Client Data Layer (ACDL) to push events. Adobe Tags listens to the ACDL. This is the same data layer used by AEM Sites Core Components — if the project already uses Sites with Tags, the wiring pattern is identical.
  • Prefer Adobe Launch/Data Collection over the older Cloud framework approach — it supports custom events beyond the OOTB set and integrates with the full Adobe Experience Cloud tag management ecosystem.

Operations & Security — the handover checklist

A form going to production is not just a publish action. It needs access control, data source security, environment configuration, and a handover package.

operations handover checklist — backend developer responsibilities

PERMISSIONS
  Assign to groups, never to individuals (scalable, auditable, revocable).
  Built-in groups to know:
    forms-users       → can view and fill forms (end users on author)
    forms-power-user  → can author forms (Forms Practitioners)
    fd-administrators → admin-level Forms access
  Use Allow over Deny.
  Never add ACLs manually in CRXDE — use the Security UI or Groovy scripts.

DATA SOURCE SECURITY
  Configure each FDM data source with a LEAST-PRIVILEGE account:
    Read-only account for prefill data sources.
    Write account (minimum required permissions) for submit-back sources.
  Credentials are encrypted in Tools → Cloud Services → Data Sources.
  Use run-mode OSGi config for environment-specific credentials (module 5).
  NEVER commit production credentials to Git.

ENVIRONMENT CONFIGURATION
  Rule: deploy the SAME build package Dev → Stage → Prod.
  Environment-specific values (API URLs, analytics property IDs) in OSGi config:
    /apps/your-project/config.dev/       → dev overrides
    /apps/your-project/config.stage/     → stage overrides
    /apps/your-project/config/           → production defaults

HARDENING
  Disable anonymous access to /content/forms/fp (submission data).
  Restrict the Rule Editor Code mode to fd-administrators group only.
  Block /bin/querybuilder.json on the dispatcher (common data leak).
  Restrict /crx/de to author only — never expose CRXDE on publish.

MONITORING
  Watch error.log for GuideSubmitAction exceptions (they don't surface to users).
  Set up JMX monitoring on the Forms submission queue if volume is high.
  Alert on 5xx responses to form submission POST endpoints.

HANDOVER DOCUMENTATION
  Which forms exist → their DAM paths
  Which submit actions → which services they call
  FDM data sources → credentials owner
  Fragments and their forms → update impact map
  Rule Editor custom functions → clientlib path, author, what each does
📖 Why this code?
  • Never expose CRXDE on publish. This is a critical security control. The Dispatcher's allow-list should block /crx/de, /crx/packmgr, and /system/console on publish. These are common attack vectors. The AEM hardening guide from module 19 applies in full to Forms deployments.
  • Restrict Rule Editor Code mode. The Code Editor allows arbitrary JavaScript execution with the form author's session permissions. Granting it to business users is the same as granting them access to run arbitrary JS in the browser context of your forms. Restrict to developers only.
  • GuideSubmitAction exceptions don't surface to end users. A failing submit action logs to error.log on Publish and may redirect to an error page, but gives the user no actionable information. Monitor error.log on Publish for com.adobe.aemds.guide exceptions in production.
  • The handover documentation is not optional. Forms projects frequently outlive the team that built them. The next developer needs to know: which custom functions exist and what they do, which submit actions call which downstream systems, and which fragments are shared between how many forms. Missing this documentation means the next change breaks something unexpected.
Try it — full pipeline smoke test — Deploy a custom submit action that logs the submitted JSON at INFO level: log.info("Submission received: {}", submitInfo.getData()). Deploy it, confirm it is ACTIVE in /system/console/components on the Publish instance (not author). Set this action on an Adaptive Form in the Form Container dialog. Preview the form with ?wcmmode=disabled, fill in all fields, and click Submit. Tail crx-quickstart/logs/error.log on the Publish instance and verify your JSON appears. Then intentionally submit with a required field empty — confirm the log entry does NOT appear (client-side validation blocked it). Then bypass client-side validation with the browser console (document.querySelector('.adaptiveForm').guideContext.submitValue()) and confirm the log DOES appear — proving your server-side validation is the real gate.
