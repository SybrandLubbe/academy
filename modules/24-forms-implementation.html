Implementing Adaptive Forms

AEM Forms is a separate add-on to AEM Sites. This module covers everything a developer needs to ship a form: setting up the Maven dependency, embedding the form in a Sites page, writing a custom submit action, connecting a REST data source, and adding custom validation.

What you'll learn

  • The Maven dependency and scope required for AEM Forms development
  • Two ways to embed a form in an AEM Sites page
  • Writing a custom submit action — full working code
  • Configuring a REST data source and Form Data Model step by step
  • Adding a custom JavaScript validator

Prerequisite: AEM Forms add-on

AEM Forms requires a separate add-on package on your AEM instance, and a Forms API Maven dependency in your project. Check your project lead before starting — it affects licensing and instance setup.

/aem-academy/core/pom.xml — add inside <dependencies> (academy.core)<dependency>
    <groupId>com.adobe.aem</groupId>
    <artifactId>aem-forms-sdk-api</artifactId>
    <version>6.5.14.0</version>
    <scope>provided</scope>         <!-- NEVER bundle — already in AEM -->
</dependency>

<dependency>
    <groupId>com.adobe.aem</groupId>
    <artifactId>core-forms-components-core</artifactId>
    <version>3.0.6</version>
    <scope>provided</scope>
</dependency>
📖 Why this code?

Both use <scope>provided</scope> — compile against them for IDE type info, but exclude from the final bundle.

  • Bundling provided-scope JARs causes class conflicts at runtime because AEM already has them. The build may succeed but AEM will log class-loading errors.
  • The version must match your installed AEM Forms add-on. A mismatch causes NoClassDefFoundError at runtime — check the add-on version in /system/console/bundles.

Embedding a form in a Sites page

option 1 — Adaptive Forms embed component (recommended)Drag the "Adaptive Forms - Embed" component onto your Sites page.
Component resource type:
  core/fd/components/formsportal/embeddedform/v1/embeddedform

The form renders inline in the page DOM — shares the page's CSS and scripts.
Authors choose which form to embed via the component's dialog (DAM path).
📖 Why this code?

The embedded component is the recommended approach — the form shares the page's theme and navigation, and AEM handles all script inclusion.

option 2 — iframe (when the consuming app is not AEM)<iframe
    src="/content/dam/formsanddocuments/loan-application/jcr:content?wcmmode=disabled"
    width="100%" height="600" frameborder="0"
    title="Loan Application Form">
</iframe>
📖 Why this code?

The iframe isolates the form from the parent page — useful when the consumer is a React SPA or external portal that can't use the AEM component.

  • ?wcmmode=disabled — loads the form in publish mode even on the author instance, bypassing the page editor's authoring overlays.
  • Cross-frame communication (e.g. scrolling the parent page on submit) requires JavaScript postMessage — extra work compared to the embedded approach.

Custom submit action

/aem-academy/core/src/main/java/biz/netcentric/academy/forms/LoanSubmitAction.java (academy.core)package biz.netcentric.academy.forms;

import com.adobe.aemds.guide.model.GuideSubmitInfo;
import com.adobe.aemds.guide.service.GuideSubmitAction;
import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.api.SlingHttpServletResponse;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Reference;
import java.io.IOException;
import javax.servlet.ServletException;

@Component(
    service  = GuideSubmitAction.class,    // AEM Forms discovers this automatically
    property = "guideDataModel=basic"      // compatible with JSON schema forms
)
public class LoanSubmitAction implements GuideSubmitAction {

    @Reference
    private LoanService loanService;       // your business logic — keep the action thin

    @Override
    public String getServiceDescription() {
        return "Submit Loan to Core Banking";  // appears in Form Container dialog
    }

    @Override
    public void submitAction(
            SlingHttpServletRequest request,
            SlingHttpServletResponse response,
            GuideSubmitInfo submitInfo) throws IOException, ServletException {

        String jsonData        = submitInfo.getData();
        String applicationRef  = loanService.submitApplication(jsonData);
        String thankYouPage    = submitInfo.getAdaptiveForm().getValueOf("thankYouPage");
        response.sendRedirect(request.getContextPath() + thankYouPage + "?ref=" + applicationRef);
    }
}
📖 Why this code?

A custom submit action is a standard OSGi component — modules 4 and 5 apply. The Forms-specific parts are the interface and the registration property.

  • @Component(service = GuideSubmitAction.class) — registers in the OSGi registry. AEM Forms' engine looks up all active GuideSubmitAction services and lists them in the Form Container dialog by their getServiceDescription() string.
  • property = "guideDataModel=basic" — makes this action available for JSON schema and schema-less forms. Use xsd for XSD-schema forms.
  • GuideSubmitInfo — wraps the current submission: form definition, submitted JSON string, attached files. Never parse the raw request body yourself — use this API.
  • Keep the submit action thin — delegate business logic to loanService. This keeps the action testable and the service reusable.

REST data source — step by step

five steps to connect a REST API to a Form Data ModelStep 1 — prepare a Swagger 2.0 or OpenAPI 3.0 spec for your REST API.
         Upload it to DAM: /content/dam/formsanddocuments/api-specs/customers.yaml

Step 2 — create a Data Source in Tools → Cloud Services → Data Sources
         Type: RESTful Web Service
         Swagger File: /content/dam/.../customers.yaml
         Authentication: Basic / OAuth2 / API Key / None
         Base URL: https://api.mycompany.com/v1

Step 3 — create a Form Data Model in AEM Forms → Data Integrations
         Select data source: CustomerAPI
         Expose operations:
           Read:  GET /customers/{id}   → "Read Customer"
           Write: POST /applications    → "Submit Application"

Step 4 — bind the FDM to your form via Form Container → Data Model tab

Step 5 — bind individual fields to FDM properties via each field's dialog
📖 Why this code?

This is entirely configuration-driven for standard REST integration — no Java code needed.

  • Step 2 stores credentials encrypted in a Cloud Services config node. Use run-mode folders (config.author / config.publish) to point different environments at different API endpoints — the same pattern from module 5.
  • If your API has no Swagger spec, you write a custom Java DataIntegrationService — significantly more work.

Custom JavaScript validator

clientlib validator — category must be "fd.af.validator"// /ui.apps/.../clientlib-validators/js/validators.js
window.guideValidator = window.guideValidator || {};

/**
 * Validates a South African 13-digit ID number (Luhn checksum).
 * Available in the Rule Editor's "Custom Functions" palette.
 */
window.guideValidator.validateSAId = function(value, field) {
    if (!value || value.length !== 13) {
        return "SA ID must be 13 digits";  // string = error message
    }
    var digits = value.split("").map(Number);
    var sum = digits.reduce(function(acc, d, i) {
        return i % 2 === 0 ? acc + d : acc + (d * 2 > 9 ? d * 2 - 9 : d * 2);
    }, 0);
    return (sum % 10 === 0) ? true : "Invalid SA ID — checksum failed";
    //                         ↑ true = valid      ↑ string = error
};
📖 Why this code?

Custom validators are JavaScript functions in a specific clientlib category — discovered automatically by AEM Forms without any additional registration.

  • window.guideValidator — the namespace AEM Forms' Rule Editor scans for custom functions. Any function registered here becomes available as a "Custom Function" in the Rule Editor.
  • Return true for valid input, or a string error message for invalid input. AEM Forms displays the string as the field's validation error. No separate error display code needed.
  • The clientlib must have category "fd.af.validator" — a different category means AEM Forms ignores the file entirely.
Try it — full pipeline
  1. Create a submit action that logs submitted JSON at INFO level: log.info("Submitted: {}", submitInfo.getData()).
  2. Deploy, confirm ACTIVE in /system/console/components.
  3. Set this action on an Adaptive Form, fill it, and submit via preview (?wcmmode=disabled).
  4. Tail crx-quickstart/logs/error.log and verify your JSON appears.
