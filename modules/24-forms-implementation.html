Submission, Embedding & Migration to Core

Forms 22 and 23 covered building. This module covers shipping — writing the custom submit action Java, generating the Document of Record, embedding a form in Sites, migrating a Foundation form to Core, wiring analytics, and hardening the environment for production.

What you'll learn

  • The complete submission pipeline — from browser submit to PDF archive
  • Custom submit actions — the Java interface, registration, and the thin-action pattern
  • Document of Record — what it is, where it's stored, and path configuration gotchas
  • Embedding forms in AEM Sites — two techniques and when to use each
  • Foundation → Core Components migration — six steps with the gotchas that sink projects
  • Analytics integration — out-of-the-box metrics and custom event tracking
  • Operations and security — permissions, least privilege, hardening checklist

The Submission Pipeline — what happens after Submit

end-to-end submission pipeline
Stage 1: Browser-side validation
  Client-side validators fire (Rule Editor rules + Custom Function validators).
  Required field checks run.
  The form does NOT submit if any validator returns an error string.
  ← This is a UX convenience, NOT a security control.

Stage 2: HTTP POST to Publish
  Browser POSTs multipart form data to the Publish instance.
  Attached files are included in the multipart body.

Stage 3: Server-side validation (ADD THIS — ALWAYS)
  Your submit action re-validates the payload.
  Never trust the browser. A determined user can bypass Stage 1 with curl.
  Reject invalid payloads with HTTP 400 before proceeding.

Stage 4: Submit action executes
  GuideSubmitAction.submitAction() runs on Publish.
    → POST JSON to downstream REST API
    → Write to JCR at /content/forms/fp (for workflow review)
    → Invoke FDM write operation
    → Dispatch a Sling Job for async heavy processing (module 18)

Stage 5: Document of Record (DoR) generation
  AEM generates a flat, non-editable PDF of all submitted field values.
  Stored to payload path, DAM, or external storage.

Stage 6: Post-submit workflow / notification
  Optional: trigger an AEM Workflow on Author (review and approve).
  Optional: send email confirmation via AEM Mail Service.
  Optional: fire analytics event via Adobe Tags.
📖 Why this code?
  • Stage 3 is not optional. Browser-side validation is a UX improvement, not a security control. A curl command bypasses it entirely. Add server-side validation in your submit action before calling any downstream system.
  • Stage 4 runs on Publish. Your OSGi service must be deployed and active on Publish — not just author. Check /system/console/components on the Publish instance when debugging.
  • Sling Jobs for slow downstream APIs. If Stage 4 calls an API that takes 5+ seconds, dispatch a Sling Job (module 18) from the submit action, return a success response immediately, and let the job handle the backend call asynchronously. The user sees the thank-you page fast; the integration continues in the background.
  • Stage 6 workflows run on Author. Configure reverse replication agents to get the payload from Publish to Author before the workflow starts — this is often forgotten in new environment setups.

Custom Submit Action — the Java implementation

biz/netcentric/academy/forms/LoanSubmitAction.java
package biz.netcentric.academy.forms;

import com.adobe.aemds.guide.model.GuideSubmitInfo;
import com.adobe.aemds.guide.service.GuideSubmitAction;
import org.apache.sling.api.SlingHttpServletRequest;
import org.apache.sling.api.SlingHttpServletResponse;
import org.osgi.service.component.annotations.Component;
import org.osgi.service.component.annotations.Reference;
import java.io.IOException;
import javax.servlet.ServletException;

@Component(
    service   = GuideSubmitAction.class,   // Forms discovers all implementations
    property  = { "guideDataModel=basic" } // "basic" = JSON schema + schema-less forms
)
public class LoanSubmitAction implements GuideSubmitAction {

    @Reference
    private LoanService loanService;  // keep action THIN — delegate business logic here

    @Override
    public String getServiceDescription() {
        return "Submit Loan to Core Banking";  // label in Form Container dialog
    }

    @Override
    public void submitAction(
            SlingHttpServletRequest  request,
            SlingHttpServletResponse response,
            GuideSubmitInfo          submitInfo) throws IOException, ServletException {

        // 1. Get submitted data
        String jsonData = submitInfo.getData();  // submitted form values as JSON

        // 2. Server-side validation (NEVER skip this)
        if (jsonData == null || jsonData.isEmpty()) {
            response.sendError(400, "Empty submission rejected.");
            return;
        }

        // 3. Delegate to business service
        String applicationRef = loanService.submitApplication(jsonData);

        // 4. Redirect to thank-you page
        String thankYouPath = submitInfo.getAdaptiveForm().getValueOf("thankYouPage");
        response.sendRedirect(
            request.getContextPath() + thankYouPath + "?ref=" + applicationRef
        );
    }
}
📖 Why this code?
  • @Component(service = GuideSubmitAction.class) — AEM Forms discovers all implementations by querying the OSGi registry. Your action appears in the Form Container dialog automatically, labelled by getServiceDescription(). No XML config or registration step.
  • property = "guideDataModel=basic" — restricts visibility to JSON schema and schema-less forms. Use "guideDataModel=xsd" for XSD-schema forms, or include both for universal compatibility.
  • Keep the action thin. The submit action is a wiring point. All business logic belongs in LoanService, which is independently testable with JUnit (module 14) without a running AEM instance. The submit action is hard to unit-test in isolation.
  • GuideSubmitInfo gives you: getData() (submitted JSON string), getAttachments() (file uploads), getAdaptiveForm() (form configuration including custom dialog properties). Never parse the raw Sling request body — use this API.
  • The Maven dependency (aem-forms-sdk-api) must use <scope>provided</scope>. Bundling it causes class-loading conflicts because AEM already has it. Symptom: a ClassCastException when AEM tries to call your method.

Document of Record — configuration and gotchas

DoR configuration on the Form Container — Advanced tab
Document of Record Type
  Auto-generated DoR  → AEM generates a PDF layout from the form structure.
                         No extra template needed. Good for simple forms.
  Template-based DoR  → You supply an XDP template.
                         Full control over PDF layout, branding, page breaks.

DoR Storage (set in submit action or workflow step)
  Payload-relative path:  ./DoR/output.pdf
    → Stored relative to /content/forms/fp/[submission-uuid]/
    → Only works when a payload JCR node exists (e.g. "Store in CRX" action).

  DAM path:               /content/dam/submissions/[form-name]/
    → Fixed DAM location; not payload-relative.
    → Good when sharing the PDF via DAM-based permissions.

  External storage variable:
    → AEM passes the DoR InputStream to a custom OSGi service.
    → The submit action handles upload to S3, SharePoint, etc.

COMMON MISTAKE: setting a payload-relative DoR path on a form that uses
"Submit to REST endpoint" — no payload node is created, so the DoR path
resolves to nothing and generation fails silently.
📖 Why this code?
  • Payload-relative paths only work when a payload node exists. "Submit to REST endpoint" does NOT create a payload node — use a DAM path or external storage for the DoR when using REST submit.
  • DoR generation runs asynchronously from the submit action in most configurations — it does not block the HTTP response. A few seconds delay before the DoR appears at its path is expected.
  • Store DoR path configuration in OSGi run-mode config per environment. The storage path often differs between Dev/Stage/Prod.

Embedding Forms in AEM Sites

two embedding approaches
APPROACH 1: Adaptive Form Container component (new form on the Sites page)
  Resource type: core/fd/components/formsportal/embeddedform/v1/embeddedform
  When to use:   The form is the primary purpose of the Sites page.
                 Authors author the form inline on the page.
  CSS:           Form uses the page's theme.

APPROACH 2: Adaptive Forms Embed (v2) component (reference existing form)
  Resource type: core/fd/components/formsportal/embeddedform/v2/embeddedform
  When to use:   One form surfaced across multiple pages.
                 Author dialog: select form by DAM path.
  Power pattern: loan application form on campaign page + customer portal
                 + branch locator results — all from one DAM node.

CLIENT LIBRARY SPLIT — what goes where:
  FORM clientlib (travels with the form)
    categories: ["your-project.form-theme"]
    Contains: form-specific BEM overrides, form CSS

  SITES page clientlib (stays on the page)
    Contains: page chrome, navigation, footer

  When embedding, include form deps in the Sites page template:
  (customheaderlibs.html of your Sites page component)
    <sly data-sly-call="${clientlib.css @ categories='your-project.form-theme'}" />
    <sly data-sly-call="${clientlib.js  @ categories='your-project.form-theme'}" />
📖 Why this code?
  • Approach 2 is the power pattern. One form, authored once in the Forms console, embedded on multiple pages. Update the form once; all surfaces reflect the change after republish. No duplication.
  • If you omit customheaderlibs.html the embedded form renders without its theme CSS (fields appear unstyled) and without its JavaScript (Rule Editor rules don't fire, submit does nothing). The form is broken for end users even though its HTML appears in the DOM.
  • CSS conflicts are the most common embedding bug. Scope your form theme CSS to the form container class — .adaptiveForm { ... } — so it never leaks into the page's global styles.
  • For iFrame embedding (non-AEM consumer — React SPA, external portal): append ?wcmmode=disabled to the form URL. Without it, the authoring overlay renders and the form is not interactive for end users.

Foundation → Core Components Migration

Foundation → Core migration — six steps
Step 1: Prerequisites (check FIRST — nothing else works without them)
  AEM 6.5 LTS with Service Pack 16 (6.5.16.0) minimum.
  Maven AEM Archetype 41+ with Forms options enabled.
  Deploy the all package to ALL author AND publish instances.
  Verify: /system/console/bundles → com.adobe.cq.forms.core-components* = Active

Step 2: Enable Core Components on the AEM instance
  Set up an Archetype 41+ project with includeFormsenrollment=y.
  Enable themes support: add clientlib references in customheaderlibs.html.
  Align core.forms versions in pom.xml to match your AEM Forms add-on version.

Step 3: Build and deploy
  mvn clean install -P autoInstallPackage
  Deploy to ALL publish instances — not just author.
  COMMON MISTAKE: deploying only to author; rules and submit run on publish.

Step 4: Create Core Components templates
  Create new templates using Adaptive Forms (Core Components) template type.
  Do NOT extend Foundation templates — they are incompatible.

Step 5: Rebuild forms on Core templates
  Open Forms console → Create → Adaptive Form → select Core Components template.
  Re-author all fields, panels, and rules from scratch.
  No migration of field-level rules or custom CSS — manual rebuild only.

Step 6: Migrate custom code
  Custom scripts (Foundation widget APIs) → rewrite as Custom Functions.
  CSS/themes → rewrite targeting BEM classes; do NOT copy Foundation CSS.
  Fragments → rebuild on Core fragments (same DAM path OK; node structure differs).
  Prefill services → DataXMLProvider interface is the same; re-test thoroughly.
  Submit actions → GuideSubmitAction interface is the same; re-test thoroughly.
  Run full regression: prefill, all rules, validation, submission, DoR.
📖 Why this code?
  • Forms are not convertible field-by-field. Foundation and Core Components use completely different JCR node structures. Migration is a rebuild. Scope it as a development project, not a configuration task.
  • Custom scripts fail completely after migration. Foundation widget APIs (guideBridge.getFocus() etc.) do not exist in Core Components. Inventory every inline script in every Foundation form before starting.
  • CSS cannot be ported directly. Foundation Components emit ad-hoc classes. Core Components emit BEM classes like cmp-adaptiveform-textinput__label. Porting means rewriting every selector — always more work than it looks.
  • Version alignment in pom.xml. core-forms-components-core version must match what your installed AEM Forms add-on provides. A mismatch causes NoClassDefFoundError at runtime.
  • Regression-test the three critical paths: prefill (data flows in on load), all Rule Editor logic (show/hide, compute, validate), and submission (data flows out, DoR generates, thank-you page loads). All three can fail silently after migration.

Analytics Integration

out-of-the-box analytics events — what you get for free
Event          What it tracks
───────────    ──────────────────────────────────────────────────
formRendered   Form opened (unique views + return visits)
formSubmit     Successful submission
formError      Client-side validation error triggered
formSave       Draft saved to Forms Portal
formHelp       Help icon clicked on a field
panelVisit     User navigated to a panel (wizard/tab forms)
fieldVisit     User focused a specific field

KEY METRIC: panel-level drop-off (via panelVisit) shows exactly which
step users abandon in a multi-step wizard form.

custom analytics events — wiring via Rule Editor + Adobe Tags
Step 1: Dispatch event in Rule Editor
  WHEN [condition]
  THEN dispatch event "sectionComplete"
  Pass payload: { eventName: "sectionComplete", section: "personalDetails" }

Step 2: Catch in Adobe Tags (module 25-26)
  Data Element type: "Adobe Client Data Layer" → reads from ACDL state
  Rule Event type: "ACDL Event Listener" → listens for "sectionComplete"
  Action: Set Variables (eVar / event) → Send Beacon (s.tl())

Step 3: Verify in AEP Debugger
  Load form → complete the section → check debugger Events tab.
  Confirm the Adobe Analytics beacon contains the mapped variable.
📖 Why this code?
  • AEM Forms uses the Adobe Client Data Layer (ACDL) to push events — the same data layer used by AEM Sites Core Components. If the project already uses Sites with Tags, the wiring pattern is identical.
  • Prefer Adobe Tags / Data Collection over the older AEM Cloud Service framework — it supports custom events beyond the OOTB set and integrates with the full AEP ecosystem.

Operations & Security

production handover checklist — backend developer responsibilities
PERMISSIONS
  Assign to groups, never to individuals.
  Built-in groups:
    forms-users       → view and fill forms (end users on author)
    forms-power-user  → author forms (Forms Practitioners)
    fd-administrators → admin-level Forms access
  Use Allow over Deny. Never add ACLs manually in CRXDE.

DATA SOURCE SECURITY
  Least-privilege account per data source:
    Read-only for prefill sources.
    Minimum write permissions for submit-back sources.
  Credentials encrypted in Tools → Cloud Services → Data Sources.
  Use run-mode OSGi config for environment-specific credentials.
  NEVER commit production credentials to Git.

HARDENING
  Disable anonymous access to /content/forms/fp (submission data).
  Restrict Rule Editor Code mode to fd-administrators group only.
  Block /bin/querybuilder.json on the dispatcher (common data leak).
  Restrict /crx/de to author only — never expose CRXDE on publish.

MONITORING
  Watch error.log on Publish for GuideSubmitAction exceptions
    (they don't surface to end users — they log silently).
  Alert on 5xx responses to form submission POST endpoints.

HANDOVER DOCUMENTATION
  Forms: DAM paths, submit actions, FDM data sources
  Fragments: which forms consume each fragment (update impact map)
  Custom Functions: clientlib path, author, what each does
📖 Why this code?
  • Never expose CRXDE on publish. The Dispatcher allow-list should block /crx/de, /crx/packmgr, and /system/console on publish. The AEM hardening guide from module 19 applies in full to Forms deployments.
  • Restrict Rule Editor Code mode. The Code Editor allows arbitrary JavaScript execution in the form author's session. Granting it to business users is effectively granting them access to run arbitrary JS in the browser context of your forms.
  • GuideSubmitAction exceptions don't surface to end users. A failing submit action logs to error.log on Publish. Monitor it — the user may see an error page while you see nothing in any UI.
  • The handover documentation is not optional. Forms projects outlive the teams that built them. The fragment-to-form impact map is critical — without it, the next developer updating a fragment doesn't know how many forms they're about to break.
Try it — full pipeline smoke test Deploy a custom submit action that logs submitted JSON at INFO level: log.info("Submission: {}", submitInfo.getData()). Confirm it is ACTIVE in /system/console/components on the Publish instance. Set this action on an Adaptive Form, preview with ?wcmmode=disabled, fill all fields, and submit. Tail crx-quickstart/logs/error.log on Publish and verify the JSON appears. Then bypass client-side validation via browser console and submit with a required field empty — confirm your server-side check rejects it with a 400 and the log entry does NOT appear.
