OSGi Services & Configuration

Module 4 covered the basics of services and components. Here's the rest: how to declare exactly what a dependency requires, when a component should start immediately rather than lazily, and how configuration actually gets deployed as part of a real project instead of edited by hand in the Felix console.

What you'll learn

  • Reference cardinality — mandatory, optional, and multiple dependencies
  • What immediate = true changes about a component's lifecycle
  • Why every service should have a separate interface and implementation class
  • Deploying configuration as .cfg.json files instead of hand-editing the console
  • How run-mode-specific configuration folders are resolved

Reference cardinality

Module 4's @Reference examples were all implicitly mandatory — the default. OSGi lets you be explicit about whether a dependency is required, optional, or one of several:

cardinality options// default: exactly one, required - component won't activate without it
@Reference
private GreetingService greetingService;

// zero or one - component activates either way
@Reference(cardinality = ReferenceCardinality.OPTIONAL)
private volatile GreetingService greetingService;

// zero or more, injected as a list
@Reference(cardinality = ReferenceCardinality.MULTIPLE)
private volatile List<GreetingService> greetingServices;

Optional and multiple references need volatile because the set of available services can change at runtime — a dependency can appear or disappear as bundles start and stop, and the field needs to reflect that safely across threads. MANDATORY (the default) is right for something your component genuinely cannot function without; OPTIONAL suits a nice-to-have that degrades gracefully if it's missing.

Immediate components

By default, an OSGi component activates lazily — the first time something actually needs it. That's wrong for a component that has to be running proactively, like a ResourceChangeListener or a scheduled job: nothing ever "calls" a listener to trigger its activation, so without help it might never start at all.

forcing eager activation@Component(
        service = ResourceChangeListener.class,
        immediate = true,
        property = {
                ResourceChangeListener.PATHS + "=/content/academy",
                ResourceChangeListener.CHANGES + "=ADDED"
        }
)
public class AcademyChangeListener implements ResourceChangeListener {
    // ...
}
Mental model If nothing in your code ever calls @Reference to pull a component in, mark it immediate = true — otherwise it may simply never start. Listeners, schedulers, and anything purely reactive almost always need this.

Interfaces and implementation classes

Every service in this curriculum so far has followed the same shape: a plain interface, and a separate @Component-annotated implementation. That's not boilerplate for its own sake — consumers depend on the interface and never reference the implementation class directly, which means the implementation can be swapped (a different provider, a mock for testing in module 14) without touching a single line of consuming code. Skipping the interface and putting @Component straight on a concrete class still works mechanically, but it locks every consumer to that one implementation.

OSGi configuration: Designate, properly

Module 4 introduced @Designate and @ObjectClassDefinition for a configurable service. The piece that was missing is how that configuration gets deployed as part of a real project rather than typed into the Felix console by hand — which doesn't survive a redeploy and isn't checked into source control.

Configuration ships as a .cfg.json file, named after the component's fully-qualified class name (its OSGi PID), placed under ui.config:

/aem-academy/ui.config/src/main/content/jcr_root/apps/academy/osgiconfig/config/biz.netcentric.academy._02.GreetingServiceImpl.cfg.json (academy.ui.config){
    "prefix": "Hello there"
}

This is just JSON matching the property names declared on your @ObjectClassDefinition annotation type — no Java involved, and it deploys as part of the same mvn clean install -PautoInstallSinglePackage you already run for everything else, since ui.config is bundled into the all package alongside core and ui.apps.

Run modes

AEM resolves configuration differently per environment using run modes — labels like author, publish, or custom ones like dev that an instance is started with. A configuration folder can be scoped to one or more run modes by suffixing it:

run-mode-scoped config foldersui.config/src/main/content/jcr_root/apps/academy/osgiconfig/
├── config/                    applies everywhere
├── config.author/              applies only on author instances
├── config.publish/             applies only on publish instances
└── config.author.dev/          applies only on author instances also running the "dev" run mode

At startup, AEM resolves the most specific folder matching the instance's actual active run modes — a value in config.author overrides the same PID's value in config on an author instance, while publish instances never see it at all. This is the standard way to point at a different external API endpoint, log level, or feature flag per environment without branching any code.

Common pitfall Editing a configuration by hand in /system/console/configMgr to "just fix it quickly" on an environment. It works until the next deployment silently overwrites it with whatever's checked into ui.config — if a value needs to be different, it belongs in a run-mode-scoped .cfg.json file, not a manual console edit.
Try it Give one of your own OSGi services an extra configurable property using @Designate — a sensible default, plus a way to override it — then deploy two different values for it via config.author and config.publish and confirm each instance picks up its own value.
