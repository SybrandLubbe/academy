OSGi Services & Configuration

Module 4 gave you the basics. This module fills in the rest: how to handle services that aren't always available, why some components must start immediately, how to structure configuration files correctly, and how run modes let you use different settings on different environments without changing a line of code.

What you'll learn

  • Reference cardinality: what it means for a dependency to be mandatory, optional, or multiple
  • Why some components need immediate = true to ever start at all
  • Why you always separate an interface from its implementation — and what breaks if you don't
  • How to ship configuration as checked-in .cfg.json files instead of hand-editing the console
  • How run-mode folders (config.author, config.publish) give you different settings per environment

Reference cardinality — what happens when a dependency is missing

In module 4, every @Reference was the simplest form: one required dependency. But real projects have three different situations:

the three cardinality options — annotated with when to use each// ── MANDATORY (default) ──────────────────────────────────────────────
// Your component WON'T start unless exactly one matching service is active.
// Use this for: things your code fundamentally cannot function without.
@Reference
private GreetingService greetingService;


// ── OPTIONAL ──────────────────────────────────────────────────────────
// Your component starts whether or not the service is present.
// The field will be null if nothing is registered.
// Must be volatile because OSGi can inject/remove it at any time.
@Reference(cardinality = ReferenceCardinality.OPTIONAL)
private volatile GreetingService greetingService;   ← volatile is REQUIRED


// ── MULTIPLE ──────────────────────────────────────────────────────────
// Collects all registered implementations into a list.
// Great for extension points: any bundle can register a handler.
// Also must be volatile.
@Reference(cardinality = ReferenceCardinality.MULTIPLE)
private volatile List<GreetingService> greetingServices;  ← volatile is REQUIRED
Why volatile? OPTIONAL and MULTIPLE references can change while your component is running — a new bundle might activate (adding a new service) or deactivate (removing one). The volatile keyword tells the JVM: "don't cache this field's value in a CPU register — always re-read it from main memory." Without it, a thread could see a stale null or stale list.

A real example: a pipeline of content processors

Here's a practical use of MULTIPLE cardinality — an extension point where any bundle can register a content processor and the main service automatically discovers all of them:

using MULTIPLE cardinality for a plugin-style extension point// The shared contract
public interface ContentProcessor {
    String process(String input);
}

// Main service: picks up ALL registered ContentProcessors automatically
@Component(service = ContentPipeline.class)
public class ContentPipelineImpl implements ContentPipeline {

    @Reference(cardinality = ReferenceCardinality.MULTIPLE,
               policyOption   = ReferencePolicyOption.GREEDY)
    private volatile List<ContentProcessor> processors;

    public String runAll(String input) {
        String result = input;
        for (ContentProcessor p : processors) {
            result = p.process(result);
        }
        return result;
    }
}

// Any other bundle can add behaviour just by registering this interface:
@Component(service = ContentProcessor.class)
public class SpellCheckProcessor implements ContentProcessor {
    public String process(String input) { /* check spelling */ return input; }
}

Immediate components — the component that nobody calls

By default OSGi is lazy: a component only activates the first time another component asks for its service via @Reference. This is efficient, but it breaks for components that run proactively — things like event listeners and scheduled jobs.

Think about it: if nothing ever calls @Reference ResourceChangeListener, the listener never starts. It can never listen for events it never started for. Nothing works. This is the bug.

immediate = true forces the component to activate on bundle start@Component(
    service   = ResourceChangeListener.class,
    immediate = true,      // ← start immediately, don't wait to be referenced
    property  = {
        ResourceChangeListener.PATHS   + "=/content/academy",
        ResourceChangeListener.CHANGES + "=ADDED",
        ResourceChangeListener.CHANGES + "=CHANGED"
    }
)
public class PageChangeListener implements ResourceChangeListener {

    private static final Logger log = LoggerFactory.getLogger(PageChangeListener.class);

    @Override
    public void onChange(List<ResourceChange> changes) {
        for (ResourceChange change : changes) {
            log.info("Content changed at: {}", change.getPath());
            // trigger re-indexing, send notification, fire a job, etc.
        }
    }
}
Rule of thumb If your component doesn't offer a service that anything else references, add immediate = true. If you forget it, the component appears in /system/console/components as satisfied (all dependencies are met) but it never actually starts — one of the more confusing AEM debugging situations.

Always separate the interface from the implementation

Every service example in this curriculum has two files: a plain interface and a separate @Component-annotated implementation. This feels like extra work. Here is exactly why it matters:

  • Swappability. Any code consuming GreetingService via @Reference never imports GreetingServiceImpl. If you replace the implementation with a completely different class, zero consumer code changes.
  • Testability. In a unit test (module 14) you register a fake GreetingService that returns predictable values. Because consumers only see the interface, the fake works identically to the real implementation from the consumer's perspective.
  • Multiple implementations. You can register two classes against the same interface (one for author, one for publish, say) and use OSGi's service ranking to control which one wins — something impossible if you put @Component on a concrete class with no interface.

Configuration as code: .cfg.json files

The Felix console is handy for experimenting. But any value you change there:

  • Only exists on that one AEM instance
  • Is not checked into version control
  • Will be overwritten the next time someone deploys

The correct approach is to commit your configuration as a .cfg.json file inside ui.config. The naming convention is the component's fully-qualified class name (its OSGi PID):

/aem-academy/ui.config/src/main/content/jcr_root/apps/academy/osgiconfig/config/biz.netcentric.academy.osgiexample.GreetingServiceImpl.cfg.json (academy.ui.config){
    "prefix": "Hello there"
}

The key names in the JSON match the method names on your @ObjectClassDefinition annotation type. The file deploys as part of the normal mvn clean install -PautoInstallSinglePackage build because ui.config is bundled into the all package alongside everything else.

how to find the correct PID if you're unsure1. Deploy your service (the one with @Designate)
2. Open /system/console/configMgr
3. Find your service by its @ObjectClassDefinition name attribute
4. The PID is shown in brackets next to the name — that's your filename.

Run modes: different settings per environment

Every AEM instance starts with one or more run modes — labels that describe what kind of instance it is. The standard ones are author and publish, but you can add custom ones like dev or staging.

Configuration folders inside ui.config can be scoped to run modes by using a special naming convention:

run-mode-scoped config folder structureui.config/src/main/content/jcr_root/apps/academy/osgiconfig/
│
├── config/                         ← applies on ALL instances
│   └── biz.netcentric...Impl.cfg.json   (e.g. prefix = "Hello")
│
├── config.author/                  ← applies ONLY on author instances
│   └── biz.netcentric...Impl.cfg.json   (e.g. prefix = "Author Hello")
│
├── config.publish/                 ← applies ONLY on publish instances
│   └── biz.netcentric...Impl.cfg.json   (e.g. prefix = "Publish Hello")
│
└── config.author.dev/              ← applies ONLY on author + dev run mode
    └── biz.netcentric...Impl.cfg.json   (e.g. prefix = "Dev Hello")

At startup, AEM picks the most specific folder that matches the instance's active run modes. An author instance running in dev mode will prefer config.author.dev over config.author over config.

Real-world use cases for run modes
  • Point at a local mock API on dev, a staging API on QA, a real API on production — same code, different apiUrl property
  • Enable verbose logging on author, suppress it on publish
  • Disable certain features (like sending real emails) on non-production environments
Common pitfall A value edited in /system/console/configMgr on one environment "just to fix it quickly" will be silently overwritten the next time a deployment runs. If a value needs to be different per environment, it belongs in a run-mode folder in ui.config — full stop.
Try it — configuration that changes per environment
  1. Add a second property String apiEndpoint() default "https://api.example.com"; to GreetingConfig.
  2. Read it in GreetingServiceImpl.activate() and log the value.
  3. Create config/biz...GreetingServiceImpl.cfg.json with "apiEndpoint": "https://api.example.com".
  4. Create config.author/biz...GreetingServiceImpl.cfg.json with "apiEndpoint": "https://author-api.example.com".
  5. Deploy and check the log output. Then check /system/console/configMgr to confirm which value is active.
