Extending Core Component Models

You'll lean on @Via(type = ResourceSuperType.class) heavily once you start extending Core Components yourself — module 12's Image and Weather components both use it. Here's the full pattern first, and why reusing a Core Component's model is almost always better than writing your own from nothing.

What you'll learn

  • Why extending a Core Component's model beats reimplementing it
  • The full @Via(type = ResourceSuperType.class) composition pattern
  • Composing by wrapping vs. composing by interface inheritance
  • What a project needs in its pom.xml before unit tests will run at all

Why reuse, not rewrite

The Core Components ship with accessibility markup, responsive image handling, edit-mode placeholders, and dialog UX that took the Core Components team years to refine. Reimplementing an Image or Teaser component from a blank HTL file throws all of that away to rebuild a worse version of it. The alternative — point resourceSuperType at the core component, and your component inherits its dialog and rendering unless you explicitly override a piece of it — is exactly what module 12 puts to work on a real Image component.

The composition pattern, in full

@Via(type = ResourceSuperType.class) tells Sling Models: "before injecting into me, first adapt this same resource to whatever model my resourceSuperType registers, and give me that object." It's the model-layer equivalent of the resourceType inheritance module 3 covered for render scripts:

composing over the core Teaser modelpackage biz.netcentric.academy.components.teaser;

import com.adobe.cq.wcm.core.components.models.Teaser;
import org.apache.sling.api.resource.Resource;
import org.apache.sling.models.annotations.DefaultInjectionStrategy;
import org.apache.sling.models.annotations.Model;
import org.apache.sling.models.annotations.injectorspecific.Self;
import org.apache.sling.models.annotations.injectorspecific.ValueMapValue;
import org.apache.sling.models.annotations.via.ResourceSuperType;
import org.apache.sling.models.annotations.via.Via;

@Model(
        adaptables = Resource.class,
        resourceType = "academy/components/teaser",
        defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL
)
public class AcademyTeaserModel {

    @Self
    @Via(type = ResourceSuperType.class)
    private Teaser coreTeaser;

    @ValueMapValue
    private String badgeLabel;  // a field the core Teaser doesn't have

    public String getTitle() {
        return coreTeaser.getTitle();
    }

    public String getLinkURL() {
        return coreTeaser.getLinkURL();
    }

    public String getBadgeLabel() {
        return badgeLabel;
    }
}

coreTeaser is a fully populated instance of the Core Components' own Teaser model — every field it already knows how to compute (title fallback logic, link resolution, image handling) is available immediately, without reimplementing any of it. Your model only adds what's actually new: badgeLabel here, asset metadata in module 12's image example.

Mental model Treat @Self @Via(type = ResourceSuperType.class) as "give me my parent's fully-built model, the same way resourceSuperType gives a render script its parent's script when one isn't overridden." Both are the same inheritance idea, applied at two different layers.

Two ways to compose

The example above wraps the core model — your class has a private field holding it, and exposes its own getters that may or may not delegate straight through. The alternative is to have your model's interface extend the core component's interface directly, inheriting its method signatures rather than re-declaring them:

composing by interface inheritancepublic interface AcademyTeaser extends Teaser {
    String getBadgeLabel();
}

Wrapping (the first example) gives you more control — you can change what a getter returns, add validation, or omit a method from the core model entirely. Interface inheritance is more honest about the relationship when your component is genuinely "a Teaser, plus one more field" with no overridden behavior. Reach for wrapping by default; reach for interface inheritance when you're confident you'll never want to diverge from the parent's behavior.

Setting up for unit testing

Module 14 covers unit testing properly, but composed models like this one are exactly where tests earn their keep — you want confidence that badgeLabel renders correctly without manually deploying to localhost:4502 every time. Before any test will run, core/pom.xml needs the testing dependencies on the test classpath:

core/pom.xml (inside <dependencies>)<dependency>
    <groupId>io.wcm</groupId>
    <artifactId>io.wcm.testing.aem-mock.junit5</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-core</artifactId>
    <scope>test</scope>
</dependency>

If your project was generated from the standard AEM Project Archetype, both are very likely already there — check before adding them again. Test classes themselves live in a parallel folder to your main source, under src/test/java instead of src/main/java, mirroring the same package structure. Module 14 picks up exactly here.

Try it Build the AcademyTeaserModel above as a real component (component definition, no dialog needed since it inherits the core Teaser's), deploy it, and confirm getTitle() and getLinkURL() behave identically to a plain core Teaser placed on the same page.
