Testing 40 min · hands-on

Unit Testing

Every exercise so far has been verified by deploying to localhost:4502 and clicking around or running curl. That's the right way to confirm a feature works end to end — it's the wrong way to confirm a single piece of logic keeps working six months from now. This module covers the actual tools.

What you'll learn

  • Why a slow, manual AEM redeploy isn't the right feedback loop for testing logic
  • JUnit 5 assertions, and testing multiple cases with parameterized tests
  • Mocking a dependency with Mockito
  • Using AemContext to test code that touches Resource or OSGi services, with no running AEM instance at all

Why unit testing, specifically here

A unit test runs in milliseconds, in your IDE or CI pipeline, with no AEM instance required. Build/deploy/curl confirms the whole system works together — valuable, but slow, and it tests far more than the one piece of logic you actually changed. The two aren't competing; a healthy AEM project has both, but most of your fast, everyday feedback should come from unit tests, not redeploys.

JUnit 5: assertions and test cases

Take the validation rule from the Java Primer's ValidationServlet (module 00, exercise 4) and pull it out into its own pure function — extracting logic like this out of a servlet and into a plain class is, on its own, the single biggest thing you can do to make code testable:

/aem-academy/core/src/main/java/biz/netcentric/academy/_04/UsernameValidator.java (academy.core)package biz.netcentric.academy._04;

public final class UsernameValidator {

    private UsernameValidator() {
    }

    public static boolean isValid(String username) {
        if (username == null || username.isBlank()) {
            return false;
        }
        return !"admin".equalsIgnoreCase(username);
    }
}
📖 Why this code?

UsernameValidator is designed to be testable — it's a pure function with no dependencies on AEM or OSGi.

  • public final class — declaring the class final prevents subclassing, which is appropriate for a utility class with only static methods. It signals that this class is not designed to be extended.
  • private UsernameValidator() — a private constructor prevents instantiation. This is the standard pattern for utility classes that only contain static methods — you call UsernameValidator.isValid(name), not new UsernameValidator().isValid(name).
  • !"admin".equalsIgnoreCase(username) — calling equals on the string literal rather than the variable protects against NullPointerException. "admin".equalsIgnoreCase(null) returns false safely; username.equalsIgnoreCase("admin") would throw NPE if username is null.

Test classes live in a parallel src/test/java folder, mirroring the same package:

/aem-academy/core/src/test/java/biz/netcentric/academy/_04/UsernameValidatorTest.java (academy.core)package biz.netcentric.academy._04;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

class UsernameValidatorTest {

    @Test
    void rejectsNullAndBlank() {
        assertFalse(UsernameValidator.isValid(null));
        assertFalse(UsernameValidator.isValid(""));
        assertFalse(UsernameValidator.isValid("   "));
    }

    @ParameterizedTest
    @CsvSource({
            "jdoe, true",
            "admin, false",
            "ADMIN, false"
    })
    void validatesAgainstReservedNames(String username, boolean expectedValid) {
        assertTrue(UsernameValidator.isValid(username) == expectedValid);
    }
}
📖 Why this code?

This test class demonstrates two testing patterns: a basic @Test and the far more powerful @ParameterizedTest.

  • @ParameterizedTest with @CsvSource — runs the same test method multiple times, once per row of CSV data. Each row provides different input and expected output. This gives you 5 test cases in the space of one method — much cleaner than writing 5 near-identical @Test methods.
  • The CSV format: each string is one row, comma-separated values map to method parameters in order. "null" is automatically converted to Java null by JUnit.
  • assertFalse / assertTrue — JUnit assertion methods. They fail the test if the condition isn't met, with a descriptive failure message. Never use if (!condition) throw ... — use assertion methods so the test framework can report results correctly.

@ParameterizedTest with @CsvSource runs the same test body once per row — covering "a normal name," "the reserved name," and "the reserved name in different casing" without three near-identical test methods. Run these with mvn test from the core module, or directly from your IDE's test runner — no AEM instance involved at all.

Mockito: testing against a mocked dependency

Mockito creates a fake implementation of an interface you can program and inspect, useful whenever a class depends on a service rather than calling a static method:

/aem-academy/core/src/test/java/biz/netcentric/academy/_02/GreetingServiceMockTest.java (academy.core)package biz.netcentric.academy._02;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class GreetingServiceMockTest {

    @Mock
    private GreetingService greetingService;

    @Test
    void mockReturnsConfiguredValue() {
        when(greetingService.greet("Maria")).thenReturn("Hello, Maria!");

        String result = greetingService.greet("Maria");

        assertEquals("Hello, Maria!", result);
        verify(greetingService).greet("Maria");
    }
}
📖 Why this code?

A Mockito test that verifies service behavior without any AEM infrastructure — the fastest kind of test to write and run.

  • @ExtendWith(MockitoExtension.class) — activates Mockito's JUnit 5 integration. This processes @Mock and @InjectMocks annotations automatically before each test.
  • @Mock private GreetingService greetingService — creates a fake implementation of GreetingService. By default, all methods return zero-values (null, 0, false). This only works because GreetingService is an interface — another reason the interface/implementation split is essential.
  • when(greetingService.greet("world")).thenReturn("Hello, world!") — programs the mock to return a specific value for a specific input. Tests stay deterministic and don't depend on real implementation logic.
  • verify(greetingService).greet("world") — asserts that the mock's greet method was called exactly once with the argument "world". This verifies interaction, not just return values.

when(...).thenReturn(...) programs the mock's behavior; verify(...) confirms a method was actually called, which matters when you're testing that a consumer used a dependency correctly rather than testing the dependency's own return value.

AEM Mocks: testing against Resource and OSGi services

Plain Mockito can't help once your code touches a Resource, a ResourceResolver, or relies on real OSGi service injection — those need AemContext from the io.wcm.testing.aem-mock library, a lightweight in-memory simulation of an AEM repository and OSGi runtime.

Mocking resources

Test module 00's ChildPagesModel (exercise 5) by building a small content tree in memory and adapting straight to the model — no localhost:4502 required:

/aem-academy/core/src/test/java/biz/netcentric/academy/_05/ChildPagesModelTest.java (academy.core)package biz.netcentric.academy._05;

import io.wcm.testing.mock.aem.junit5.AemContext;
import io.wcm.testing.mock.aem.junit5.AemContextExtension;
import org.apache.sling.api.resource.Resource;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

import java.util.List;

import static org.junit.jupiter.api.Assertions.assertEquals;

@ExtendWith(AemContextExtension.class)
class ChildPagesModelTest {

    private final AemContext context = new AemContext();
    private Resource pageResource;

    @BeforeEach
    void setUp() {
        context.addModelsForClasses(ChildPagesModel.class);

        pageResource = context.create().resource("/content/academy/page",
                "sling:resourceType", "academy/components/page");

        Resource childB = context.create().resource("/content/academy/page/child-b");
        context.create().resource(childB.getPath() + "/jcr:content", "jcr:title", "Banana Page");

        Resource childA = context.create().resource("/content/academy/page/child-a");
        context.create().resource(childA.getPath() + "/jcr:content", "jcr:title", "Apple Page");
    }

    @Test
    void returnsChildTitlesSortedAlphabetically() {
        ChildPagesModel model = pageResource.adaptTo(ChildPagesModel.class);

        List<String> titles = model.getChildPageTitles();

        assertEquals(List.of("Apple Page", "Banana Page"), titles);
    }
}
📖 Why this code?

An AEM Mocks test for a Sling Model — the step up from plain Mockito when your code actually touches Resources and the Sling APIs.

  • AemContext context = new AemContext() — creates an in-memory Sling + AEM environment with a real ResourceResolver, real Sling Models injection machinery, and real OSGi service registry. No AEM server required.
  • context.addModelsForClasses(ChildPagesModel.class) — registers the model with the mock Sling Models framework. Without this, adaptTo() returns null even with a valid resource.
  • context.create().resource("/content/academy", ...) — creates in-memory JCR nodes with the specified properties. This is the content that @ValueMapValue will read when the model is adapted.
  • resource.adaptTo(ChildPagesModel.class) — runs through the complete real Sling Models injection process against the in-memory content. If it returns null, the test setup is wrong — not the model logic.

context.addModelsForClasses(...) is the line easiest to forget — without it, AemContext has no idea your @Model class exists, and adaptTo() silently returns null, the same failure mode module 6's pitfall callout warned about.

Mocking services

The same AemContext can register fake OSGi services and inject them into a real servlet via @Reference, letting you test module 00's GreetingServlet end to end without AEM:

/aem-academy/core/src/test/java/biz/netcentric/academy/_02/GreetingServletTest.java (academy.core)package biz.netcentric.academy._02;

import io.wcm.testing.mock.aem.junit5.AemContext;
import io.wcm.testing.mock.aem.junit5.AemContextExtension;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

import javax.servlet.ServletException;
import java.io.IOException;

import static org.junit.jupiter.api.Assertions.assertEquals;

@ExtendWith(AemContextExtension.class)
class GreetingServletTest {

    private final AemContext context = new AemContext();

    @Test
    void respondsWithGreeting() throws ServletException, IOException {
        context.registerService(GreetingService.class, name -> "Hello, " + name + "!");

        GreetingServlet servlet = new GreetingServlet();
        context.registerInjectActivateService(servlet);

        context.request().addRequestParameter("name", "Maria");
        servlet.doGet(context.request(), context.response());

        assertEquals("Hello, Maria!", context.response().getOutputAsString());
    }
}
📖 Why this code?

Testing a servlet with OSGi service injection — combining AemContext with Mockito for a full integration-style unit test.

  • context.registerService(GreetingService.class, mockGreetingService) — registers the Mockito mock in the in-memory OSGi service registry. When the test calls context.registerInjectActivateService(servlet), the framework injects this mock into the servlet's @Reference GreetingService field.
  • context.registerInjectActivateService(servlet) — the equivalent of deploying to AEM. It processes all @Reference fields on the servlet using the registered mock services, then calls any @Activate method.
  • This test proves the full chain works: the servlet activates, injects the service, calls it with the right argument, and writes the expected response.

context.registerService(...) puts a fake implementation in the mock OSGi registry; context.registerInjectActivateService(servlet) then performs real field injection on the servlet's @Reference field, exactly as the real OSGi runtime would. This is the same reason module 7 recommended interface-based services and models — without the GreetingService interface, none of this would be mockable at all.

Best practices

Test your own logic, not the framework underneath it — there's no value in a test that only confirms ValueMap.get() works. Keep each test focused on one behavior, named so the failure message tells you what broke without opening the test body. And prefer the plain Mockito test (fast, no AemContext setup) whenever your code doesn't actually touch Resource or OSGi — reach for AemContext only when you genuinely need it.
