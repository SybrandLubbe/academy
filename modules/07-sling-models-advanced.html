Sling Models In Depth

Module 6 gave you a working model. This module explains why it works, fills in the parts that trip people up in real projects, and builds good habits that make your models testable and maintainable as they grow.

What you'll learn

  • What "adaptation" is actually doing under the hood — no more magic
  • The real decision rule for Resource vs. SlingHttpServletRequest as adaptable
  • Constructor injection vs. field injection — and why constructor injection often wins
  • Interface-based vs. class-based models — and when to use each
  • How a model is deployed (there is no manual registration step)
  • How a model uses an OSGi service via @OSGiService
  • How configuration reaches a model without it ever being an OSGi component
  • Six practices that keep models maintainable long-term

03 · Adaptables — what actually happens when you call adaptTo()

In module 6 you called resource.adaptTo(TeaserModel.class) and got a populated model back. What actually happened? Let's trace it step by step:

what happens inside adaptTo() — the full sequence1. resource.adaptTo(TeaserModel.class) is called.

2. Sling checks its registry of AdapterFactories — OSGi services
   that know how to convert one type to another.

3. The Sling Models AdapterFactory is registered for this purpose.
   It intercepts the call, reads TeaserModel.class.

4. It scans TeaserModel for the @Model annotation.
   It checks: does Resource.class match one of the declared adaptables?
   → Yes.

5. It creates a new TeaserModel instance (using the default constructor
   or the @Inject constructor if you use constructor injection).

6. It processes every @ValueMapValue, @ChildResource, @SlingObject field,
   running the appropriate injector for each.

7. After all injection: it calls the @PostConstruct method.

8. It returns the populated instance, or null if any required field
   couldn't be filled.
📖 Why this code?

This sequence removes the mystery from adaptTo(). Every step in this chain is a standard OSGi mechanism — not framework magic.

  • Step 2 — AdapterFactories: the OSGi service registry contains "adapter factories" — services that know how to convert one type into another. resource.adaptTo(ValueMap.class) uses a different factory than resource.adaptTo(TeaserModel.class) — both use the same lookup mechanism.
  • Step 4 — @Model annotation scan: the Sling Models AdapterFactory reads your class's @Model annotation to verify the source type matches and to find the injection metadata.
  • Step 8 — null return: the factory never throws an exception for a failed injection. It returns null, which is why null-checking the result of adaptTo() is always required in production code.

The takeaway: adaptTo() is not magic. It is a lookup in the OSGi service registry, the same registry you learned about in module 4. There is nothing special about Sling Models — they use the same wiring mechanism as everything else in AEM.

Resource vs. SlingHttpServletRequest as adaptable

Your @Model annotation has an adaptables attribute that declares what you can adapt from. The two most common options are Resource.class and SlingHttpServletRequest.class. Getting this wrong is a very common source of confusing null values.

Resource.class — use this by default Resource.class works anywhere you have a Resource:
  • During a normal HTTP request (via HTL's data-sly-use)
  • From inside another model (via @Self or @ChildResource)
  • From a servlet
  • From a background job or workflow step
  • From a unit test, with no HTTP request at all
SlingHttpServletRequest.class — only when you need request-specific data Use this only when you specifically need something that doesn't exist on a bare Resource:
  • URL selectors (request.getRequestPathInfo().getSelectorString())
  • Query parameters (request.getParameter("q"))
  • Request attributes set by a filter
  • The current user's session
why defaulting to SlingHttpServletRequest breaks things// BAD — declared as Request adaptable out of habit
@Model(adaptables = SlingHttpServletRequest.class)
public class ProductModel { ... }

// This works fine from a servlet or HTL:
ProductModel m = request.adaptTo(ProductModel.class);  ✓

// But this FAILS silently — no request exists here:
@ChildResource
private ProductModel relatedProduct;   // ← adaptTo fails, field is null

// Or from inside another model via @Self:
@Self
private ProductModel productModel;  // ← null! No request available.

// Always ask: "Do I actually NEED request data?"
// If not → use Resource.class
📖 Why this code?

This code shows the most common Sling Models mistake and exactly why it fails. The comments in the code are the explanation — read them carefully.

  • When @ChildResource tries to adapt a child node to ProductModel, it calls childResource.adaptTo(ProductModel.class). It passes a Resource object, not a SlingHttpServletRequest. But the model declared it only accepts SlingHttpServletRequest — so the AdapterFactory refuses and returns null.
  • No error is logged at default log levels. The field is silently null. This can take hours to debug without knowing to check the adaptables declaration.
  • The fix is always the same: use adaptables = Resource.class unless you genuinely need a request-specific value.

Constructor injection vs. field injection

In module 6, all injection happened through fields annotated with @ValueMapValue, etc. Sling Models also supports injecting through the constructor, which many teams now prefer. Here is the same model both ways so you can compare:

field injection — the approach from module 6@Model(adaptables = Resource.class)
public class ProductModel {

    @ValueMapValue
    private String name;

    @ValueMapValue
    private double price;

    private String displayPrice;

    @PostConstruct
    protected void init() {
        // fields are populated here
        this.displayPrice = String.format("€%.2f", price);
    }

    public String getDisplayPrice() { return displayPrice; }
}
📖 Why this code?

Field injection is the most common style you'll see in existing AEM codebases. It's familiar but has a subtle limitation.

  • @ValueMapValue private String name — Sling Models sets this field using reflection after the object is constructed. The field cannot be final because Sling needs to write to it post-construction.
  • @PostConstruct is necessary because the field values don't exist yet when the constructor runs — displayPrice must be built after price is already injected.
  • There is a brief window between construction and the @PostConstruct call where fields like name and price are their Java defaults (null/0.0). This window creates risk if the model is ever used before @PostConstruct completes.
constructor injection — same model, different style@Model(adaptables = Resource.class)
public class ProductModel {

    private final String displayPrice;   // ← can be final now!

    @Inject   // ← Sling calls this constructor and injects the annotated params
    public ProductModel(
        @ValueMapValue String name,
        @ValueMapValue double price
    ) {
        // derivation happens right here in the constructor
        this.displayPrice = String.format("€%.2f", price);
    }

    public String getDisplayPrice() { return displayPrice; }
}
📖 Why this code?

Constructor injection eliminates the "injected-after-construction" window and makes fields immutable.

  • @Inject on the constructor — tells Sling Models to use this constructor rather than the no-arg default. Sling reads the parameter annotations and injects each value before calling the constructor body.
  • private final String displayPrice — the field is final because it's assigned exactly once, in the constructor, and never changed afterward. Final fields are inherently thread-safe and prevent accidental mutation.
  • No @PostConstruct needed — the derivation logic (String.format) happens inside the constructor, where both name and price are guaranteed to be available as parameters.
  • Unit testing benefit: you can write new ProductModel("Widget", 9.99) directly in a test without any Sling Models infrastructure.

Constructor injection has a clear advantage: fields become final. A final field can only be set once — in the constructor — so the model is fully valid the instant it exists. There is no window where a field is null before @PostConstruct runs. It is also much easier to unit test (module 14) because you can just call new ProductModel("Widget", 9.99) directly without needing Sling's injection machinery at all.

Interface-based vs. class-based models

So far you've put @Model directly on a class. You can also split the model into an interface plus an implementation — the same "interface over implementation" pattern from modules 4 and 5, applied here to models:

interface-based model — two files, one interface, one implementation// FILE 1: the public contract
public interface Teaser {
    String getTitle();
    String getShortDescription();
    boolean hasImage();
}

// FILE 2: the implementation (callers never import this class)
@Model(
    adaptables  = Resource.class,
    adapters    = Teaser.class,          // ← "register me under Teaser, not TeaserImpl"
    resourceType = "academy/components/teaser"
)
public class TeaserImpl implements Teaser {
    @ValueMapValue private String title;
    // ...
}

// Callers adapt to the interface:
Teaser teaser = resource.adaptTo(Teaser.class);   // ← TeaserImpl is wired in automatically
📖 Why this code?

Interface-based models are the professional standard — splitting the contract from the implementation opens up composition and testing patterns that class-based models can't support.

  • public interface Teaser — the contract. This is what callers see and depend on. It can be placed in a shared API bundle so other modules can depend on it without depending on your implementation.
  • adapters = Teaser.class in @Model — registers TeaserImpl in the adapter registry keyed by Teaser.class. Callers do resource.adaptTo(Teaser.class), not resource.adaptTo(TeaserImpl.class) — they never import the implementation.
  • This is exactly how Core Components work: you adapt to com.adobe.cq.wcm.core.components.models.Teaser (the interface), not to their internal implementation class. Module 8 builds directly on this.

Why bother? Two concrete reasons:

  • Composition across Core Components. Module 8 shows how to wrap a Core Component's model inside your own. That only works because Core Components publish interfaces — you adapt to com.adobe.cq.wcm.core.components.models.Teaser, not to an internal class you don't control.
  • Mockable in unit tests. In a test, you register a fake implementation of Teaser that returns hardcoded values. Because the consuming code only sees the interface, the fake is indistinguishable from the real thing.

04 · Deploying & Using a Model in a Component

One thing that trips every beginner up at least once: you never write @Component(service = ...) for a Sling Model. There is no registration step. The Sling Models Maven plugin scans your compiled classes during the build, finds every class annotated with @Model, and generates the OSGi registration metadata automatically. Just run mvn clean install -PautoInstallSinglePackage and the model is live.

using a model in an HTL template — the complete picture<!-- data-sly-use.teaser="..." triggers resource.adaptTo(TeaserModel.class) -->
<div data-sly-use.teaser="biz.netcentric.academy._05.TeaserModel">

    <!-- teaser.title calls model.getTitle() -->
    <h2>${teaser.title}</h2>

    <!-- data-sly-test removes the element if the expression is falsy -->
    <p data-sly-test="${teaser.shortDescription}">
        ${teaser.shortDescription}
    </p>

    <!-- teaser.hasImage calls model.hasImage() -->
    <div data-sly-test="${teaser.hasImage}">
        <!-- render image -->
    </div>
</div>
📖 Why this code?

This shows the full picture of a model being used inside an HTL template — every comment in the code is part of the explanation.

  • data-sly-use.teaser="..." — the fully-qualified class name triggers adaptation. The result is bound to teaser for the rest of the template scope.
  • ${teaser.title} calls model.getTitle(). HTL uses Java introspection to map property names to getters.
  • data-sly-test="${teaser.shortDescription}" — removes the element entirely from the output (not just hides it with CSS) if getShortDescription() returns null or an empty string. This is cleaner HTML for screen readers and crawlers.
  • If adaptation fails (model returns null), every ${teaser.xxx} expression evaluates to an empty string — the template renders as blank with no error thrown.

If the model is null (adaptation failed) the data-sly-use silently binds an empty object and all the expressions evaluate to empty strings. This means a broken model often looks like a blank component rather than an error — which is why checking logs and enabling debug logging on org.apache.sling.models.impl is so important.

05 · OSGi Services in a Model

A model itself is never an OSGi component. It has no @Component, no lifecycle, and is created fresh every single time something calls adaptTo(). But it can still consume OSGi services using one more injector annotation:

@OSGiService — the model's equivalent of @Reference@Model(adaptables = Resource.class)
public class WeatherModel {

    @OSGiService               // ← same registry as @Reference, different annotation
    private WeatherService weatherService;

    @ValueMapValue
    private String city;

    private String temperature;

    @PostConstruct
    protected void init() {
        // delegate the actual work to the service
        temperature = weatherService.getCurrentTemperature(city);
    }

    public String getTemperature() { return temperature; }
}
📖 Why this code?

This shows how a Sling Model consumes an OSGi service — despite never being an OSGi component itself.

  • @OSGiService — looks up the OSGi service registry for the requested type, exactly like @Reference does in an OSGi component. The different annotation name is purely because Sling Models isn't itself an OSGi component — the underlying registry lookup is identical.
  • If no WeatherService is registered when a request triggers adaptation of this model, the injection fails. Because weatherService is required (no @Optional), the whole model returns null — the template renders blank, potentially with no obvious error.
  • The design principle here: the model's job is to read content and orchestrate. The service's job is to do actual work (geocoding, HTTP calls). Keeping these separate means you can unit test the service independently and mock it when testing the model.

@OSGiService does exactly the same lookup in the OSGi registry as @Reference does in a component — the only reason it's a different annotation is that a model isn't itself managed by OSGi. If no matching service is registered and the field is required, adaptation returns null (the usual culprit when a model seems to fail for no reason).

06 · OSGi Configurations in a Model

A model can't have a @Designate configuration — there's no OSGi component for the config to attach to. Configuration reaches a model through two different paths depending on what kind of value it is:

  • Environment-level settings (same for all sites, different per environment) — put them in an OSGi service with @Designate, and inject that service with @OSGiService. The model calls a method on the service and gets the configured value back without knowing it came from a .cfg.json file.
  • Content-level settings (different per site or per piece of content) — use Context-Aware Configuration (module 15). The model injects ConfigurationBuilder via @Self and reads a @Configuration-annotated interface directly.
reading a content-level config directly in a model@Model(adaptables = Resource.class)
public class WeatherModel {

    @Self
    private ConfigurationBuilder configurationBuilder;

    @PostConstruct
    protected void init() {
        // Read a configuration value scoped to the current site's content hierarchy
        WeatherConfig config = configurationBuilder.as(WeatherConfig.class);
        String defaultCountry = config.defaultCountry();  // e.g. "DE" for German site
    }
}
📖 Why this code?

This shows how a model reads content-level configuration (values that differ per site on the same instance, not per environment).

  • @Self private ConfigurationBuilder configurationBuilder — @Self injects the adaptable itself (the Resource), but typed as a different object. Sling's Context-Aware Configuration framework registers an adapter from Resource to ConfigurationBuilder, so this works via the same adaptation mechanism as everything else.
  • configurationBuilder.as(WeatherConfig.class) — resolves the configuration for the current content path. It walks up the content hierarchy looking for a sling:configRef pointer that leads to the right /conf tree. Different sites can have different values for the same WeatherConfig interface.
  • This is different from OSGi config (@Designate) which is instance-wide. CA Config is content-aware — the value changes based on where in the repository you are.

07 · Sling Models Best Practices

These six habits are the difference between a model that stays clean as the project grows and one that becomes a maintenance nightmare:

1 — Keep models thin A model's job is to read content and expose typed values. If you find yourself writing business logic, calling external APIs, or building complex objects inside a model — move that to an OSGi service and inject the service. A 50-line model is healthy. A 500-line model is a sign something went wrong.
2 — Default to Resource.class as adaptable Unless you genuinely need selectors, request parameters, or request attributes, use Resource.class. It works in more contexts and is easier to test. Defaulting to SlingHttpServletRequest.class is the single most common cause of unexplained null adaptations from inside other models.
3 — Prefer constructor injection on new models Constructor injection gives you final fields and eliminates the null-before-PostConstruct window. It also makes unit testing trivial — you just call new MyModel(arg1, arg2) with test values.
4 — Use interface-based models for anything shared If another model, another component, or a unit test will need to depend on your model, split it into an interface and an implementation. Module 8 relies on this completely.
5 — Never do I/O inside @PostConstruct Calling an external HTTP API, running a slow query, or reading files inside @PostConstruct blocks the render thread on every page load. Module 12's WeatherModel does this intentionally as a cautionary example. Module 18 shows the correct fix (background jobs + caching).
6 — Never suppress the null, investigate it When adaptTo() returns null, the instinct is to add null checks everywhere. Resist this. Enable debug logging on org.apache.sling.models.impl to find the exact failing field, fix the root cause, and remove the workaround. Null-checking around a broken model just hides the bug.
Try it — convert from field to constructor injection Take the TeaserModel from module 6 and convert it to use constructor injection. Notice which fields can become final. Then write a plain Java unit test (no AEM, no mocks) that creates a TeaserModel by calling the constructor directly with a 100-character description string, and asserts that getShortDescription() is truncated to 80 characters.
