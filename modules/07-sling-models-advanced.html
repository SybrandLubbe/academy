Sling Models In Depth

Module 6 covered enough Sling Models to get you building. This module fills in everything else: how adaptation and injection style actually work, how a model gets deployed and used inside a real component, how it relates to OSGi services and configuration even though it's never an OSGi component itself, and what separates a model that's pleasant to maintain from one that isn't.

What you'll learn

  • What "adaptation" is actually doing under the hood, and the real decision rule for Resource vs. SlingHttpServletRequest
  • Constructor injection vs. field injection, and interface-based vs. class-based models
  • How a model gets deployed (there's no manual registration step) and wired into a real component
  • How a model consumes an OSGi service, and how configuration reaches it without it ever being an OSGi component
  • The handful of practices that keep a model maintainable as it grows

03 · Adaptables (Request vs Resource) & Injection Style

What adaptation actually does

Calling resource.adaptTo(MyModel.class) isn't special-cased to Sling Models — it's the same generic Adaptable mechanism Sling uses everywhere (it's how a Resource becomes a ValueMap, too). Behind the scenes, an OSGi-registered AdapterFactory for Sling Models inspects your @Model annotation, checks whether the source object's type matches one of your declared adaptables, and — if so — runs the injection process and hands you back a populated instance, or null if a required field couldn't be filled.

Resource vs. Request

Module 6 introduced this briefly; here's the actual decision rule. Adapt from Resource.class whenever you can — it works in more places (including being adapted from inside another model — exactly what you'll need once you start composing over Core Components' own models) and doesn't depend on there being an active HTTP request at all. Adapt from SlingHttpServletRequest.class only when you specifically need something a bare resource doesn't carry: selectors, request parameters, the resolved suffix, or request attributes set by a filter earlier in the chain.

Common pitfall Declaring adaptables = SlingHttpServletRequest.class out of habit, then later trying to adapt the same model from inside another model (which only has a Resource to offer) — and finding it returns null with no obvious explanation. If a model doesn't genuinely need request-specific data, keep it adaptable from Resource so it stays composable.

Constructor vs. field injection

Everything you've seen so far uses field injection with @PostConstruct for any derived logic. Sling Models also support constructor injection, which many teams now prefer:

field injection (what you've used so far)@Model(adaptables = Resource.class, resourceType = "academy/components/teaser")
public class TeaserImpl implements Teaser {

    @ValueMapValue
    private String title;

    private String displayTitle;

    @PostConstruct
    protected void init() {
        displayTitle = title != null ? title.toUpperCase() : "Untitled";
    }
}
constructor injection@Model(adaptables = Resource.class, resourceType = "academy/components/teaser")
public class TeaserImpl implements Teaser {

    private final String displayTitle;

    @Inject
    public TeaserImpl(@ValueMapValue String title) {
        this.displayTitle = title != null ? title.toUpperCase() : "Untitled";
    }
}

Constructor injection makes every field final — the object is fully valid the moment it exists, there's no window where it's half-constructed, and it's noticeably easier to unit test (module 14) because you can simply call the constructor directly with test values instead of needing the full Sling Models injection machinery. Field injection is still completely valid and you'll see plenty of it in existing codebases; reach for constructor injection on new models when you can.

Interface-based vs. class-based models

You can put @Model directly on a concrete class (everything you've built so far does this), or split it into an interface plus an implementation:

interface-based modelpublic interface Teaser {
    String getTitle();
    String getDescription();
}

@Model(
        adaptables = Resource.class,
        adapters = Teaser.class,
        resourceType = "academy/components/teaser"
)
public class TeaserImpl implements Teaser {
    // ...
}

Callers adapt to Teaser.class, never seeing TeaserImpl at all — the same interface-over-implementation idea module 13 covers for Java in general, applied here to models. Two concrete benefits: it's what makes composing over a Core Component's own model possible at all — you're adapting to a published interface, not a class you don't control, a pattern you'll use directly once you start extending Core Components yourself — and it's what lets module 14 mock a model's dependencies in a unit test without needing the real implementation on the classpath.

04 · Deploying & Using a Model in a Component

Unlike the OSGi components from module 4, you never write @Component(service = ...) for a Sling Model — the Sling Models bundle plugin scans your compiled classes for @Model annotations during the Maven build and generates the OSGi metadata automatically. Run mvn clean install -PautoInstallSinglePackage the same way as any other change, and the new model is registered the moment the bundle activates. If a model genuinely isn't being found, the most common cause isn't a missing registration — it's a resource type or adaptable type that doesn't match what's actually being adapted.

A model only earns its keep once a render script actually uses it. Module 9 covers HTL properly, but the shape is short enough to preview here, continuing the same TeaserModel from module 6:

/aem-academy/ui.apps/src/main/content/jcr_root/apps/academy/components/teaser/teaser.html (academy.ui.apps)<div data-sly-use.teaser="biz.netcentric.academy._05.TeaserModel">
    <h2>${teaser.title}</h2>
    <p>${teaser.shortDescription}</p>
</div>

data-sly-use.teaser="..." is what actually triggers the adaptation — it calls resource.adaptTo(TeaserModel.class) behind the scenes and binds the result to the teaser name used in the expressions below it. The model's resourceType doesn't have to match the script's location for this to work (you can data-sly-use any model from any script), but in the normal case — a component's own render script using its own model — they line up because both are resolved against the same component folder, the one module 11 shows you how to wire up with a dialog and a component definition.

05 · OSGi Services

A model is never an OSGi component itself — it has no @Component annotation, no lifecycle of its own, and a fresh instance is built every time something adapts to it. But it can still consume services that other components publish, through one more injector:

inside a Sling Model@OSGiService
private GreetingService greetingService;

@OSGiService looks the requested type up in the exact same OSGi service registry that @Reference reads from in module 4 — it's the same registry and the same lookup, just a different annotation because a model isn't itself a component that OSGi manages. If nothing implementing that service type is currently active, the field behaves like any other unfilled required field: the model fails to instantiate and adaptTo() returns null, unless the field is marked optional.

This matters more than it sounds: it's the seam that keeps real logic out of the model. A model should ask an injected service to do work — geocode a city, call an external API, run a calculation — rather than doing that work inline itself. Module 12's WeatherModel deliberately breaks this rule (making an HTTP call directly inside @PostConstruct) as a worked example of why the rule exists; module 18 shows the production-correct fix.

06 · OSGi Configurations

Since a model is never an OSGi component, it can never carry @Designate the way a service can — there's no component instance for that configuration to attach to. Configuration still reaches a model, just one level removed, through two different routes depending on what kind of value it is:

  • Environment-level configuration, indirectly. The model injects a service (@OSGiService, as above), and that service is the thing carrying @Designate and reading its own .cfg.json file (module 5). The model just calls a method on the service and gets back an already-configured result — it never touches OSGi configuration directly, and doesn't need to know it exists.
  • Content-level configuration, directly. For a value that should differ per site rather than per environment — a default country for a Weather component, say — a model can adapt itself (or its resource) straight to ConfigurationBuilder and read a Context-Aware Configuration value with no service in between at all. Module 15 covers this in full; the shape is short enough to preview here:
inside a Sling Model@Self
private ConfigurationBuilder configurationBuilder;

protected void init() {
    WeatherConfig config = configurationBuilder.as(WeatherConfig.class);
    String fallbackCountry = config.defaultCountry();
}

The rule of thumb: if a value is the same for every site on the instance and only changes between environments (author vs. publish, dev vs. prod), it belongs in OSGi configuration behind a service. If it should differ per site or per piece of content, it belongs in Context-Aware Configuration, read straight from the model.

07 · Sling Models Best Practices

A handful of habits separate a model that stays pleasant to maintain from one that quietly turns into a dumping ground:

  • Keep models thin. Push real business logic into an OSGi service (section 05 above) that the model injects, rather than letting the model itself grow into a few hundred lines mixing content reading with actual logic.
  • Default to interface-based models for anything another component, model, or test might need to depend on — it's what makes composition (module 8) and clean mocking (module 14) possible in the first place.
  • Avoid doing I/O inside @PostConstruct without thinking it through. You'll see this mistake made on purpose, as a cautionary example, when you build module 12's WeatherModel.
  • Prefer constructor injection on new models when you can — final fields and a model that's trivially testable without the Sling Models machinery are worth the slightly less familiar syntax.
  • Don't request SlingHttpServletRequest "just in case." An adaptable you don't actually need for request-specific data is the most common reason a model unexpectedly can't be composed into another one later.
  • Let adaptTo() failing loudly guide you, don't suppress it. A model returning null is Sling Models telling you something specific is missing — chase it with debug logging (module 6) rather than working around it with extra null checks everywhere a model is used.
Try it Convert the Java Primer's StudentModel (module 00, exercise 3) from field injection to constructor injection. Note which fields can become final once you do.

Knowledge Check

Ten questions to ask students once they've finished this module — answers are hidden by default so you can quiz live before revealing them.

  1. What mechanism does resource.adaptTo(MyModel.class) actually use under the hood?

    Show answer

    The generic Sling Adaptable mechanism via an OSGi-registered AdapterFactory for Sling Models — the same general mechanism used for things like adapting a Resource to a ValueMap.

  2. What's the practical difference between putting @Model directly on a concrete class versus splitting it into an interface plus an implementation?

    Show answer

    Interface-based models let callers adapt to the interface and never see the implementation class — enabling composition patterns and easier mocking in tests.

  3. How does a Sling Model actually get registered with OSGi — what replaces the @Component registration an OSGi service needs?

    Show answer

    There's no manual registration step; the Sling Models Maven plugin scans compiled classes for @Model annotations during the build and generates the OSGi metadata automatically.

  4. What's the main practical benefit of constructor injection over field injection for a Sling Model?

    Show answer

    Every field can become final — the object is fully valid the instant it exists, with no half-constructed window, and it's easier to unit test by calling the constructor directly with test values.

  5. What does data-sly-use.teaser="..." actually trigger behind the scenes?

    Show answer

    It calls resource.adaptTo(TeaserModel.class) and binds the result to the "teaser" name used in the expressions below it.

  6. Give the decision rule for choosing Resource vs. SlingHttpServletRequest as a model's adaptable, and what goes wrong if you default to Request out of habit?

    Show answer

    Adapt from Resource whenever possible — it works in more places, including from inside another model. Defaulting to SlingHttpServletRequest out of habit means the model can't later be adapted from inside another model (which only has a Resource to offer) — it'll return null with no obvious explanation.

  7. Where should real business logic live, according to this module's best-practices guidance?

    Show answer

    In an OSGi service that the model injects, keeping the model itself thin rather than growing it to hundreds of lines.

  8. What specific mistake does the upcoming WeatherModel deliberately demonstrate, as referenced in this module?

    Show answer

    Doing I/O (an outbound HTTP call) inside @PostConstruct without thinking it through.

  9. What's the practical difference between an OSGi component's @Reference and a Sling Model's @OSGiService?

    Show answer

    They look up the exact same OSGi service registry — @OSGiService exists as a separate annotation only because a model isn't itself an OSGi component that OSGi can manage.

  10. A model needs a value that's the same for every site but should differ between author and publish. Does that belong in OSGi configuration or Context-Aware Configuration?

    Show answer

    OSGi configuration, behind an injected service — Context-Aware Configuration is for values that differ per site or piece of content, not per environment.
