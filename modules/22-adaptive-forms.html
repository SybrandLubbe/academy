Dynamic Forms / Adaptive Forms

AEM Adaptive Forms let you build smart, responsive web forms that change based on user input, device, and business rules — without writing front-end JavaScript for every rule. They connect directly to back-end systems via the Form Data Model and live inside AEM the same way pages and components do.

What you'll learn

  • What an Adaptive Form is and how it differs from a plain HTML form
  • Foundation Components vs Core Components — which to use
  • Form Container, field types, panels, and the Rule Editor
  • What the Form Data Model is and how it connects to external data
  • Submit actions — what happens when a user clicks Submit

What is an Adaptive Form?

An Adaptive Form adapts to the device (responsive layout), to user input (show "Spouse income" only if "Married" is selected), to external data (pre-fill a returning customer's address), and to validation rules (check age before allowing submission). Traditional HTML forms are static — you write the HTML, logic, validation, and handler yourself. Adaptive Forms move all of that into AEM's authoring environment, so business analysts configure show/hide rules without touching code.

Analogy A paper form has all questions printed regardless of your situation. A bank teller asks only relevant follow-up questions. Adaptive Forms turn your web form from a paper form into the teller.

Foundation vs Core Components

two generations — know which one your project usesFoundation Components (legacy)
  Based on: JSP templates
  Resource type: /libs/fd/af/components/
  Status: no new features — maintenance only

Core Components (current — use for all new projects)
  Based on: HTL + Sling Models (same pattern as AEM Sites)
  Resource type: /libs/core/fd/components/
  Status: actively developed by Adobe
📖 Why this code?

This is not cosmetic — Foundation and Core Components use completely different rendering pipelines. Core Components follow the same Sling Model + HTL pattern you've learned throughout this training, making them consistent with AEM Sites development.

  • /libs/fd/ vs /libs/core/fd/ — different resource type paths mean a form built with Foundation Components cannot mix in Core Component fields.
  • Adobe has stopped adding features to Foundation Components. Always use Core Components for new projects.

Form Container and field types

Every Adaptive Form starts with one outer Form Container component that holds all other components and carries the submit action, data binding, and prefill service configuration.

common Core Form field resource typescore/fd/components/form/textinput/v2/textinput      → single-line text
core/fd/components/form/textarea/v2/textarea        → multi-line text
core/fd/components/form/numberinput/v1/numberinput  → numeric with min/max
core/fd/components/form/datepicker/v1/datepicker    → date selector
core/fd/components/form/dropdown/v1/dropdown        → select from a list
core/fd/components/form/checkboxgroup/v1/checkboxgroup → multi-select
core/fd/components/form/radiobutton/v1/radiobutton  → single-select radios
core/fd/components/form/fileupload/v1/fileupload    → file attachment
core/fd/components/form/panel/v1/panel              → group fields, target for rules
core/fd/components/form/wizard/v1/wizard            → multi-step wizard layout
📖 Why this code?

These resource types follow the same Sling resolution from module 3 — they're just Core Components that happen to be form fields.

  • The panel is especially important: it groups related fields and is the target for show/hide rules. Hiding a panel hides all fields inside it with one rule, not one rule per field.
  • The wizard renders panels as sequential steps, automatically handling Next/Previous navigation and step-level validation.

Form Data Model — connecting to back-end systems

Form Data Model data source typesRESTful web services  → any REST API with a Swagger / OpenAPI spec
SOAP web services     → legacy systems with a WSDL
OData services        → Microsoft Dynamics, SharePoint, SAP
Relational databases  → MySQL, PostgreSQL, Oracle via JDBC
AEM User Profile      → logged-in user's profile properties
📖 Why this code?

The FDM is a mapping layer — it describes external data in AEM's own terms so the form doesn't need to know whether data lives in a REST API or a database.

  • A data source is configured once in Tools → Cloud Services → Data Sources. Multiple forms can share one FDM, and one FDM can combine multiple data sources.
  • Once an FDM is connected to a form, you bind fields to FDM properties by dragging from the FDM tree in the field's dialog — no code required for standard cases.

Submit actions

built-in submit actionsSubmit to REST endpoint
  → POSTs form data as JSON to a configurable URL

Invoke a Form Data Model Service
  → calls a write operation on your configured FDM

Send Email
  → sends confirmation email via AEM's Mail Service OSGi config

Store in AEM Repository
  → writes submission as a content node under /content/forms/fp
  → useful for review workflows, not for high-volume storage

Custom submit action
  → implement GuideSubmitAction in Java — full control
📖 Why this code?

Submit actions are configured on the Form Container's dialog — no code for the standard ones. The custom action is the path requiring Java development (covered in module 24).

  • Submit to REST endpoint is the most common integration pattern — AEM posts JSON to your microservice; AEM acts as front-end only.
  • Store in AEM Repository should not be used as a production database — AEM's JCR is optimised for content management, not high-volume transactional data.

Show/hide rules — the "adaptive" part

rule examples — configured visually in the Rule Editor, no code required// Show/hide
WHEN field "maritalStatus" has value "Married"
THEN show panel "SpouseDetails"
ELSE hide panel "SpouseDetails"

// Compute a value
WHEN field "annualIncome" changes
THEN set field "monthlyIncome" = annualIncome / 12

// Validate
WHEN field "dateOfBirth" changes
THEN run custom function "calculateAge"
     IF age < 18 THEN show error "You must be 18 or older"

// Enable/disable
WHEN checkbox "agreeToTerms" is NOT checked
THEN disable button "Submit"
📖 Why this code?

Rules run in the browser — no server round-trips — so conditional logic feels instant even on complex forms.

  • The Rule Editor generates JavaScript under the hood but authors never see it. Business analysts configure rules; developers only step in for custom functions.
  • Rules target components by their Name property. Always give fields meaningful names before writing rules — changing a name later breaks every rule that references it.
  • Custom functions extend the Rule Editor: write a JavaScript function in a clientlib, register it, and it appears in the Rule Editor's function palette.
Try it In AEM Forms (localhost:4502/aem/forms), create an Adaptive Form using the blank Core Components template. Add a dropdown named employmentStatus with options "Employed" / "Self-employed". Add a panel named employerDetails with a text field inside. Open the Rule Editor on the panel and write: show the panel only when employmentStatus equals "Employed". Preview and verify the panel appears and disappears correctly.
