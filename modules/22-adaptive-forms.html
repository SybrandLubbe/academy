AEM Forms — Platform & Architecture

What you'll learn

  • What AEM Forms is and its three flagship enterprise use cases
  • The eight building blocks and how they map to concepts you already know
  • The author → publish → backend → storage topology
  • Digital Enrollment data flow end to end
  • Core Components vs Foundation Components — the decision that drives everything
  • Which roles you will interact with on a Forms project

What is AEM Forms?

AEM Forms is a separate add-on to AEM Sites. It is an enterprise platform for creating, managing, publishing, and updating complex digital forms and correspondence. Think of it as three products bundled together:

three flagship use cases

Digital Enrollment
  Responsive, rules-driven data capture — think bank account opening,
  insurance applications, government registrations.
  The form is the product. Users start on mobile, finish on desktop.

Customer Communications
  Personalised correspondence generated at scale — statements, welcome
  letters, policy documents. Templates merge with customer data to
  produce PDFs or HTML delivered via email, print, or web.

Enterprise Form Management
  A centralised portal for every form type — Adaptive, PDF, and XFA.
  One place to publish, version, tag, search, and govern them all.
📖 Why this matters for a backend developer
  • Each use case has a different architectural topology — the data flows differently. Knowing which one you're building for prevents you from wiring the wrong integration pattern.
  • Enrollment needs prefill (read from CRM before render) and submit-back (write to CRM after submit). Both require Java OSGi services you write.
  • Communications is largely configuration-driven — templates, data dictionaries, batch runs. Less Java, more content authoring.
  • Management is mostly Forms Portal configuration. Your job is often deployment and permission setup.

The Eight Building Blocks

Every AEM Forms feature maps to one of eight building blocks. Understanding these upfront stops you staring at an unfamiliar dialog wondering where you are in the product.

eight building blocks — your mental map of the product

1. Adaptive Forms
   Responsive, rules-driven HTML5 forms authored in AEM.
   Stored as nodes in /content/dam/formsanddocuments/ — same JCR you know.
   → Module 22 (this one)

2. Templates & Themes
   Templates  = form structure + allowed components (content policy, same as Sites).
   Themes     = CSS client libraries — styling separate from structure.
   → Module 23

3. Components
   Core Components   → BEM, responsive, no jQuery, actively developed.
   Foundation Comps  → legacy JSP, maintenance only. Avoid for new projects.
   → Module 22 (section below)

4. Rule Editor
   Condition → action rules (show/hide, validate, set value, invoke service).
   Visual editor for authors; JavaScript code editor for developers.
   → Module 23

5. Form Data Model (FDM)
   DAO/ORM-like layer connecting forms to REST / SOAP / JDBC / CRM.
   Build the model once; bind forms to it later. No coupling form ↔ source.
   → Module 23

6. Submission & Output
   Submit actions (store, REST, custom Java).
   Document of Record (DoR) — flattened PDF of what the user submitted.
   → Module 24

7. AEM Sites Embedding
   Place a form on a Sites page via the Embed (v2) component.
   Author once, surface everywhere — campaign pages, portals, microsites.
   → Module 24

8. Operations & Roles
   Access, permissions, environment config, monitoring, handover.
   → Module 24
📖 Why this code?
  • Building blocks 1–3 are what authors work with daily. Building blocks 4–6 are where you spend most of your time as a backend developer.
  • The Form Data Model (block 5) is the most important integration concept — it abstracts every data source behind a single AEM-managed layer, so forms never call REST APIs directly. Your OSGi services plug in here.
  • Adaptive Forms are stored in the JCR exactly like Sites pages — as a tree of nodes under /content/dam/formsanddocuments/. Every skill from modules 2 and 3 (reading node properties, Sling resource resolution) applies directly.

Architecture — Author, Publish, Backend, Storage

AEM Forms uses the same author/publish topology you learned in module 1, with a backend tier added for data integration.

AEM Forms deployment topology

AUTHOR                    PUBLISH                   BACKEND
  │                         │                         │
  │  Design & configure     │  Render form (HTML5)    │  REST · SOAP
  │  Core Components        │  Run Rule Editor JS     │  JDBC · OData
  │  Form Data Model        │  Execute submit action  │  CRM · AEM Profile
  │  Templates & Themes     │                         │
  └────── Replication ──────┘                         │
                            └── Form Data Model ──────┘
                                   calls data sources

STORAGE
  Submissions   → /content/forms/fp (JCR) or external DB
  DoR (PDF)     → DAM or external storage
  Workflows     → AEM Workflow engine on Author
📖 Why this code?
  • The Rule Editor JavaScript runs in the browser — no server round-trip. This means conditional logic is instant, but it also means any custom JavaScript validator you write must be deployed as a clientlib to the publish instance, not just author.
  • Submit actions run on the publish instance. Your OSGi service must be deployed and active on publish. Check /system/console/components on the publish instance, not author, when debugging a submit action that doesn't appear.
  • The Form Data Model's data source configuration lives on author. At runtime, the publish instance calls the configured endpoint. Use run-mode OSGi config folders (config.publish) to point different environments at different API URLs — same pattern as module 5.
  • The AEM Workflow engine lives on author. If your submit action triggers a workflow, the submission payload travels from publish → author via the JCR replication reverse path. This is called a reverse replication and needs to be configured explicitly in a real deployment.

The Digital Enrollment Topology — end to end

This is the most common use case you will implement. It touches every building block.

Digital Enrollment — data flow

1. Author builds form on AUTHOR with Core Components + FDM binding.
   Publishes form and FDM to PUBLISH via replication.

2. End user opens form URL on PUBLISH.
   Prefill service fires: FDM calls CRM / REST API.
   Form renders pre-populated with customer data.

3. User fills remaining fields. Rule Editor show/hide runs in browser.
   Client-side validators fire on blur/change.

4. User clicks Submit.
   Server-side validation fires (always add this — never trust the browser).
   Submit action executes on PUBLISH:
     → POST JSON payload to downstream REST API  (most common)
     → OR trigger AEM Workflow on AUTHOR via reverse replication
     → OR store in /content/forms/fp for a review workflow

5. Document of Record generated:
   AEM renders a flat PDF of all submitted values.
   Stored in DAM or external storage per submit action config.

6. Analytics event fired:
   Form submission event reaches Adobe Analytics via Adobe Tags.
   Panel-level completion and drop-off tracked.
📖 Why this code?
  • Step 4 is where your Java code lives. The submit action is an OSGi component implementing GuideSubmitAction. Module 24 walks through the full implementation.
  • Step 2 (prefill) is the other Java touchpoint — a service implementing DataXMLProvider. Module 23 covers this.
  • Steps 3 and 5 are configuration-only for standard cases. Only step 4 and a custom step 2 require Java code.
  • Keep this six-step flow in your head. Every Forms task you get assigned maps to one of these steps.

Core Components vs Foundation Components

This is the single most important decision on any AEM Forms project. It affects rendering, CSS, Rule Editor behaviour, migration effort, and your ability to move to AEM as a Cloud Service.

Foundation Components (legacy — do not use for new projects)

  Rendering:        JSP templates
  Resource type:    /libs/fd/af/components/
  JavaScript deps:  jQuery + Underscore.js (bundled, heavy)
  Accessibility:    limited ARIA support
  BEM CSS:          no — custom ad-hoc selectors
  Status:           maintenance only — no new features from Adobe
  Cloud Service:    NOT supported on AEM as a Cloud Service


Core Components (use for all new projects)

  Rendering:        HTL + Sling Models — same pattern as AEM Sites
  Resource type:    /libs/core/fd/components/
  JavaScript deps:  none — zero third-party JS dependencies
  Accessibility:    full ARIA + keyboard navigation built in
  BEM CSS:          yes — predictable selectors, easy to override
  Status:           actively developed by Adobe (open source)
  Cloud Service:    fully supported
  Source:           github.com/adobe/aem-core-forms-components
📖 Why this code?
  • Core Components follow exactly the same Sling Model + HTL pattern you've used throughout this training. There is no new rendering paradigm to learn — just apply modules 6, 7, and 9.
  • The different resource type paths (/libs/fd/ vs /libs/core/fd/) mean the two systems are completely separate. A form built on Foundation Components cannot mix in Core Component fields. You cannot gradually upgrade field-by-field — migration means rebuilding the form from scratch on a Core Components template.
  • Foundation Components depend on jQuery and Underscore.js. Core Components ship with zero third-party JavaScript. This matters for Lighthouse scores, bundle size, and CSP (Content Security Policy) compliance.
  • Custom component development follows the same overlay/proxy pattern from module 12: duplicate under /apps, keep beside the original, never modify /libs.
  • Adobe has confirmed Foundation Components will not be supported on AEM as a Cloud Service. If your client is planning a cloud migration, Foundation Components is a dead end.

Who builds it — roles you will work with

AEM Forms projects involve more roles than a typical Sites project. Knowing who does what prevents you from doing their job or blocking them waiting for yours.

role map for an AEM Forms project

Forms Practitioner (Business Analyst / Power User)
  ↳ Authors forms using the visual editor
  ↳ Configures Rule Editor show/hide logic (no code)
  ↳ Creates templates and themes (no code for standard cases)
  ↳ You unblock them by: deploying Core Components, setting up templates

Backend Developer (you)
  ↳ Custom submit actions (Java — GuideSubmitAction)
  ↳ Prefill services (Java — DataXMLProvider)
  ↳ Custom validators (JavaScript clientlib — fd.af.validator category)
  ↳ FDM data source setup when the API has no Swagger spec
  ↳ OSGi config for run-mode–specific API endpoints

AEM Administrator
  ↳ Access & permissions — forms-users / forms-power-user groups
  ↳ Data source credentials in Cloud Services
  ↳ Reverse replication config for workflow-based submissions

UX Designer
  ↳ Theme CSS (clientlib targeting BEM classes Core Components emit)
  ↳ You unblock them by: providing the correct BEM class reference

Solution Architect
  ↳ Decides enrollment vs communications vs management topology
  ↳ Decides Core vs Foundation (should always be Core)
  ↳ FDM design — which data sources, which operations exposed
📖 Why this code?
  • The boundary between Forms Practitioner and Backend Developer is the Rule Editor. Everything in the visual Rule Editor is the practitioner's job. Once they need a Custom Function — a JavaScript function they can call from a rule — that's yours. Module 23 covers Custom Functions.
  • The AEM Administrator sets up data source credentials in Tools → Cloud Services → Data Sources. These are encrypted OSGi configs. As a developer you design which credentials are needed; the admin applies them per environment.
  • Keep permissions clean: assign to groups (forms-users, forms-power-user), never to individuals. This is the AEM security best practice from module 5 applied to Forms.
Try it — If you have access to a local AEM instance with the Forms add-on installed, navigate to http://localhost:4502/aem/forms. This is the Forms authoring console — equivalent to the Sites console at /sites.html. Then open CRXDE and browse to /content/dam/formsanddocuments. Create a folder there and notice it appears immediately in the Forms console. Now open /libs/core/fd/components/form — this is every Core Component field type. Count them, read the node names. This is the palette your authors drag from.

Ten questions for this module — ask them live, then check the Trainer Answer Key for the full answers.

  1. Name the three flagship AEM Forms enterprise use cases. For each one, describe in one sentence what it delivers to end users.
  2. Where in the JCR are Adaptive Forms stored? What does this tell you about how they are versioned and replicated?
  3. Name all eight AEM Forms building blocks. Which three require Java backend development for non-trivial projects?
  4. Draw the Digital Enrollment topology — author, publish, backend, storage — and label which step your prefill service runs in and which step your submit action runs in.
  5. A submit action is deployed but does not appear in the Form Container dialog on the author instance. What is the first thing you check, and on which instance?
  6. Explain the difference between Core Components and Foundation Components from a backend developer's perspective. Include resource type paths and JavaScript dependency differences.
  7. Why can you not gradually migrate a form from Foundation Components to Core Components field by field?
  8. What is the Rule Editor's role, and at what point does a Forms Practitioner need to hand work to a Backend Developer?
  9. A custom validator clientlib is deployed but the Rule Editor does not show the custom function. What category must the clientlib use?
  10. The Form Data Model's data source configuration is set up on the author instance. Which instance actually calls the external REST API at runtime, and what does this mean for OSGi run-mode config?
