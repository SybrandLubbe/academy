Architecture Overview

Three layers, stacked: a repository that stores everything as a tree, a framework that turns URLs into rendered resources, and a runtime that wires the code together. Once these click, the rest of AEM is just detail.

What you'll learn

  • The repository / Sling / OSGi split, and why AEM is built this way
  • The difference between an author instance and a publish instance
  • What replication and the dispatcher each do, in one sentence
  • Where your code will actually live in a real project

The three layers

AEM is not one product — it's three open-source projects stacked on top of each other, plus Adobe's applications (Sites, Assets, Forms) built on top of that stack. As a backend developer, you'll spend most of your time in the middle and bottom layers.

1. Apache Jackrabbit Oak — the repository

Everything in AEM — pages, components, assets, user accounts, workflow definitions, your own custom data — is stored as a node in a single hierarchical tree, the JCR repository. Each node has a path (like a filesystem path), a set of properties (key/value pairs), and child nodes. There is no separate database for "content" versus "configuration" versus "code metadata" — it's all the same tree. You'll meet this properly in the next module.

2. Apache Sling — the resource framework

Sling's job is to turn an incoming HTTP request into a Java object (a resource) and then find the right script or servlet to render it. It does this by mapping the URL path directly onto a repository path, then asking "what type of resource is this?" and resolving a renderer for that type. This is the opposite of a typical MVC framework where you define routes — in Sling, the content tree is the routing table.

3. Apache Felix (OSGi) — the runtime

Your Java code doesn't run as one big application — it runs as a collection of bundles, small modular JARs that declare what they need and what they provide. OSGi is the runtime that loads, wires, and can hot-swap these bundles independently, without restarting the whole server. This is what lets a large AEM instance run code from dozens of teams without it turning into a single tangled deployment.

Mental model Repository = what's stored. Sling = how a request finds and renders it. OSGi = how your code is packaged and run. Every AEM concept you'll learn maps onto one of these three.

Author and publish

A typical AEM environment runs (at least) two kinds of instances:

  • Author — where content authors and developers work. Content is created, edited, and reviewed here. It is never exposed directly to end users.
  • Publish — serves the live, public-facing site. It holds a copy of the approved content, kept up to date through replication.

Replication is the process of pushing content (and sometimes code) from author to publish, triggered when a page is activated. As a backend developer, you'll often need to reason about which instance a piece of code runs on — some services only make sense on author (workflow logic, authoring UI backends) and some only on publish (high-traffic read APIs).

The dispatcher

Sitting in front of publish instances, the dispatcher is an Apache HTTP Server module that does two jobs: it caches rendered pages as static files so publish doesn't have to re-render every request, and it acts as a security gatekeeper, blocking requests that don't match an allow-list of safe URL patterns. You'll cover this properly in module 19, but it's worth knowing it exists from day one — a surprising number of "it works locally but not in production" bugs come from dispatcher rules.

Common pitfall New developers often write code assuming a single running instance. In a real deployment, author and publish are separate JVMs with separate copies of the repository. A service registered or configuration set on author will not exist on publish unless you've explicitly arranged for it.

Where your code lives

In a typical project repository (the Git one, not the JCR one), backend code is organized as a Maven multi-module project, commonly using the AEM Project Archetype. The two paths you'll see constantly inside the JCR tree once it's deployed:

JCR paths/apps/your-project/      → your code: components, templates, OSGi configs, clientlibs
/libs/                   → out-of-the-box AEM code — never modify this directly
/content/your-project/   → the actual authored content (pages, assets)
📖 Why this code?

This diagram shows the three top-level paths every AEM developer works with every day. Understanding which path is for what prevents the most common class of beginner mistakes.

  • /apps/your-project/ — your custom code: components (HTL scripts + dialogs), clientlibraries, and OSGi config files. This path survives AEM upgrades because it's yours.
  • /libs/ — Adobe's built-in code. Never modify this directly. It is overwritten on every AEM upgrade, hotfix, or service pack installation. Any change you make here disappears silently.
  • /content/your-project/ — the actual page and asset content authors create. This is the data; /apps is the code that renders it.

The rule that trips up almost everyone at first: never edit anything under /libs. It's overwritten on every product upgrade. If you need to change out-of-the-box behavior, you overlay it — recreate the path under /apps and AEM's resource resolution will prefer your version. You'll see exactly how that resolution works in module 3.

Try it If you have access to a local AEM instance, open http://localhost:4502/crx/de (CRXDE Lite) and browse to /apps and /content. Don't worry about understanding everything you see yet — just get comfortable with the idea that this tree is the entire system.
