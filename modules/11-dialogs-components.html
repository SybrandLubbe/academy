Dialogs, Components & the Touch UI

A component is content plus a dialog that lets an author edit that content. The dialog itself is just more Granite UI markup sitting in the repository — no different in spirit from the JCR tree you met in module 2.

What you'll learn

  • The standard component folder layout
  • How a dialog is itself repository content, resolved the same way as module 3's scripts
  • The Granite UI field types you'll reach for most often
  • Design dialogs and content policies — and which one your project actually uses
  • Organizing a larger dialog with tabs

Component anatomy

Every component is a folder under ui.apps (academy.ui.apps). The path you create it at in your project and the path it ends up at in the running repository are different — jcr_root in your project maps directly onto the repository root once deployed, so everything under it just drops the jcr_root segment:

/aem-academy/ui.apps/src/main/content/jcr_root/apps/academy/components/teaser/ (academy.ui.apps — becomes /apps/academy/components/teaser in the repository)teaser/
  .content.xml              component definition: title, group, resourceSuperType
  teaser.html                the HTL render script (module 9)
  _cq_dialog/.content.xml    the author dialog
  _cq_template/.content.xml  default content when dragged onto a page (optional)
📖 Why this code?

This folder layout is the physical structure of an AEM component on disk — what you create in ui.apps and what ends up in the repository after deployment.

  • .content.xml at the root — the component definition. Without this file, AEM doesn't recognise the folder as a component; it's just a directory.
  • teaser.html — the render script. The filename must match the component's folder name for Sling's default script resolution to find it automatically.
  • _cq_dialog/.content.xml — the author dialog. The _cq_dialog folder name is a fixed AEM convention — renaming it means the dialog won't appear in the page editor.

The component definition itself — the file that makes a folder an actual AEM component at all, rather than just an HTL script sitting somewhere — sets its title, which group it appears under in the author's component browser, and (optionally) which existing component it extends:

/aem-academy/ui.apps/src/main/content/jcr_root/apps/academy/components/teaser/.content.xml (academy.ui.apps)<?xml version="1.0" encoding="UTF-8"?>
<jcr:root xmlns:jcr="http://www.jcp.org/jcr/1.0"
    xmlns:sling="http://sling.apache.org/jcr/sling/1.0"
    jcr:primaryType="cq:Component"
    jcr:title="Teaser"
    componentGroup="Academy Training"/>
📖 Why this code?

This XML file is what makes a folder an AEM component. It's the simplest possible component definition.

  • jcr:primaryType="cq:Component" — the node type that marks this folder as a component. AEM scans the repository for nodes of this type to build the component registry.
  • jcr:title="Teaser" — the label shown in the page editor's "Insert Component" browser and in the component browser. Keep it short and descriptive.
  • componentGroup="Academy Training" — groups this component with others of the same group in the browser. More importantly, template policies (module 11's activation section) allow/deny entire groups — so getting the group name right is essential for authors being able to use the component.

componentGroup matters more than it looks: it's both how the component is organized in the author's "Insert component" browser, and — as you'll see below — the thing a template's policy has to explicitly allow before an author can use the component at all.

The dialog is just more repository content

A dialog node tree maps directly onto the Granite UI form it renders, using the same resourceType resolution mechanism from module 3 — it's simply running inside the author's editing UI instead of a page:

/aem-academy/ui.apps/src/main/content/jcr_root/apps/academy/components/teaser/_cq_dialog/.content.xml (academy.ui.apps)<?xml version="1.0" encoding="UTF-8"?>
<jcr:root xmlns:jcr="http://www.jcp.org/jcr/1.0"
    xmlns:sling="http://sling.apache.org/jcr/sling/1.0"
    jcr:primaryType="nt:unstructured"
    sling:resourceType="cq/gui/components/authoring/dialog">
    <content jcr:primaryType="nt:unstructured"
        sling:resourceType="granite/ui/components/coral/foundation/fixedcolumns">
        <items jcr:primaryType="nt:unstructured">
            <column jcr:primaryType="nt:unstructured"
                sling:resourceType="granite/ui/components/coral/foundation/container">
                <items jcr:primaryType="nt:unstructured">
                    <title jcr:primaryType="nt:unstructured"
                        sling:resourceType="granite/ui/components/coral/foundation/form/textfield"
                        fieldLabel="Title"
                        name="./jcr:title"/>
                    <image jcr:primaryType="nt:unstructured"
                        sling:resourceType="granite/ui/components/coral/foundation/form/pathfield"
                        fieldLabel="Image"
                        rootPath="/content/dam"
                        name="./image"/>
                </items>
            </column>
        </items>
    </content>
</jcr:root>
📖 Why this code?

This is the XML that defines the author dialog — the form that appears when an author clicks "Edit" on a component. It's just a tree of nodes in the repository, rendered by Granite UI.

  • sling:resourceType="cq/gui/components/authoring/dialog" — marks this node as a dialog container. Granite UI reads this resourceType to know how to render the form wrapper (with OK/Cancel buttons, etc.).
  • sling:resourceType="granite/ui/components/coral/foundation/form/textfield" — each field's resourceType determines what UI element renders. textfield renders a text input, pathfield renders a repository browser, checkbox renders a toggle.
  • name="./jcr:title" — the ./ prefix means "relative to this component's content node." When the author saves the dialog, AEM writes the value to the jcr:title property on the component's content node — the same property your Sling Model reads with @ValueMapValue.
Mental model Every field's name attribute is just a repository property path. A textfield named ./jcr:title writes straight to the jcr:title property on the component's own node — the dialog isn't a separate data layer, it's an editor for the exact nodes your Sling Model reads in module 6.

Common field types

A handful of Granite UI field types cover most dialogs: textfield for short text like a title, pathfield for browsing the repository to pick an asset or page, select for a fixed list of options, checkbox for a boolean, and multifield for a repeatable group — a list of link/label pairs, for example. multifield is the one that trips people up first, since each repetition is itself a small nested form. This goes inside the same _cq_dialog/.content.xml above, as a sibling of title and image inside <items> — not a separate file:

multifield excerpt — inside the existing dialog's <items><links
    jcr:primaryType="nt:unstructured"
    sling:resourceType="granite/ui/components/coral/foundation/form/multifield"
    fieldLabel="Related links">
    <field
        jcr:primaryType="nt:unstructured"
        sling:resourceType="granite/ui/components/coral/foundation/container"
        name="./links">
        <items jcr:primaryType="nt:unstructured">
            <label jcr:primaryType="nt:unstructured"
                sling:resourceType="granite/ui/components/coral/foundation/form/textfield"
                fieldLabel="Label" name="./label"/>
            <url jcr:primaryType="nt:unstructured"
                sling:resourceType="granite/ui/components/coral/foundation/form/pathfield"
                fieldLabel="Link" name="./url"/>
        </items>
    </field>
</links>
📖 Why this code?

Multifield is the most complex standard dialog field — it allows authors to create a repeating list of grouped values.

  • sling:resourceType=".../multifield" — renders a repeating group with Add/Remove/Reorder controls. Each repetition is stored as a child node under a links child node of the component's content node.
  • sling:resourceType=".../container" for the inner field — each repetition is itself a form container, holding multiple sub-fields (link text + href, for example). The container groups these into one logical "row."
  • Why it's complex: the stored data structure is a tree (a links child node containing numbered child nodes, each with its own properties), not a flat list. Reading this in a Sling Model requires @ChildResource combined with adapting each child to a sub-model.

Design dialog vs. content policy

Older, non-editable templates used a design dialog (cq:design_dialog) to capture settings shared across an entire site design under /etc/designs — one set of values applied everywhere that design was active. Modern editable templates replaced this with content policies under /conf/.../policies: the same idea of author-locked, component-level settings, but scoped to a specific template-and-component pairing rather than a whole site. If your project uses editable templates (almost all new projects do), policies are what control things like which components a paragraph system allows, or a teaser's permitted image ratio.

Organizing a bigger dialog with tabs

Once a component grows past a handful of fields, wrap related groups in a tabs container instead of one long scrolling form — authors find a labeled "Advanced" or "SEO" tab far easier to navigate than a wall of fields, and it keeps the most-used settings on the first tab where they're seen immediately.

Activating the component so authors can actually use it

Deploying a component does not make it available to authors. A component that builds successfully and exists under /apps is still invisible in the page editor until it's explicitly allowed by the template it's being used on — this is the single most common "where did my component go?" moment for anyone new to AEM authoring, and it has nothing to do with your Java or dialog being broken.

  1. Build and deploy as usual: mvn clean install -PautoInstallSinglePackage from /aem-academy.
  2. Confirm the component exists before chasing a policy problem: open /apps/academy/components/teaser in CRXDE Lite (localhost:4502/crx/de), or check it's listed at /libs/wcm/core/content/sites/components/componentbrowser.html — if it isn't there, the problem is the deploy, not the policy.
  3. Open the page's template in the Template Editor: Tools → General → Templates, find the template the page uses, and open it.
  4. Click into the layout container or responsive grid where you want the component allowed (the main paragraph system, typically), then click Policy in the toolbar that appears.
  5. Under Components, find the Academy Training group (the exact componentGroup value from the component's .content.xml) and check it. Unchecked groups are simply never offered to authors, regardless of whether the component exists.
  6. Save the policy and close the Template Editor.
  7. Open an actual page using that template, click the + insert-component button in the paragraph system, and the Teaser should now appear — search by name if the browser has a lot of components.
Common pitfall This entire policy step only applies to editable templates (almost every current AEM project). If you're on an older, non-editable-template project, the equivalent control is the page component's Design dialog instead (opened from the page Sidekick's gear icon) — the concept is identical, but the path to get there is different. If a component still doesn't show up after allowing its group, double-check you edited the policy on the correct layout container — a page can have several, each with its own independently-configured policy.
