Adobe Tags — Setup & Concepts

Adobe Experience Platform Tags (formerly Adobe Launch, formerly Adobe DTM) is a tag management system: a platform for deploying and managing marketing JavaScript without a code deploy for every change. For AEM developers it's the standard integration point for Adobe Analytics, Adobe Target, and any third-party tracking.

What you'll learn

  • What a tag management system is and the problem it solves
  • The five core concepts: Properties, Extensions, Data Elements, Rules, Environments
  • How to create and configure a Tag Property step by step
  • The publishing workflow from Development to Production
  • How AEM Sites integrates Tags via Cloud Services

What problem does Adobe Tags solve?

before and after tag managementWITHOUT a TMS:
  Every tracking script → developer ticket → code deploy → 1-2 day turnaround
  Config change to Google Analytics → another deploy
  New A/B test event → back to the developer queue

WITH Adobe Tags:
  ONE embed script on every page (added once, never changed)
  Everything else is configured in the Tags UI — no deploys needed
  Marketing team can add/change tracking in minutes, not days
📖 Why this code?

The core value: one deploy by a developer (the embed code), then unlimited changes by the marketing team without touching the site's codebase.

  • The embed code is a small JavaScript snippet loading the Tags library from Adobe's CDN. When a page loads, the Tags library executes all configured rules.
  • For AEM developers: add the embed code once via Cloud Services config, set up the Adobe Client Data Layer — then the implementation team works in the Tags UI from that point forward.

The five core concepts

Adobe Tags terminology — with AEM developer analogiesPROPERTY
  Container for everything belonging to one website.
  ≈ An AEM project: isolated config per site.

EXTENSIONS
  Plugins that add capabilities.
  Examples: Adobe Analytics, Core, Adobe Target, Hotjar, Google Analytics.
  ≈ OSGi bundles: install/remove independently.

DATA ELEMENTS
  Named variables referencing page data.
  Example: "Page Name" → document.title
           "User ID"   → digitalData.user.userId
  ≈ Sling Model @ValueMapValue: reads data by name.

RULES
  Event → Condition → Action logic.
  Example: Page Loaded → (always) → Send Analytics page view
  ≈ ResourceChangeListener: trigger + condition + action.

ENVIRONMENTS
  Dev / Staging / Production — separate embed codes, separate workflows.
  ≈ OSGi run-mode config folders: different config per environment.
📖 Why this code?

The AEM analogies make the learning curve shorter — the patterns are identical even though the tools are different.

  • Data Elements are the most important concept to get right. A well-named Data Element ("Page Name") used across 20 Rules is far more maintainable than hardcoding document.title in 20 places.
  • Rules are evaluated in the order they're listed and can be given a priority number. Order matters when multiple rules fire on the same event.

Creating a Tag Property — step by step

walkthrough in Adobe Experience Platform Data Collection UI1. https://experience.adobe.com/#/data-collection/ → Tags → New Property
   Name: "Academy Training Site"
   Platform: Web
   Domain: academy.netcentric.com

2. Install the Adobe Analytics extension:
   Extensions → Catalog → "Adobe Analytics" → Install
   Report Suite ID:  dev-academy-report-suite   ← use a DEV suite, not production
   Tracking Server:  your-company.sc.omtrdc.net
   Character Set:    UTF-8

3. Create your first Data Element:
   Data Elements → Add Data Element
   Name:            "Page Name"
   Extension:       Core
   Data Element Type: JavaScript Variable
   Variable name:   digitalData.page.pageInfo.pageName
📖 Why this code?

The Tags UI is where all configuration lives — not in AEM. AEM only provides the mechanism to load the embed code.

  • Use a DEV report suite for the development Tags environment. Development data pollutes production reports — always separate them.
  • Tracking Server (your-company.sc.omtrdc.net) is the Analytics server receiving beacons. Ask your Analytics admin for the correct value — it's specific to your organisation.
  • digitalData.page.pageInfo.pageName references the Adobe Client Data Layer (ACDL) that AEM Core Components populate automatically. Module 26 covers this in detail.

Creating Rules

rule: send a page view beacon to AnalyticsRULE NAME: "Send Page View"

EVENT:
  Extension: Core
  Type: Library Loaded (Page Top)
  → fires when the Tags library loads on every page

CONDITIONS:
  (none — fires on every page)

ACTIONS:
  1. Adobe Analytics — Set Variables
     eVar1   = %Page Name%      ← %...% references a Data Element
     prop1   = %User Agent%
     events  = event1

  2. Adobe Analytics — Send Beacon
     Tracking Type: Page View (s.t())
📖 Why this code?

Always: Set Variables first, then Send Beacon. Never merge them — keeping them separate lets you insert conditions between setting and sending.

  • %Page Name% — the curly-brace syntax resolves a Data Element by name. At runtime, Tags substitutes the Data Element's current value.
  • eVar1, prop1, events — Adobe Analytics variables. eVars persist across pages (like a session cookie); props are per-hit only; events are counters for specific actions. Your Analytics admin assigns which variable maps to which data.
  • s.t() = page view (increments Page Views metric). s.tl() = link tracking for clicks and custom events that should not be counted as page views.

Environments and publishing workflow

publishing flow from development to productionDEVELOPMENT
  Embed: https://assets.adobedtm.com/...dev.js
  Changes appear immediately after saving — no publish step needed.
  Use: local dev, rapid iteration.

STAGING
  Embed: https://assets.adobedtm.com/...staging.min.js
  Requires: Submit → Approve → Build to Staging.
  Use: QA against production content.

PRODUCTION
  Embed: https://assets.adobedtm.com/...min.js
  Requires: Promote → Approve → Build to Production.
  Use: live site only.

AEM maps:
  Author instance     → Development embed  (via Cloud Services run-mode config)
  Non-prod publish    → Staging embed
  Production publish  → Production embed
📖 Why this code?

Never load the Development embed in production — it's unminified, larger, and may contain in-progress rules not approved for end users.

  • Changing what the embed URL does (adding rules, updating Data Elements) doesn't require an AEM deployment. Changing which embed URL AEM loads (switching from Staging to Production) does — it's an AEM Cloud Services config change.

AEM Cloud Services integration

where Tags embed URLs live in AEMTools → Cloud Services → Adobe Experience Platform Launch
  → Creates config at /conf/<site>/settings/cloudconfigs/launch/jcr:content
    Properties:
      production.uri  = "https://assets.adobedtm.com/...launch-prod.min.js"
      staging.uri     = "https://assets.adobedtm.com/...launch-staging.min.js"
      development.uri = "https://assets.adobedtm.com/...launch-dev.js"

AEM Core Components' Page component reads this config and injects:
  <script src="{correct-uri-for-current-run-mode}"></script>
  in <head> automatically — no template editing required.
📖 Why this code?

This is a Context-Aware Configuration (module 15) — each site in AEM can have a different Tags property. The Page component reads it automatically when it extends Core Components.

  • Assign the config to your site by setting sling:configRef on /content/academy pointing to /conf/academy, or via Page Properties → Cloud Services tab on the root page.
Try it In Adobe Experience Platform Data Collection, create a Tag Property, install the Adobe Analytics extension, and create one Data Element "Page Name" reading document.title. Create a Rule: Library Loaded → Set Variables (eVar1 = %Page Name%) + Send Beacon. Copy the Development embed URL for use in module 26.
