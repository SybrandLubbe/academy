Adobe Analytics 40 min read

Web Analytics & Adobe Analytics

Before you wire a Data Element or fire a beacon, you need to understand why analytics exists, what a datalayer is and why you can't skip it, and where Adobe Analytics sits in the pipeline. This module is the conceptual foundation — module 26 is where you build it.

What you'll learn

  • What web analytics is and why it matters to the three teams you'll work with
  • The difference between Channels, Events, and Metrics
  • What a datalayer is and what three properties make one good
  • The three common datalayer types — which one you build on AEM
  • How Adobe Analytics fits into the full data pipeline: click to report

Why this matters to a backend developer

As an AEM backend developer you own the data that feeds the entire analytics pipeline: your component's HTML, your clientlib JavaScript, and whether the ACDL contains the right values at the right time. If you get it wrong — wrong property name, wrong event timing, missing a field the Analytics team expected — the reports are wrong. Silently. No console error. The data just doesn't match reality.

Your role in the chain AEM Developers → build components and populate the datalayer correctly. Analytics Engineers → read the datalayer and configure Launch rules. Business / Reporting teams → consume the data in Workspace. All three depend on what you push to the datalayer.

Web analytics fundamentals

Web analytics is the measurement, collection, and analysis of website data. The goal: replace assumptions about user behaviour with real evidence, then make better decisions with it.

the three building blocks — Channels, Events, MetricsCHANNELS    Where users come from
  Paid     → Google Ads, LinkedIn Ads, display banners
  Organic  → unpaid search (Google, Bing) — SEO-driven
  Social   → LinkedIn, Twitter/X, Facebook referrals
  Direct   → user typed the URL or used a bookmark
  Email    → links clicked in marketing emails

  → Developer note: UTM parameters (?utm_source=google&utm_medium=cpc)
    in landing page URLs are how Analytics attributes channel.
    AEM redirect rules or rewrite configs that strip query strings
    silently break channel attribution for every campaign.

EVENTS      What actions users perform on the site
  Page views     → baseline — every page load
  Clicks         → CTAs, nav links, downloads, video plays
  Form submits   → lead gen, checkout, registration
  Searches       → what users type in site search

  → Developer note: click and form events must be pushed to the
    datalayer from your component clientlib JS. If the push is
    missing, the event is never tracked — no error, just absence.

METRICS     Quantitative measures of behaviour
  Page Views       → total loads (one user, ten loads = 10)
  Unique Visitors  → distinct people (one user, ten loads = 1)
  Bounce Rate      → sessions with only one page view (%)
  Conversion Rate  → sessions that completed a goal (%)

  → Metrics are calculated from events.
    Wrong events → wrong metrics → wrong business decisions.
📖 Why this code?

This is the shared vocabulary that lets you talk to Analytics Engineers and business stakeholders without a translation layer in the room.

  • Channels and UTM parameters — utm_source, utm_medium, and utm_campaign are query parameters that Analytics reads from the landing page URL. An AEM developer who adds a redirect rule like RewriteRule (.+) $1? [R=301] (stripping query strings) kills campaign attribution for every paid ad.
  • Events are binary — either the push happens or it doesn't. There's no partial tracking. A click that fires the datalayer push is counted; one that doesn't is invisible. This makes complete clientlib coverage critical.
  • Metrics are derived — they're aggregations of events. When a stakeholder says "our form completion rate dropped," they mean a metric. Your job is to trace it back to which event is no longer firing.

What is a datalayer?

A datalayer is a centralised JavaScript object that acts as a bridge between user interactions on your site and your MarTech stack — Adobe Analytics, Adobe Target, Adobe Experience Platform, and any third-party tool. Instead of every tracking tool scraping the DOM independently, all tools read from one clean, structured source of truth.

the problem a datalayer solves — before and afterWITHOUT a datalayer (fragile, common on legacy sites):
  Tags reads page name from DOM:
    document.querySelector('h1').innerText
    ← breaks when a designer adds a hero h1 to the layout
    document.title
    ← returns "Netcentric | Banking Dashboard" — wrong format
    window.location.pathname
    ← returns "/en/banking/dashboard.html" — not human-readable

  Consequence: every HTML refactor or URL change silently
  breaks tracking. The Analytics team finds out weeks later.

WITH a datalayer (correct):
  Component pushes on render:
  adobeDataLayer.push({
    "page": {
      "pageInfo": { "pageName": "banking:dashboard" }
    }
  });

  Tags Data Element reads:
    page.pageInfo.pageName   ← always "banking:dashboard",
                                regardless of what h1 or URL says

  The contract: developer owns the datalayer.
  Analytics Engineer owns what Tags does with it.
📖 Why this code?

This is the core argument for why datalayers exist. DOM scraping works until it doesn't, and when it breaks it breaks silently.

  • document.querySelector('h1').innerText — reads whatever text is in the first h1 on the page. When the design team adds a visually decorative h1 inside an image banner, this suddenly returns "See our rates" instead of "Banking Dashboard." No error, just wrong data in Analytics.
  • page.pageInfo.pageName as a datalayer path — a deliberate contract set by the developer. The Analytics Engineer writes one Data Element against this path and it works on every page, forever, regardless of what the UI looks like.
  • This is the same separation-of-concerns principle as Sling Models: the model (datalayer) is the contract; the HTL template (DOM) is the presentation layer that Tags should never depend on.

Three properties of a good datalayer

what separates a good datalayer from a fragile oneSINGLE SOURCE OF TRUTH
  Centralised structure storing all customer interaction data.
  Standardized format shared across ALL tools:
    Analytics, Target, AEP, Google Analytics, Hotjar — all read here.
  → All teams use the same values. Discrepancies disappear.

DECOUPLES TRACKING FROM CODE
  Separates business logic (what the component does) from
  tracking logic (what gets measured).
  → Analytics rules in Launch can be updated without a code deploy.
  → Front-end refactors don't break tracking as long as the
    datalayer contract (property names and structure) is kept.

DRIVES CONSISTENCY
  Standard naming and structure across every user journey.
  "pageName" always means the same thing, formatted the same way,
  on every page, in every component.
  → Reduces data discrepancies and reporting issues between teams.
📖 Why this code?

These three properties are not features — they're design disciplines. Projects that violate them end up with unmaintainable analytics implementations.

  • Single source of truth — without it, Adobe Analytics reads document.title, Google Analytics reads a meta tag, and Target reads a custom attribute. Three tools, three values, three reports that never agree, three teams arguing about whose number is right.
  • Decouples tracking from code — the Analytics Engineer can add a new rule on a Tuesday without a sprint. The developer can refactor a component on Wednesday without breaking existing rules, as long as the datalayer push stays the same.
  • Drives consistency — naming matters. If the checkout page sends pageName: "checkout" and the product page sends page_name: "Product Detail", no segment can reliably filter "all users who saw a product page and then checked out." Consistency is the developer's responsibility when writing datalayer pushes.

The three common datalayer types

You will encounter three patterns across projects. Knowing which one a project uses tells you immediately what Tags Data Elements to build and what naming conventions to follow.

digitalData — W3C standard

digitalData — static, state-based, legacy enterprise patternwindow.digitalData = {
  page: {
    pageInfo: {
      pageName: "banking:dashboard",
      language: "en-GB"
    }
  },
  user: {
    userProfile: {
      "loginStatus": "logged in"
    }
  }
};
📖 Why this code?

window.digitalData is a W3C specification for a standardised analytics object. You'll find it on enterprise sites built 2015–2019, often alongside Tealium or older Adobe Launch setups.

  • Static / state-based — set once on page load. If a user logs in via a modal after load, loginStatus won't update unless you manually reassign it. This makes post-load interactions hard to track.
  • window.digitalData — globally accessible. Tags Data Elements of type "JavaScript Variable" read it via path like digitalData.page.pageInfo.pageName.
  • When you'll see it: older Adobe Analytics implementations, Tealium-managed sites, AEM projects that pre-date the ACDL. Work with it; don't replace it mid-engagement.

Google DataLayer — push array

Google DataLayer — event-push driven, GTM and GA4 standardwindow.dataLayer.push({
  "event": "loginSuccess",
  "pageName": "banking:dashboard",
  "language": "en-GB",
  "loginStatus": "true"
});
📖 Why this code?

The Google DataLayer is the standard for Google Tag Manager (GTM) and GA4. If a client also uses GTM alongside Adobe Launch, both tools typically read from window.dataLayer.

  • window.dataLayer.push({...}) — dataLayer is a JavaScript array. GTM's "Data Layer Variable" reads the most recent value pushed for a given key.
  • Flat structure — unlike ACDL's nested objects, pushes are flat key-value pairs. Simpler, but less expressive for component-level data hierarchies.
  • When you'll see it: projects using GA4 or GTM as the TMS. ACDL and Google DataLayer can coexist on the same page — both push to their own objects.

ACDL — Adobe Client Data Layer

ACDL — event-driven + state-based, the correct choice for AEM + Adobe Launch// Push an event with structured data
adobeDataLayer.push({
  "event": "loginSuccess",
  "page": {
    "pageInfo": {
      "pageName": "banking:dashboard",
      "language": "en-GB"
    }
  },
  "user": {
    "loginStatus": "logged in"
  }
});

// Read the current merged state at any time
window.adobeDataLayer.getState();
// → { page: { pageInfo: { ... } }, user: { ... } }

// Tags listens for events like this (configured in Launch, not your code):
window.adobeDataLayer.push(function(dl) {
  dl.addEventListener("loginSuccess", function(event) {
    // Adobe Launch's ACDL extension handles this automatically
    console.log("Captured:", event.eventInfo);
  });
});
📖 Why this code?

ACDL is both a push queue and a persistent state store — it combines the event-driven nature of Google DataLayer with the structured state of digitalData. This is why it's the right choice for AEM + Adobe Launch projects.

  • adobeDataLayer.push({...}) — unlike a plain array push, the ACDL push method merges the object into persistent state AND notifies all registered event listeners simultaneously. One call does both.
  • event: "loginSuccess" — the event name that Adobe Launch Rules listen for via the "ACDL Event Listener" event type. This is how post-load interactions (login, form submit, video play) are tracked without a page reload.
  • Nested structure (page.pageInfo.pageName) — paths map directly to Tags Data Elements of type "Data Layer Computed State." The same structure AEM Core Components populate automatically when ACDL is enabled.
  • getState() — returns the complete merged snapshot. Run this in the browser console to see exactly what Tags has to work with at any moment. Your first debugging step every time.
  • Designed for AEM: Core Components push to ACDL automatically. Your job is to extend this with additional pushes from custom component clientlibs.
The datalayer type is a project decision On Netcentric AEM projects you will use the ACDL. Never switch a project's datalayer type unilaterally — the Analytics Engineer's entire Tags configuration depends on the structure and naming already in place.

Adobe Analytics — where your data lands

Adobe Analytics is a digital analytics platform that collects, processes, and stores user interaction data from websites and mobile apps. From a developer's perspective it's the destination at the end of a five-step pipeline.

the complete data pipeline — user interaction to Analytics report1. USER INTERACTION
   A user performs an action on your site:
   Page view, click, form submit, purchase, search, video play

            ↓

2. DATA LAYER (ACDL)
   Your component captures the interaction and structures it:
   adobeDataLayer.push({
     "event": "formSubmit",
     "page":  { "pageInfo": { "pageName": "loan-application" } },
     "form":  { "name": "Loan Application", "step": "complete" }
   });

            ↓

3. ADOBE LAUNCH
   Listens for the event, evaluates rules, fires actions:
   EVENT:   ACDL push with event = "formSubmit"
   CONDITION: page.pageInfo.pageName contains "loan"
   ACTION:  Set eVar1 = page.pageInfo.pageName
            Set event5 (form complete counter)
            Send Analytics beacon (s.t() or s.tl())

            ↓

4. WebSDK / AppMeasurement
   The tracking library sends the HTTP request to Adobe's servers:
   WebSDK (Alloy.js)      → modern, sends to AEP Datastream
   AppMeasurement.js      → legacy, sends directly to tracking server

            ↓

5. ADOBE ANALYTICS
   Data is processed, stored, and available for reporting.
   Analysis Workspace shows the data within 30–90 minutes.
   Report Suites: always use a separate Dev suite for testing.
📖 Why this code?

This pipeline is the mental model to carry through all analytics work. Every problem can be located to one step in this chain.

  • Step 1 → 2 is your responsibility. The component must push to the datalayer with the right structure at the right time. A push that fires before the DOM is ready, or that uses the wrong key name, breaks everything downstream — silently.
  • Step 2 → 3 is the Analytics Engineer's responsibility. They configure Tags Data Elements and Rules against the datalayer paths you've established. They can only work with data that exists in the datalayer.
  • Step 3 → 4 is handled by the chosen extension (Analytics Extension uses AppMeasurement, Web SDK extension uses Alloy.js). Configured once in the extension setup; it handles serialisation and the HTTP request automatically.
  • Debugging flow: first check window.adobeDataLayer.getState() (step 2) — is your data there? Then use the AEP Debugger Chrome extension (step 3–4) — did Launch fire? Did the beacon contain the right values?
what Adobe Analytics is used for — the business problems it answersUNDERSTAND BEHAVIOUR
  Online banking:    which dashboard features do users actually use?
  E-commerce:        where in checkout do people abandon?
  Content sites:     which articles drive the most return visits?

IDENTIFY PROBLEMS
  Drop-offs in key journeys:
    40% of loan applicants exit on step 3 of 5 — is step 3 broken?
  Friction in login/authentication:
    Login error rate spiked after Tuesday's deploy — which commit?
  Low click-through on high-traffic pages:
    Product page gets 10k visits but CTA click rate is 2%

OPTIMISE
  A/B test (Adobe Target + Analytics) → does version B convert better?
  Device analysis → on which device type is bounce rate highest?
  Feature adoption → which features get used vs. which can be cut?

  The developer connection: you build the components that create
  these interactions. You write the datalayer pushes that make
  them measurable. Analytics accuracy starts with your code.
📖 Why this code?

This makes the connection between your developer work and real business decisions explicit — something that's easy to lose when you're focused on OSGi annotations and Sling Models.

  • "Which features do users actually use?" — only answerable if every feature interaction fires a datalayer push. A feature with no tracking is invisible to the business, regardless of how many users interact with it.
  • "Which commit caused the spike?" — Adobe Analytics timestamps every hit. If error events spiked at 14:32 and your deploy went out at 14:30, that correlation is visible in Workspace within hours. This is why tracking matters even for purely technical releases.
  • Adobe Target + Analytics — Adobe Target's A/B testing uses Adobe Analytics as its reporting source. If the conversion event is missing from the datalayer, Target can't determine which variant won.
Try it — inspect a live datalayer Open any AEM site with Core Components and ACDL enabled (or your local instance after enabling via OSGi config). Open the browser console and run window.adobeDataLayer.getState(). Look for page.pageInfo.pageName and page.pageInfo.language. Now click something on the page and run it again — did a new event appear? This is the raw material every Tags rule operates on.
