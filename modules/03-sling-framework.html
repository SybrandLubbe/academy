Sling Framework Fundamentals

In a typical backend framework you define routes. In Sling, the content tree already is the routing table — your job is understanding how a request finds its way to a script.

What you'll learn

  • How a URL is decomposed into path, selectors, extension, and suffix
  • How Sling turns that path into a Resource
  • How sling:resourceType decides what renders the resource
  • How script resolution order works, and how overlays use it

Decomposing a request URL

Sling parses every incoming URL into up to four parts before it does anything else:

URL anatomy/content/my-site/en/about.teaser.html/jcr:content/par/image
\__________ path __________/\selectors/\ext/\______ suffix _______/
  • Path — matched against the repository tree to find a starting resource. Sling walks the path looking for the longest segment that actually exists as a node; anything left over becomes the suffix.
  • Selectors — optional dot-separated tokens between the path and the extension (here, teaser). They let one resource render in different variants — a JSON API view versus an HTML view, for instance — without changing the underlying content.
  • Extension — usually html, but could be json, xml, or a custom one your code defines. It strongly influences which script or servlet handles the request.
  • Suffix — anything after the extension, passed through to your code as extra path info.

From path to Resource

Once the path is resolved, Sling produces a Resource object — a thin wrapper around the underlying JCR node (or, in principle, any other back-end Sling is configured to read from; the repository is the default and by far the most common one). Almost every Sling API you'll touch — in HTL, in a servlet, in a Sling Model — starts from a Resource or a ResourceResolver used to look one up.

resourceType decides the renderer

Every resource that should be rendered carries a sling:resourceType property, a path pointing at the component that knows how to render it. Sling takes that resource type, the selectors, and the extension, and searches for a matching script under /apps first, then /libs:

resourceType → script lookupsling:resourceType = "my-site/components/teaser"
extension = html, no selectors

Sling looks for, in order:
  /apps/my-site/components/teaser/teaser.html
  /apps/my-site/components/teaser/html.jsp
  /libs/my-site/components/teaser/teaser.html   (only if not found above)

This is the mechanism behind the "never edit /libs" rule from module 1: because /apps is searched first, recreating the same resource type path under /apps silently takes priority — that's an overlay, and it's the standard, supported way to customize out-of-the-box behavior.

Mental model sling:resourceType answers "what kind of thing is this?" Selectors and extension answer "which variant, in what format?" Together they're enough for Sling to find exactly one script.

resourceSuperType: inheritance for components

A component can declare a sling:resourceSuperType pointing to another component. If Sling can't find a script for the component's own resource type, it walks up to the super type and tries again — and it keeps walking until it finds a match or runs out of ancestors. This is how AEM components share and override rendering logic without copy-pasting markup, similar in spirit to class inheritance.

Servlets, briefly

Everything above describes script-based rendering, but the same resourceType-based resolution also applies to Java servlets registered against a resource type instead of a URL pattern — that's how AEM exposes most of its backend APIs. You'll build one yourself in module 10; for now, just know that "servlet" in AEM usually means "registered by resource type," not "registered by URL path" the way a typical Java web framework works.

Common pitfall Forgetting that script resolution checks /apps before /libs is a frequent source of "I changed the file but nothing happened" bugs — you may be editing the /libs copy while an overlay in /apps is quietly winning.
Try it Pick any component on a page you have access to, find its sling:resourceType in CRXDE Lite, then locate the matching script under /apps. Check whether it declares a sling:resourceSuperType and, if so, follow the chain.

Knowledge Check

Ten questions to ask students once they've finished this module — answers are hidden by default so you can quiz live before revealing them.

  1. What four parts does Sling decompose every incoming URL into?

    Show answer

    Path, selectors, extension, and suffix.

  2. In a URL like /content/my-site/en/about.teaser.html/jcr:content/par/image, identify the selector and the suffix.

    Show answer

    Selector = teaser; suffix = /jcr:content/par/image.

  3. What does Sling produce once the path portion is resolved against the repository?

    Show answer

    A Resource object — a thin wrapper around the underlying JCR node (or whatever backend Sling is configured to read from).

  4. What property tells Sling which component should render a resource?

    Show answer

    sling:resourceType.

  5. When resolving a script, which path does Sling search first — /apps or /libs?

    Show answer

    /apps first, then /libs.

  6. How does this search order make /apps overlays work, mechanically?

    Show answer

    Because /apps is searched first, recreating the same resourceType path under /apps silently takes priority over the /libs version.

  7. What does sling:resourceSuperType let a component do?

    Show answer

    Declare another component as its "super type" — if Sling can't find a script for the component's own resourceType, it walks up to the super type and tries again, similar to class inheritance.

  8. In AEM, what does "servlet" usually mean — registered by URL path or by resource type?

    Show answer

    Usually registered by resource type, unlike a typical Java web framework's URL-path routing (though path-based registration is also possible).

  9. What's the classic symptom of editing the /libs copy of a script while an /apps overlay quietly wins?

    Show answer

    "I changed the file but nothing happened" — the change has no visible effect because /apps is resolved first.

  10. Besides resourceType and selectors, what else strongly influences which script or servlet handles a request?

    Show answer

    The extension (usually html, but could be json, xml, or a custom one).
