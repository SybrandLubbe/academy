Sling Framework Fundamentals

In most backend frameworks you write a router — a list of URL patterns matched to handler functions. In Sling there is no router. The repository tree is the routing table, and understanding this idea unlocks almost everything else about how AEM works.

What you'll learn

  • How Sling breaks a URL into four distinct parts — and what each one does
  • What a Resource is and why it is the central object in all of Sling
  • How sling:resourceType connects content to the code that renders it
  • Why scripts are looked up in /apps before /libs, and how that makes overlays work
  • What sling:resourceSuperType (component inheritance) means in practice

Start here: what Sling actually is

AEM is built on top of Apache Sling, a web framework with one central idea: every URL points to a piece of content, and that content knows how to render itself.

In a Spring or Express app you would write something like @GetMapping("/about") to attach a handler to a URL. In Sling you never do that. Instead, when a request arrives for /content/my-site/en/about, Sling walks straight into the repository, finds the node living at that path, reads a property on it called sling:resourceType, and uses that to decide which script renders the response. There is no separate routing table to maintain.

Analogy Think of a library. Every book has a Dewey Decimal number that tells the librarian exactly which shelf it lives on and which librarian specialises in that category. In Sling, the URL path is the Dewey Decimal number, the repository node is the book, and sling:resourceType is the category that tells Sling which specialist (script) handles it.

Step 1 — Breaking the URL apart

Before Sling does anything else it parses the incoming URL into up to four pieces. Knowing these pieces by heart will save you hours of debugging:

URL anatomy — read this slowlyhttps://localhost:4502/content/my-site/en/about.print.html/extra/info

                        ↓ path ↓      ↓sel↓ ↓ext↓ ↓── suffix ──↓
                /content/my-site/en/about . print . html / extra/info
📖 Why this code?

Sling parses every incoming URL before doing anything else. Knowing which part is which is essential for debugging "why is Sling calling the wrong script?" problems.

  • Path (/content/my-site/en/about) — maps to a node in the JCR repository. This is the primary key for content lookup.
  • Selector (print) — one or more dot-separated words before the extension. They let you serve different representations of the same content (print view, thumbnail, mobile) without duplicating content nodes.
  • Extension (html) — tells Sling the expected output format. Combined with the selector, it determines which script file is picked.
  • Suffix (/extra/info) — arbitrary extra path data your script can read via request.getRequestPathInfo().getSuffix(). Commonly used to pass a secondary resource path to a servlet.
  • Path — /content/my-site/en/about. Sling uses this to find a node in the JCR repository. No node at that path means a 404.
  • Selector(s) — print. Zero or more dot-separated words that appear before the extension. They let one resource render differently depending on context — about.print.html might render a printer-friendly version while about.html renders the normal page, both reading the same content node.
  • Extension — html. Usually html but can be json, xml, or anything you define. It participates in script resolution.
  • Suffix — /extra/info. Everything after the extension, passed to your script as extra context. Often used to pass a secondary path.
Quick quiz yourself In the URL /content/site/page.mobile.json/section/hero — what is the selector? What is the extension? What is the suffix?

Answer: selector = mobile, extension = json, suffix = /section/hero.

Step 2 — The path becomes a Resource

Once Sling has the path it looks up the matching node in the JCR repository and wraps it in a Resource object. This is the most important object in all of Sling — every API you'll write (models, servlets, HTL scripts) starts here.

Think of a Resource as a box with two things inside:

  • A path — where this node lives in the tree (e.g. /content/my-site/en/about/jcr:content)
  • A ValueMap — a map of every property on that node, readable as typed Java values
reading a Resource in Java — this is what a Sling Model does for you automaticallyResource resource = request.getResource();

// path
String path = resource.getPath(); // "/content/my-site/en/about/jcr:content"

// read any property by name
ValueMap props = resource.getValueMap();
String title  = props.get("jcr:title", String.class);   // "About Us"
boolean hide  = props.get("hideInNav", false);           // false
📖 Why this code?

This shows what a Resource object is and how to read data from it manually. In practice, Sling Models (module 6) handle all of this for you automatically via @ValueMapValue — but understanding the underlying API makes debugging far easier.

  • request.getResource() — returns the Resource that corresponds to the URL's path segment. This is the central object in all of Sling.
  • resource.getValueMap() — returns a read-only Map<String, Object> of every JCR property on this node. The two-argument get(key, defaultValue) form both reads the property and coerces it to the right type.
  • The comment "this is what a Sling Model does for you automatically" is the key insight: @ValueMapValue private String title is just a cleaner way to write props.get("title", String.class).

You will never call most of this by hand — Sling Models (module 6) do it for you automatically via @ValueMapValue. But understanding that a Resource is just "a path + a bag of properties" is the mental model that makes everything else click.

Step 3 — resourceType decides what renders it

Every content node that should be rendered on a page carries a property called sling:resourceType. Its value is a path to a component — a folder under /apps (or /libs) that contains the render script.

a content node in CRXDE Lite — what you'd actually see/content/my-site/en/about/jcr:content/par/teaser
  sling:resourceType = "my-site/components/teaser"   ← this is the key property
  jcr:title          = "Welcome to our site"
  image              = "/content/dam/images/hero.jpg"
📖 Why this code?

This is what a content node looks like in CRXDE Lite — the data structure a Sling Model reads from when it processes a Teaser component.

  • sling:resourceType = "my-site/components/teaser" — the most important property on any content node. Sling reads this to decide which script (or servlet) handles rendering. Without it, Sling can't render the node.
  • jcr:title and image — plain JCR properties storing the author's input. These are what @ValueMapValue reads in your model.
  • The node path (/content/.../par/teaser) is both the URL path and the repository path — in Sling, they're the same thing.

When Sling sees this node, it reads sling:resourceType and now knows: "I need to find the script for my-site/components/teaser." It then combines that with the selectors and extension from the URL to find one specific script:

how Sling finds the right script — step by stepRequest: GET /content/my-site/en/about.html
Content node has: sling:resourceType = "my-site/components/teaser"
Extension: html, no selectors

Sling searches these locations in order, stopping at the first match:
  1. /apps/my-site/components/teaser/teaser.html   ← your custom script
  2. /apps/my-site/components/teaser/html.jsp       (older JSP format)
  3. /libs/my-site/components/teaser/teaser.html   ← Adobe's default (only if 1 and 2 don't exist)
📖 Why this code?

This is the script resolution algorithm — the exact lookup Sling performs on every request to decide which file renders the output.

  • Sling always checks /apps first, then /libs. This order is fixed and not configurable — it's the foundation of the overlay pattern.
  • The filename convention is componentName.html for the default script. If a selector is present (e.g. print), Sling looks for componentName.print.html first.
  • Sling stops at the first match. If your /apps version exists, the /libs version is never even looked at — which is exactly why overlays work without any explicit "override" declaration.
This is the key rule /apps is always searched first, before /libs. This is not configurable — it is how Sling works. Keep this in mind; it explains a lot of "mysterious" AEM behaviour.

What is /libs and why can't I edit it?

Adobe ships all of AEM's built-in components, workflows, and UI inside /libs. You must never edit anything under /libs — not because AEM physically stops you, but because every AEM upgrade or hotfix overwrites /libs completely. Your edit would silently disappear.

The correct approach is to create your own copy of the same path under /apps. Because /apps is searched first, your copy wins automatically. This is called an overlay.

example: overlaying an Adobe component to change one thingAdobe's original:   /libs/core/wcm/components/text/v2/text/text.html
Your overlay:       /apps/core/wcm/components/text/v2/text/text.html  ← same path, under /apps

Sling finds /apps version first → Adobe's original is completely ignored.
You only change what you need; for everything else, use resourceSuperType to fall back.
📖 Why this code?

This is the overlay pattern in its simplest form. By recreating a file at the same relative path under /apps, your version silently takes priority over Adobe's.

  • The path structure under /apps must mirror the path under /libs exactly — same folder names, same filename. Sling's lookup is purely path-based.
  • You don't need to copy the entire script. If you only want to change one small block, you can use sling:resourceSuperType on your component to inherit everything from the original and only override what's different.
  • This pattern is why AEM recommends sling:resourceSuperType pointing to Core Components rather than copying their code — upgrades to Core Components automatically benefit your component via inheritance, whereas a copy receives no updates.
The most common beginner mistake Editing a file under /libs directly (via CRXDE Lite), then wondering why the change "disappeared" after the next AEM service pack. Always work under /apps.

sling:resourceSuperType — component inheritance

Imagine you want to build a custom Teaser component that is mostly identical to Adobe's Core Teaser, but with one extra field. You do not want to copy 500 lines of HTL. Instead, you declare your component as a child of the Core Teaser:

your custom teaser .content.xml<jcr:root
    jcr:primaryType="cq:Component"
    jcr:title="Academy Teaser"
    componentGroup="Academy Training"
    sling:resourceSuperType="core/wcm/components/teaser/v2/teaser"/>
                                        ↑ inherits ALL scripts from here
📖 Why this code?

This is the component definition file — the XML that makes a folder under /apps an actual AEM component rather than just a directory.

  • jcr:primaryType="cq:Component" — the node type that declares "this is a component." Without it, the folder is invisible to the AEM component system.
  • jcr:title="Academy Teaser" — the human-readable name shown in the author's "Insert Component" browser.
  • componentGroup="Academy Training" — the group label under which this component appears in the browser. Template policies also use this group name to allow or disallow components (module 11).
  • sling:resourceSuperType="core/wcm/components/teaser/v2/teaser" — declares that this component inherits all scripts and dialogs from the Core Teaser. Your component only needs to define what's different.

Now when Sling looks for teaser.html for your component and finds nothing, it walks up to core/wcm/components/teaser/v2/teaser and tries again. The chain keeps walking until a match is found. You only need to add the scripts that are different — everything else is inherited for free.

Selectors: one URL, many views

Selectors let you serve multiple representations of the same content node without duplicating content or URLs. A common real-world pattern:

selector-based script resolution in practiceGET /content/site/page.html          → teaser/teaser.html      (normal render)
GET /content/site/page.print.html    → teaser/print.html        (printer-friendly)
GET /content/site/page.thumbnail.html→ teaser/thumbnail.html    (small card view)
GET /content/site/page.json          → your servlet or .model.json exporter

All four URLs point to the SAME content node. Only the selector (and extension) change.
📖 Why this code?

This table shows how selectors let a single content node serve completely different output formats without any conditional logic in the content itself.

  • The content node is the same for all four URLs — only the selector and extension change in the URL. Sling routes each to a different script file based purely on the URL structure.
  • This is far cleaner than ?format=print query parameters: selectors are part of the path, so they can be cached by the dispatcher, included in static URLs, and handled by Sling's script resolution rather than by if/else in your code.
  • The .json extension (with no selector) is typically handled by either a registered servlet or the .model.json Sling Models exporter — not by an HTL script.

Servlets follow the same rules

So far we've only talked about scripts (HTL files). But Java servlets in AEM use the exact same resolution mechanism. Instead of a .html file, a servlet registers itself against a resource type, a selector, and an extension, and Sling routes requests to it using the same lookup process. You'll build one in module 10 — for now, just know that "there's only one routing mechanism in all of Sling."

Try it — 15 minutes
  1. Open CRXDE Lite at localhost:4502/crx/de.
  2. Navigate to any page's jcr:content node (e.g. /content/we-retail/us/en/men/jcr:content).
  3. Find the sling:resourceType property. Note its value.
  4. Now open that path under /apps (or /libs) in the tree and find the render script.
  5. Does the component declare a sling:resourceSuperType? If so, follow the chain one level up.
