Adobe Launch — Architecture & Rules

Adobe Launch (Tags) is a central platform to manage and deploy marketing and analytics scripts without a code deploy for every change. It listens to user interactions, reads data from the datalayer, and decides when and what data to send to Analytics, Target, and any other destination. This module covers how it actually works — the full architecture from event to destination.

What you'll learn

  • What Launch is and its three core characteristics
  • The full 6-step architecture: event → datalayer → Launch → rules → actions → destinations
  • Data Elements — all 8 types and when to use each
  • Rules — Events, Conditions, and Actions in detail
  • Extensions — what they are and which ones matter
  • Environments, publishing workflow, and AEM Cloud Services integration

What is Adobe Launch?

Adobe Launch (officially: Adobe Experience Platform Tags) is a tag management system — a JavaScript runtime that loads on every page and acts as a central coordinator for all marketing and analytics scripts. Instead of each tracking tool adding its own script tag to your HTML, Launch loads once and handles everything.

what Launch is and what it gives youRULE-BASED ENGINE
  Executes logic using Event → Condition → Action framework.
  Example:
    EVENT:     Page loads (Library Loaded)
    CONDITION: URL contains "/checkout/"
    ACTION:    Set eVar5 = "checkout", send Analytics beacon

DECOUPLES TRACKING FROM CODE
  Analytics and marketing logic managed independently
  of the website code.
  → Marketing team adds a new event rule on Tuesday.
  → Developer doesn't touch a single file.
  → No deploy. No ticket. No waiting.

FLEXIBLE & SCALABLE DEPLOYMENT
  Environment-based: Development / Staging / Production
    Each environment has its own embed code URL.
    Changes are promoted through environments with approval.
  Version-controlled publishing workflow:
    Every published build is versioned and rollback is instant.

KEY BENEFITS
  ✓ Tag governance and consistency across all pages
  ✓ No code changes for tag updates
  ✓ Reusable components (Data Elements used across many Rules)
  ✓ Powerful rules and conditions
  ✓ Extensible with 200+ extensions in the catalog
📖 Why this code?

The three characteristics — rule-based, decoupled, environment-based — are what make Launch different from just adding script tags to a page template.

  • Rule-based — without a rule engine, every tracking requirement means a code change. With Launch, the Analytics Engineer writes a Rule; no developer involved. This is the entire value proposition.
  • Decoupled from code — the embed code is added to AEM's Cloud Services config once and never changes. The Launch library it loads changes constantly as the Analytics team updates Rules and Data Elements — but none of those changes require a developer.
  • Environment-based deployment — the Dev embed URL loads a library that changes instantly when you save a rule. The Prod embed URL only changes after a formal publish workflow. This means you can develop and test rules without touching production data.

The full Launch architecture — 6 steps

Every analytics interaction follows this exact sequence. Understanding each step tells you where to look when something isn't working.

Adobe Launch architecture — the complete flowSTEP 1: EVENT OCCURS
  User Interaction: Page View, Click, Form Submit, Purchase
  System/App Event: History Change (SPA navigation), Error, Timer

          ↓

STEP 2: DATA PUSHED TO DATALAYER (ACDL)
  adobeDataLayer.push({
    "event": "productView",
    "pageName": "Product Detail",
    "product": {
      "id":       "12345",
      "name":     "Running Shoes",
      "price":    129.99,
      "category": "Footwear"
    },
    "user": {
      "loggedIn": true,
      "userId":   "abc123"
    }
  });

          ↓

STEP 3: LAUNCH RECEIVES THE EVENT AND LOADS DATA ELEMENTS
  The ACDL extension fires "productView" event into Launch.
  Launch evaluates all Rules whose event matches.
  Data Elements resolve their values from defined sources.

          ↓

STEP 4: RULES EVALUATE EVENT + CONDITIONS
  RULE: "Track Product Views"
  EVENT:     ACDL push — event = "productView"
  CONDITION: pageName equals "Product Detail"
             AND user.loggedIn equals true
  → If ALL conditions are met, rule fires.

          ↓

STEP 5: ACTIONS ARE TRIGGERED
  If matched:
    Set eVar1  = %Page Name%          (Data Element)
    Set eVar10 = %Product Name%       (Data Element)
    Set event2 = product view counter
    Send Beacon → s.t()

          ↓

STEP 6: EXTENSIONS EXECUTE AND SEND TO DESTINATIONS
  Adobe Analytics Extension → sends to Report Suite
  Adobe Target Extension    → personalisation decisions
  Google Analytics          → GA4 event stream
  Custom Code               → any custom JavaScript
📖 Why this code?

This 6-step flow is the complete mental model for debugging any Launch/Analytics issue. Every problem lives at exactly one of these steps.

  • Step 1 → 2: developer responsibility. The component must push the right data at the right time. If the push is missing or malformed, nothing else in the chain works.
  • Step 3: Data Elements resolve their values. A Data Element of type "Data Layer Variable" reads product.name from the ACDL state. If it returns undefined, check whether the push happened before or after Launch tried to read it.
  • Step 4 → Conditions: conditions are AND by default (all must pass). A condition that fails silently stops the rule — no error, no beacon. The AEP Debugger shows exactly which condition failed.
  • Step 5 → Actions: %Page Name% syntax references a Data Element by name. At execution time Launch substitutes the DE's current value. If the DE returned undefined, eVar1 will be empty.
  • Step 6 → Extensions: the extension is what sends the actual HTTP request. The Analytics Extension sends an AppMeasurement beacon; the Web SDK extension sends an XDM payload to an AEP Datastream.

Data Elements — all 8 types

Data Elements are named variables that retrieve values from various sources. They're the reusable building blocks of your Launch implementation — define a value once, use it in any number of Rules.

all 8 Data Element types — when to use each1. DATA LAYER VARIABLE (ACDL)    ← use this most often on AEM
   Source: Adobe Client Data Layer (window.adobeDataLayer)
   Path:   page.pageInfo.pageName
   → Reads from ACDL's computed state. Best option for all
     values pushed by Core Components and your custom pushes.

2. JAVASCRIPT VARIABLE
   Source: any global JavaScript variable
   Path:   window.digitalData.page.pageInfo.pageName
   → Use for legacy digitalData implementations or any custom
     global variable. Also useful for debugging:
     window.adobeDataLayer.getState().page.pageInfo.pageName

3. DOM ELEMENT
   Source: a CSS selector targeting an element's text or attribute
   Selector: .product-price
   Attribute: data-product-id
   → Avoid where possible — DOM structure changes silently break it.
     Use only when no datalayer alternative exists.

4. COOKIE
   Source: a browser cookie by name
   Cookie Name: session_id
   → Use for session identifiers, A/B test assignments,
     or consent state stored in cookies.

5. URL VARIABLE  (protocol / hostname / pathname / query / hash)
   Source: window.location
   Component: query parameter
   Name: utm_source
   → Use for UTM parameter attribution and URL-based conditions.
     Reads from the current page URL at rule execution time.

6. CONSTANT
   Source: a hardcoded value you define in Launch
   Value: "Netcentric Banking Site"
   → Use for values that never change per environment: site name,
     brand ID, or report suite ID (though RSIDs are usually in
     the Analytics extension config, not a DE).

7. LOCAL STORAGE
   Source: window.localStorage.getItem(key)
   Key: user_preference_theme
   → Use for values persisted across sessions client-side:
     user preferences, cached profile data, feature flags.

8. LOOKUP TABLE
   Source: a map of input → output defined in Launch
   Input Data Element: %Page Template%
   Lookup Table:
     "article"   → "Content"
     "product"   → "Commerce"
     "home"      → "Navigation"
   → Use to translate technical values into analytics-friendly labels
     without touching site code.
📖 Why this code?

Data Elements are the "read" half of Launch — they define where values come from. Understanding all 8 types means you can always find a way to get the right data without asking a developer to change the site.

  • Data Layer Variable vs JavaScript Variable — both read from JavaScript, but Data Layer Variable uses ACDL's getState() which merges all pushes into one consistent snapshot. JavaScript Variable reads directly from whatever the path returns at the moment of evaluation — which might be stale or undefined if the push hasn't happened yet.
  • DOM Element — listed last for a reason. It's the most fragile type. A class rename, a DOM restructure, or a React re-render can all break it silently. Use it only as a last resort when no datalayer value exists.
  • Lookup Table — one of the most underused types. Instead of asking a developer to add a new "contentCategory" property to every page's datalayer push, the Analytics Engineer creates a Lookup Table that maps the existing page.pageInfo.template value to a category label. Zero code change.
  • URL Variable for UTM parameters — this is how channel attribution works. The Data Element reads utm_source from the query string; a rule on Page Load fires and stores it in an eVar for cross-page tracking.

Rules — Events, Conditions, Actions

A Rule is the core unit of Launch logic. It answers: When should something happen? Under what conditions? What should be done? Every tracking requirement maps to at least one Rule.

complete Rule anatomy — page view tracking exampleRULE: "Send Page View to Analytics"

─── EVENT (when does this rule check?) ────────────────────
Extension:  Core
Event Type: Library Loaded (Page Top)
  → fires when the Launch library executes on any page
  Other common event types:
    DOM Ready          → after HTML is parsed, before images load
    Window Loaded      → after all resources (images, scripts) load
    Click              → on a CSS selector match
    ACDL Event         → when adobeDataLayer.push({ event: "X" }) fires
    Custom Event       → any custom JS event dispatched via document

─── CONDITIONS (should this rule fire?) ───────────────────
Condition type: Value Comparison
  Left operand:  %Page Template%         (Data Element)
  Operator:      does not equal
  Right operand: "error"
  → don't track 404/500 error pages as page views

Conditions can be:
  ALL (AND) — every condition must pass (default)
  ANY (OR)  — at least one condition must pass

─── ACTIONS (what should happen?) ─────────────────────────
Action 1: Adobe Analytics — Set Variables
  eVar1  = %Page Name%        (resolved from Data Element)
  eVar2  = %User Login Status%
  eVar3  = %Page Template%
  events = event1             (page view counter)

Action 2: Adobe Analytics — Send Beacon
  Tracking Type: Page View (s.t())
  → s.t() increments Page Views metric
  → s.tl() does NOT increment Page Views (for interactions)
📖 Why this code?

The Event → Condition → Action pattern maps directly to the OSGi patterns from earlier modules — and is equally important to understand completely.

  • Event types matter — "Library Loaded" fires before the DOM exists (fastest, for page-level data already in the ACDL). "DOM Ready" fires after parsing (use for DOM-dependent Data Elements). "Window Loaded" fires last (use only if you must wait for all resources). Using the wrong event type is a common source of "DE returned undefined" bugs.
  • Conditions are guards — they prevent Rules from firing in unwanted contexts. A page view rule that fires on error pages counts error views as valid sessions, inflating every metric. Always guard your page view rule against error templates.
  • Set Variables always before Send Beacon — these must be separate Actions, in this order. Set Variables populates the Analytics object (s.eVar1). Send Beacon then fires. If you merge them or reverse the order, variables aren't set when the beacon sends.
  • s.t() vs s.tl() — s.t() is a Page View call: increments the "Page Views" metric, resets visit timeout, and uses the full variable set. s.tl() is a Link Tracking call: does NOT increment Page Views, but records the event. Use s.tl() for clicks, downloads, form submits — any interaction that isn't a new page load.
a second Rule — custom event tracking (click / form submit)RULE: "Track CTA Click"

EVENT:
  Extension:  Adobe Client Data Layer
  Event Type: Data Pushed (Event Listener)
  Event Name: cta:click       ← matches the "event" key in the ACDL push

  Your component clientlib fires this push on click:
  document.querySelector('.cta-button').addEventListener('click', () => {
    window.adobeDataLayer.push({
      "event": "cta:click",
      "eventInfo": {
        "path": "component.hero-cta",
        "value": {
          "ctaLabel": "Apply Now",
          "ctaTarget": "/loan-application"
        }
      }
    });
  });

CONDITIONS:
  (none — track all CTA clicks)

ACTIONS:
  Action 1: Adobe Analytics — Set Variables
    eVar20 = %CTA Label%        (DE reads eventInfo.value.ctaLabel)
    eVar21 = %CTA Target%       (DE reads eventInfo.value.ctaTarget)
    events = event10            (CTA click counter)

  Action 2: Adobe Analytics — Send Beacon
    Tracking Type: Custom Link (s.tl())
    Link Name: %CTA Label%
📖 Why this code?

This is the complete pattern for tracking any user interaction that isn't a page load. The developer writes the ACDL push; the Analytics Engineer writes the Rule. These are separate, independent concerns.

  • window.adobeDataLayer.push({ "event": "cta:click", ... }) — your component clientlib fires this on every CTA button click. This is the entirety of the developer's responsibility for this interaction. You don't call any Analytics functions directly.
  • event: "cta:click" — the exact string that the Launch Rule's "ACDL Event Listener" listens for. The Analytics Engineer configures this in Launch; it must match exactly what your push sends (case-sensitive).
  • eventInfo.value.ctaLabel — Data Elements of type "Data Layer Variable" read from the pushed object's path. The Analytics Engineer creates a DE "CTA Label" pointing to eventInfo.value.ctaLabel. Your push populates it; their rule reads it.
  • s.tl() for clicks — this is a link tracking call, not a page view. It increments event10 (the click counter) but does NOT increment Page Views, which is correct: clicking a button is not a new page view.

Extensions

Extensions are plugins that add capabilities to a Launch Property. They provide the Events, Conditions, Actions, and Data Element types available when building Rules. Without an extension installed, you can't use its capabilities.

the key extensions — what each providesCORE (always installed, required)
  Provides: standard event types (Library Loaded, DOM Ready,
            Click, Custom Event), basic condition types,
            and JavaScript Variable DE type.
  → This is the foundation. Every other extension builds on it.

ADOBE CLIENT DATA LAYER
  Provides: "Data Layer Variable" DE type (reads from ACDL),
            "ACDL Event Listener" event type (fires on push events).
  → Install this on every AEM + Launch project.

ADOBE ANALYTICS
  Provides: "Set Variables" action, "Send Beacon" action,
            "Clear Variables" action.
  Config:   Report Suite ID, Tracking Server, Character Set.
  → The AppMeasurement.js route. Sends data to Adobe Analytics.

ADOBE EXPERIENCE PLATFORM WEB SDK (Alloy.js)
  Provides: "Send Event" action (XDM format), "Apply Propositions" (Target).
  Config:   Datastream ID (configured in AEP, not in Launch).
  → The modern route. One beacon reaches Analytics + Target + RTCDP.
  → Use for all greenfield projects.

ADOBE TARGET
  Provides: "Load Target" action, "Add Params to All Requests".
  → A/B testing and personalisation. Uses Analytics as its reporting source.

CUSTOM CODE (from Core extension)
  Provides: run arbitrary JavaScript inside a rule.
  → Use only when no standard action covers your need.
    Everything in Custom Code is invisible to Launch's audit log.
📖 Why this code?

Extensions are the reason Launch has 200+ integrations without each one requiring a custom build. Each extension packages one tool's tracking logic into a reusable set of Launch building blocks.

  • Core extension — can't be removed. It provides the fundamental event types (Library Loaded, DOM Ready, Click) and the JavaScript Variable DE type. Everything else is optional.
  • ACDL extension — the bridge between your AEM datalayer and Launch. Without it, the only way to read ACDL data is via a JavaScript Variable DE using window.adobeDataLayer.getState().some.path — which works but loses the reactive event listener capability.
  • Analytics vs Web SDK — they're mutually exclusive approaches. You either send AppMeasurement beacons (Analytics Extension) OR XDM payloads to a Datastream (Web SDK). Using both creates double-counting in reports.
  • Custom Code — a trap for the unwary. Code written here is invisible to Launch's change log, can't be referenced as a Data Element, and makes auditing the implementation impossible. Use it only when a standard action genuinely doesn't exist.

Environments and publishing workflow

environments — the three embed URLs and how publishing flowsDEVELOPMENT
  Embed: https://assets.adobedtm.com/...launch-xxx-development.js
  Behaviour: changes appear immediately after saving — no publish step.
  Load in: AEM author instance (via Cloud Services run-mode config).
  Use for: rule development, Data Element iteration, local testing.

STAGING
  Embed: https://assets.adobedtm.com/...launch-xxx-staging.min.js
  Behaviour: requires Submit → Approve → Build to Staging workflow.
  Load in: non-production AEM publish instances.
  Use for: QA against production content, stakeholder sign-off.

PRODUCTION
  Embed: https://assets.adobedtm.com/...launch-xxx-min.js
  Behaviour: requires Promote to Production → Approve → Build workflow.
  Load in: production AEM publish instances.
  Use for: the live site — always minified, always approved.

IMPORTANT:
  Never load Development embed on production — it's unminified,
  larger, and may contain in-progress rules not fit for end users.

  Changing what the embed URL does (rules, DEs, extensions)
  → managed entirely in Launch, no AEM deploy needed.

  Changing which embed URL AEM loads (Dev → Staging → Prod)
  → requires an AEM Cloud Services config update + AEM deploy.
📖 Why this code?

The environment distinction is where most implementation mistakes happen — using the dev embed in production, or not realising that promoting to staging requires an explicit build.

  • Development "saves immediately" — this is intentional for iteration speed. You save a rule change in Launch and it's live on the dev embed within seconds. No build, no approval. The trade-off: dev is not suitable for production because it's unsecured and unminified.
  • Staging and Production require builds — each build creates a versioned, immutable snapshot of your entire Launch library. If a bad rule makes it to production, you roll back to the previous build in one click — no re-deployment of AEM needed.
  • AEM Cloud Services stores the embed URL per run-mode — AEM's page component reads this config and injects the correct <script> tag. The author instance reads development.uri; the publish instance reads production.uri. A developer changes which URI is loaded by updating the Cloud Services config and deploying AEM — this is the one part that requires a developer.

AEM Cloud Services integration

wiring Launch to AEM — what to configure and where1. ENABLE THE ACDL (one OSGi config, once per project)
   File: ui.config/.../config/
         com.adobe.cq.wcm.core.components.internal.services.DataLayerConfig.cfg.json
   Content: { "enabled": true }
   → Core Components will now push page and component data to ACDL.

2. CONFIGURE CLOUD SERVICES (in AEM Author UI)
   Tools → Cloud Services → Adobe Experience Platform Launch → Create
   Production:   https://assets.adobedtm.com/...launch-prod.min.js
   Staging:      https://assets.adobedtm.com/...launch-staging.min.js
   Development:  https://assets.adobedtm.com/...launch-dev.js
   proxyEnabled: true  (serves JS through AEM, avoids ad-blockers)

3. ASSIGN TO YOUR SITE
   Set sling:configRef on /content/your-site → /conf/your-site
   OR via Page Properties → Cloud Services tab on the root page.
   → AEM Core Components' Page template reads this config and
     injects the correct script tag in <head> automatically.

4. VERIFY
   Open any page in browser → open AEP Debugger extension
   Launch tab: Container loaded = YES
   Check which library URL loaded (dev/staging/prod)
📖 Why this code?

These four steps are the full developer checklist for wiring Launch to a new AEM project. Steps 1 and 2 are done once; step 3 assigns the config to the content tree.

  • Step 1 — OSGi config: without this, Core Components output no ACDL JavaScript at all. The datalayer simply doesn't exist on the page, and all Tags Data Elements of type "Data Layer Variable" return undefined.
  • Step 2 — proxyEnabled: with this true, AEM serves the Launch library from its own domain instead of assets.adobedtm.com. Browser ad-blockers commonly block third-party marketing scripts but won't block a first-party AEM URL. Essential for accurate tracking in markets with high ad-blocker usage.
  • Step 3 — sling:configRef: this is the Context-Aware Config mechanism from module 15. The page component reads the nearest CA Config for the current content path. Set it at the root of your content tree (/content/your-site) and every page beneath inherits it.
  • Step 4 — AEP Debugger: the Chrome extension is the simplest way to verify the integration. If "Container loaded" is YES, the embed code is working. If it's NO, check the Cloud Services config and the proxyEnabled setting.

Testing the full pipeline

verification checklist — from datalayer to Analytics beaconSTEP 1: Verify the datalayer
  Browser console: window.adobeDataLayer.getState()
  ✓ page.pageInfo.pageName is set and correct
  ✓ user.loginStatus is present (if expected)
  ✓ Event-specific data appears after triggering the interaction

STEP 2: Verify Launch loaded
  AEP Debugger → Launch tab
  ✓ Container loaded: YES
  ✓ Library URL: matches your expected environment (dev/staging/prod)
  ✓ Rules fired: list shows "Send Page View" (or your rule name)
  ✗ If rules didn't fire: expand the rule to see which condition failed

STEP 3: Verify the Analytics beacon
  AEP Debugger → Analytics tab
  ✓ Report Suite: correct ID (not accidentally using prod suite in dev)
  ✓ eVar1: matches the page name from the datalayer
  ✓ Events: event1 (or your configured events)
  ✓ Beacon type: s.t() for page views, s.tl() for interactions

STEP 4: Network tab verification (ground truth)
  Filter: b/ss/
  → These are the Analytics HTTP requests to the tracking server
  Query parameters contain all variables in raw form:
    v1=banking%3Adashboard     ← eVar1
    events=event1              ← events
    pageName=banking%3Adashboard
📖 Why this code?

This checklist isolates the problem to one step in the chain. Never jump straight to the Analytics interface to debug — by the time data appears there (30–90 min delay), you've lost context.

  • Step 1 first — if getState() doesn't contain what you expect, the problem is in your component's clientlib push. Everything else is irrelevant until step 1 is correct.
  • Step 2 before step 3 — if Launch didn't load (container = NO), no rule will ever fire. Check the Cloud Services config. If Launch loaded but the rule didn't fire, expand it in the Debugger to see the condition that prevented it.
  • Step 3 vs step 4 — the Debugger's Analytics tab decodes the beacon for readability. The Network tab shows the raw URL-encoded query string, which is what Adobe's servers actually received. Use the Network tab when the Debugger gives confusing results.
  • b/ss/ — the URL path pattern for Analytics beacons. Every hit goes to https://your-company.sc.omtrdc.net/b/ss/report-suite-id/.... Filtering for this pattern in DevTools shows only Analytics traffic, not the hundreds of other network requests on a typical page.
Try it — trace the full pipeline
  1. Enable the ACDL (OSGi config) and deploy to your local AEM instance.
  2. Open a page → console → window.adobeDataLayer.getState(). Confirm page.pageInfo.pageName exists.
  3. In your Launch Property (Development environment), create a Data Element "Page Name" of type Data Layer Variable, path page.pageInfo.pageName.
  4. Create a Rule: Library Loaded → Set Variables (eVar1 = %Page Name%) → Send Beacon (s.t()).
  5. Open AEP Debugger. Launch tab: container loaded? Analytics tab: eVar1 correct?
  6. Network tab: filter b/ss/ — does the beacon contain v1= with your page name?
