Implementing Adobe Tags in AEM

The Tag Property is ready. Now it needs real data from your AEM pages. This module wires the Adobe Client Data Layer — built into AEM Core Components — to Tags Data Elements and Rules, covering the complete pipeline from page content to analytics beacon.

What you'll learn

  • What the Adobe Client Data Layer (ACDL) is and what Core Components push to it
  • Enabling the ACDL via OSGi config and loading Tags via Cloud Services
  • Data Elements that read from the ACDL
  • Custom event tracking — pushing from component clientlibs
  • Testing with the Adobe Experience Platform Debugger
  • Analytics Extension vs Web SDK — which to choose

The Adobe Client Data Layer (ACDL)

The ACDL is a JavaScript object (window.adobeDataLayer) that AEM Core Components populate on every page. Instead of Tags scraping text from the DOM (fragile) or hard-coding values in rules (unmaintainable), Tags reads structured data from the ACDL.

what the ACDL contains — inspect via browser consolewindow.adobeDataLayer.getState()

// Returns:
{
  "page": {
    "pageInfo": {
      "pageName":      "Academy — Home",
      "pageID":        "/content/academy/en",
      "destinationURL":"https://training.netcentric.com/en.html",
      "language":      "en-GB",
      "template":      "academy/components/page"
    },
    "category": {
      "siteID":          "academy",
      "primaryCategory": "Home"
    }
  },
  "component": {
    "/content/academy/en/jcr:content/root/hero": {
      "name":  "Hero Image",
      "title": "Welcome to Academy Training",
      "type":  "academy/components/hero"
    }
  },
  "user": { "loginStatus": "anonymous" }
}
📖 Why this code?

The ACDL is an open specification Adobe contributed to the W3C — not proprietary. Any Core Component or custom component can push to it.

  • window.adobeDataLayer is a JavaScript array with push() and getState() methods. Core Components push their data as inline script blocks during server-side rendering.
  • getState() returns the merged state of all pushes so far. Always use this in the browser console to see exactly what data Tags has access to at any point in the page lifecycle.

Enabling the ACDL

/aem-academy/ui.config/.../config/com.adobe.cq.wcm.core.components.internal.services.DataLayerConfig.cfg.json (academy.ui.config){
    "enabled": true,
    "skipDataLayerForInvisibleNodes": true
}
📖 Why this code?

One OSGi config enables the ACDL globally — the same config pattern from modules 4 and 5.

  • "enabled": true — activates ACDL output in Core Components. With false, no data layer JavaScript is included in component output.
  • Place in config/ for all environments, or config.publish/ if you only want ACDL active on publish (some teams disable it on author to reduce noise in Tag management tools).

Loading Tags via Cloud Services

AEM Cloud Services config for Tags embedTools → Cloud Services → Adobe Experience Platform Launch → Create
  production.uri  = "https://assets.adobedtm.com/...launch-prod.min.js"
  staging.uri     = "https://assets.adobedtm.com/...launch-staging.min.js"
  development.uri = "https://assets.adobedtm.com/...launch-dev.js"
  proxyEnabled    = true   ← serves embed via AEM, avoids ad-blockers

Assign to site:
  Page Properties → Cloud Services tab → select "academy" config
  (or sling:configRef on /content/academy → /conf/academy)
📖 Why this code?

This is a Context-Aware Configuration (module 15). The Core Components Page template reads it and injects the correct script tag automatically.

  • proxyEnabled = true — AEM proxies the Tags JS file. The browser sees a first-party URL, avoiding ad-blocker blocks that would prevent all tracking from firing.

Data Elements reading the ACDL

Data Elements in the Tags UI — reading from ACDL pathsData Element: "Page Name"
  Extension:         Adobe Client Data Layer
  Data Element Type: Data Layer Computed State
  Path:              page.pageInfo.pageName          → "Academy — Home"
  Default Value:     "(unknown)"

Data Element: "Page Template"
  Extension:         Adobe Client Data Layer
  Path:              page.pageInfo.template           → "academy/components/page"

Data Element: "Login Status"
  Extension:         Core
  Type:              JavaScript Variable
  Variable name:     window.adobeDataLayer.getState().user.loginStatus
📖 Why this code?

The "Adobe Client Data Layer" extension in Tags reads ACDL state with dot-notation paths — no custom JavaScript required for standard page data.

  • Data Layer Computed State type — reads from the ACDL's current merged state at evaluation time. The path mirrors the JSON structure shown above.
  • Always set a Default Value — if the path doesn't exist (e.g. a component not present on this page), Data Elements return undefined, which Analytics silently ignores. A default makes missing data visible.

Custom event tracking from component clientlibs

pushing a download event to the ACDL from a component clientlib// /ui.apps/.../clientlib-download/js/download-tracking.js
(function() {
    'use strict';
    document.querySelectorAll('.academy-download-btn').forEach(function(btn) {
        btn.addEventListener('click', function() {
            window.adobeDataLayer.push({
                event: 'academy:download',        // custom event name Tags listens for
                eventInfo: {
                    path: 'component.download',
                    value: {
                        documentTitle: btn.getAttribute('data-doc-title'),
                        documentPath:  btn.getAttribute('data-doc-path')
                    }
                }
            });
        });
    });
}());
📖 Why this code?

Any component can push to the ACDL — this is how Tags learns about user interactions beyond built-in browser events.

  • event: 'academy:download' — a custom event name. In Tags, you create a Rule with event type "ACDL Event Listener" listening for academy:download. When this push executes, that rule fires.
  • A Data Element with type "Event Listener" and path eventInfo.value.documentTitle reads the document title from the push payload inside the Rule's actions.
  • The data-doc-title / data-doc-path attributes are written in the component's HTL template: data-doc-title="${download.title}". The JS reads them at click time.

Testing with the AEP Debugger

what to verify in the DebuggerInstall: "Adobe Experience Platform Debugger" Chrome extension.
Open any page → click the Debugger icon.

LAUNCH TAB:
  ✓ Container loaded: YES
  ✓ Library: launch-xxx-development.js
  ✓ Rules fired: ["Send Page View"]

ANALYTICS TAB:
  ✓ Report Suite: dev-report-suite
  ✓ eVar1: "Academy — Home"
  ✓ Events: event1
  ✓ Beacon: s.t() (page view)

NETWORK TAB (browser DevTools):
  Filter: "b/ss/" → Analytics server calls
  Query parameters: your eVars, props, events
  This is the ground truth if the Debugger gives unexpected results.
📖 Why this code?

The Debugger is the most important tool for Tags/Analytics development. Learn it on day one.

  • The Launch tab shows which Rules fired. Expand a Rule to see which condition failed if it didn't fire.
  • The Analytics tab shows a decoded beacon — far more readable than raw query parameters. Check eVars and events here before declaring an implementation correct.

Analytics Extension vs Web SDK

two integration pathsAdobe Analytics Extension (AppMeasurement.js)
  + Mature, well-documented, familiar eVar/prop/event model
  + Data goes to Adobe Analytics
  - Only Analytics; not other AEP products
  → Use for: existing Analytics projects and organisations new to AEP

Adobe Experience Platform Web SDK (Alloy.js)
  + One beacon for all AEP products (Analytics, Target, RTCDP, CJA)
  + Smaller library, better performance, first-party cookies by default
  - Steeper config: XDM schemas, Datastreams, AEP Sandbox setup required
  → Use for: greenfield projects building on the full AEP platform
📖 Why this code?

The Web SDK is Adobe's strategic direction — all new AEP features require it. The Analytics Extension is in maintenance mode but fully supported.

  • For most current AEM projects, the Analytics Extension is the correct choice — your admin already knows eVars/props, documentation is excellent.
  • Choose Web SDK for new greenfield projects where you're also implementing Target, Offer Decisioning, or Customer Journey Analytics — the unified XDM data model is more efficient than separate beacons per product.
Try it — verify the full pipeline
  1. Enable the ACDL via OSGi config and deploy to your local instance.
  2. Open a page in browser console, run window.adobeDataLayer.getState(). Verify page.pageInfo.pageName is present.
  3. In your Tags property, create "Page Name" Data Element (ACDL path: page.pageInfo.pageName).
  4. Open AEP Debugger. Does the Tags library load? Does eVar1 in the Analytics tab show the page name?
