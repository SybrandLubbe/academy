Servlets & Backend APIs

You've already written path-based servlets in the Java Primer. Here's the rest of the picture: when to register by resource type instead, when to skip the servlet entirely, and how to handle input and errors like a real API.

What you'll learn

  • Path-based vs. resourceType-based servlet registration, and when to use each
  • When a Sling Model's JSON exporter is enough, and when you need a real servlet
  • Reading request parameters safely
  • Building structured JSON responses instead of concatenated strings
  • Why a POST might return 403 even with valid permissions

Two registration styles

The Java Primer's servlets all registered by path — simple, and fine for a handful of standalone endpoints:

path-based (what you've seen so far)@Component(
        service = Servlet.class,
        property = {
                "sling.servlet.paths=/bin/academy/hello",
                "sling.servlet.methods=GET"
        }
)
📖 Why this code?

Path-based servlet registration is the simpler of the two approaches — useful for utility endpoints that aren't tied to specific content.

  • sling.servlet.paths=/bin/academy/hello — registers this servlet against a fixed URL path. Any GET request to that exact URL is routed here, regardless of what content node (if any) lives at that path in the repository.
  • The /bin/ prefix is a convention for non-content API endpoints. The Dispatcher is typically configured to block paths that don't start with /content/ or /bin/, so using this prefix ensures the endpoint is reachable through the Dispatcher.
  • sling.servlet.methods=GET — restricts this servlet to GET requests. Without this, the servlet registers for all HTTP methods, which is usually not what you want for a read-only endpoint.

The AEM-native alternative ties a servlet to a resource type instead, the same mechanism module 3 used for rendering scripts:

resourceType-based@Component(
        service = Servlet.class,
        property = {
                "sling.servlet.resourceTypes=academy/components/search",
                "sling.servlet.selectors=results",
                "sling.servlet.extensions=json",
                "sling.servlet.methods=GET"
        }
)
📖 Why this code?

ResourceType-based registration is the AEM-native way to create endpoints — it ties the servlet to a specific type of content rather than a URL.

  • sling.servlet.resourceTypes=academy/components/search — this servlet only handles requests where the resolved content node has sling:resourceType="academy/components/search". This means the same servlet handles every search component instance, regardless of where in the content tree it lives.
  • sling.servlet.selectors=results — narrows the registration to requests using the .results. selector. A plain .html request to the same component renders the HTL template; a .results.json request routes to this servlet.
  • sling.servlet.extensions=json — combined with the selector, this means only .results.json requests hit this servlet. Other extensions (like .html) are handled normally.

A resourceType-based servlet only answers requests against resources of that type, inherits and can be overlaid exactly like a render script, and stays conceptually attached to actual content instead of a hand-picked URL. Reach for it whenever the endpoint is naturally "an action on this kind of resource" rather than a standalone utility.

When you don't need a servlet at all

If all you need is a resource's properties as JSON, module 6's @Exporter on a Sling Model is simpler to maintain than a hand-rolled servlet — you already used this for student.model.json and page.model.json. Write an actual servlet when you need a non-GET verb, a request body, a response shape that isn't "this resource as JSON," or a side effect (writing content, calling another system).

Handling input safely

Prefer getRequestParameter over the raw getParameter for incoming text — it's encoding-aware and avoids platform-default charset bugs that getParameter is prone to on some setups:

reading parametersString query = request.getRequestParameter("q") != null
        ? request.getRequestParameter("q").getString()
        : null;
📖 Why this code?

Sling's own parameter reading API is safer than the standard servlet API for AEM use.

  • request.getRequestParameter("q") — Sling's encoding-aware version of parameter reading. Unlike request.getParameter("q") (the standard Servlet API), this method handles character encoding correctly across all platforms, avoiding subtle character corruption bugs with non-ASCII input.
  • The null check before calling .getString() is necessary — if the parameter isn't present in the request, getRequestParameter() returns null, and calling null.getString() would throw a NullPointerException.

Returning JSON cleanly

String concatenation worked for the Primer's single-field error responses, but it breaks down fast once a response has nested or repeated data — a stray unescaped character and the response is no longer valid JSON. Build it with a JSON library instead:

SearchServlet.java (excerpt)import javax.json.Json;
import javax.json.JsonObjectBuilder;
import javax.json.JsonArrayBuilder;

JsonArrayBuilder results = Json.createArrayBuilder();
matches.forEach(page -> results.add(
        Json.createObjectBuilder()
                .add("title", page.getTitle())
                .add("path", page.getPath())
));

JsonObjectBuilder responseBody = Json.createObjectBuilder()
        .add("count", matches.size())
        .add("results", results);

response.setContentType("application/json");
response.getWriter().write(responseBody.build().toString());
📖 Why this code?

Using the javax.json API (built into AEM's JVM) to build a structured JSON response safely.

  • Json.createArrayBuilder() and Json.createObjectBuilder() — the builder pattern ensures every string value is properly JSON-escaped. Building JSON by string concatenation is dangerous — a title containing a quote character would break the JSON structure or, worse, enable JSON injection attacks.
  • The result is a well-formed JSON array where each element is an object with title and path fields. The builder API handles all escaping, quoting, and structural characters automatically.

javax.json ships with AEM, so this needs no extra dependency.

CSRF protection on state-changing requests

Any non-GET request is checked by Sling's CSRF filter before it reaches your servlet at all. A client has to first fetch a token from /libs/granite/csrf/token.json and send it back as a CSRF-Token header on the POST/PUT/DELETE — without it, the filter rejects the request with a 403, regardless of whether the caller actually had permission to make the change.

Common pitfall A POST that returns 403 in AEM is, more often than not, a missing CSRF token rather than a permissions problem. Check the response body for a CSRF-related message before spending time auditing ACLs.
Try it Change the Primer's ValidationServlet from GET to POST (update both the @Component property and the method name to doPost). Confirm a plain curl -X POST now gets a 403, then fetch a token from /libs/granite/csrf/token.json and pass it as a CSRF-Token header to get through.
